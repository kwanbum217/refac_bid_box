## 6. 워커 운영에서 배운 것

### 6.1 워크트리 기준 커밋이 뒤처집니다

**`orca worktree create` 는 현재 `main` 이 아니라 세션 시작 시점 커밋을
기준으로 워크트리를 만듭니다.** 다섯 번째 워크트리(`orca-ng2b`)가 15커밋
뒤처졌고, 워커가 선행 Task 의 코드를 찾지 못해 1분 24초 만에 정확히
escalation 했습니다.

**세션 초반에는 드러나지 않습니다.** 그때는 세션 시작 커밋과 `main` 이 같기
때문입니다. 병합을 몇 번 한 뒤 새 워크트리를 만드는 순간부터 어긋납니다.

조치는 워크트리 생성 직후
`git -C <워크트리> rev-list --count HEAD..main` 확인이고, 0 이 아니면
`--base-branch main` 을 주거나 그 워크트리에서 `main` 을 병합합니다.
코디네이터가 만든 병합 커밋은 워커가 되돌리지 않도록 지시문에 명시합니다.

### 6.2 escalation 은 `orchestration reply` 로 답해야 합니다

터미널로 지시를 보내면 워커는 읽지만 **Task 는 답변 대기로 남습니다.**
`orca_worker_watch.py` 가 `[차단:답변 대기]` 로 표시하며, 다음 Dispatch 가
막힐 수 있습니다. `orca orchestration reply --id <msg_id> --run <run_id>
--body '<답변>'` 이 정규 경로입니다.

### 6.3 워커 effort 는 명시 지정해야 합니다

`~/.codex/config.toml` 에 `model_reasoning_effort = "xhigh"` 가 전역으로 박혀
있고 `scripts/orca_codex_launch.py` 는 `--effort` 미지정 시 아무것도 넘기지
않습니다. 그래서 **Codex 워커가 전부 xhigh 로 뜹니다.** DB 조회 반복이나
파일 재배치 같은 절차적 과제도 최고 등급으로 돌아갑니다.

사용자 지시입니다. **작업 성격에 맞춰 `--effort` 를 명시하십시오.** 문서·조사·
절차적 구현은 `medium`, 원인 추적처럼 추론 밀도가 필요한 것만 `high` 입니다.
이미 기동해 진척이 있는 워커는 effort 를 고치려고 재기동하지 마십시오. 되던
작업을 버리고 토큰을 다시 태우는 쪽이 더 비쌉니다.

### 6.4 모델 풀 등록

### 6.5 워커 기동 경로

CLI 마다 기동 방식이 다릅니다.

| CLI | 경로 |
| --- | --- |
| Codex | `worker-start --agent codex --worktree path:<경로>` 직접 (감독) |
| qwen / opencode | `terminal create --command '<런처>'` 후 `taskctl dispatch --terminal --launcher` (비감독) |

`terminal create` 에 `--command` 로 런처를 지정하지 않으면 `dispatch --inject`
가 `no_agent_detected` 로 거부합니다. 런처 없이 만든 빈 터미널에는 붙지
않습니다.

`worker-start --repo .` 는 `repo_not_found` 입니다. `--repo path:<절대경로>`
형태여야 합니다.

### 6.6 Level 1 게이트의 `--verify`

mypy 는 `--tests` 로 넣을 수 없습니다. `--tests` 는 pytest 대상 경로만 받습니다.
`--verify 'mypy src'` 를 써야 `backend_mypy` 능력이 덮입니다. 빠뜨리면
`blocking_skipped` 에 남아 게이트가 완결되지 않습니다.

### 6.7 `worker_done` 보고 형식이 게이트를 막습니다

이번 세션에서 게이트 6 실패가 네 번 있었고 **전부 내용이 아니라 보고 형식**
이었습니다.

| 증상 | 원인 |
| --- | --- |
| 보고 파일 없음 | `.orca/capsules/<task>/worker_done.json` 미작성 |
| `changed_files` 불일치 | 이력상 건드린 파일을 적음. 게이트는 `git diff main...HEAD` 순 변경과 대조 |
| commit SHA 실존성 실패 | 41자 (한 글자 더 붙음) |
| 검증 불일치 | `result` 에 경위 서술을 넣어 실패 보고로 읽힘 |
| 중간 결과 보고 | 수정 도중의 `70 passed, 1 failed` 를 최종 결과로 적음. 실제 재실행은 `71 passed` |

**Capsule 에 다음 세 줄을 넣으면 대부분 막힙니다.** `changed_files` 는
`git diff main...HEAD` 순 변경과 일치할 것, `commit_shas` 는 `git rev-parse`
로 읽은 40자일 것, `verification[].result` 에는 경위 없이 최종 숫자만 적을 것.

**워커는 검증 명령을 여러 번 돌리고 그 중 하나를 보고에 적습니다.** 수정
도중에 실패했다가 고친 뒤 통과한 경우, 중간 결과가 그대로 남기 쉽습니다.
Capsule 에 "최종 재실행 결과만 적어라" 를 명시하고, 코디네이터는 게이트가
잡아주기 전에 의심스러운 항목을 직접 한 번 돌려 보십시오. 2026-09-10 에
전량 테스트는 통과인데 지정 테스트만 실패로 적힌 모순이 있었고, 직접 돌리니
실패 0 이었습니다.

**필드명을 `reported_result` 라고 부르지 마십시오.** 그것은 게이트가 내부에서
쓰는 이름이고 `worker_done.json` 스키마의 실제 필드는 `result` 입니다.
2026-09-10 에 코디네이터가 지시문에 `reported_result` 라고 적어 워커가 필드명을
바꿨고 형식 위반 6건이 나 왕복이 한 번 더 들었습니다. 게이트 출력에 보이는
이름과 워커가 쓸 이름이 다르다는 점을 기억하십시오.

### 7.1 diff 를 읽는 것과 제어 흐름을 추적하는 것은 다릅니다

NG2b 에서 리뷰가 잡은 둘은 **Level 1 게이트와 코디네이터 Level 3 를 모두
통과한 뒤에 나왔습니다.**

| 결함 | 내용 |
| --- | --- |
| `id` 중복 | 신설 분포 블록이 NG1 블록과 같은 `id="negotiation-info"` 를 씀. jQuery 가 첫 요소만 잡아 **NG1 블록이 영구히 숨겨짐** |
| 렌더 미도달 | `if (renderNegotiation(data)) { return; }` 가 `renderNegotiationDistribution(data)` 보다 앞에 있어 **협상 공고에서 분포가 전부 대시로만 보임** |

못 잡은 이유가 각각 다릅니다.

| 검증 | 한계 |
| --- | --- |
| Level 1 게이트 | 파일 범위·테스트·mypy·린터를 본다. HTML `id` 중복과 JS 제어 흐름은 대상이 아니다 |
| 테스트 | 백엔드 집계만 덮었다. 템플릿 렌더 경로를 검사하는 테스트가 없었다 |
| 코디네이터 Level 3 | 백엔드는 실제 DB 로 실행해 20개 값을 검증했으나 **템플릿은 diff 만 읽었다** |

**추가된 줄만 보면 정상으로 보입니다.** 기존 코드와의 상호작용은 추가된 줄에
나타나지 않습니다. 템플릿이나 프런트엔드 변경을 검토할 때는 다음 둘을
diff 밖에서 확인하십시오.

- 새로 붙인 `id` 와 클래스가 파일 안에서 **유일한지** (`grep -c`)
- 새 렌더 함수가 **실제로 호출에 도달하는지**. 앞선 분기의 조기 `return` 을
  따라가 보십시오

2026-09-09 의 "구조는 맞고 값은 틀림" 이 이번에는 "구조는 맞고 화면에 안 뜸"
으로 재현됐습니다. 재작업에서 템플릿 문자열의 `id` 출현 횟수와 렌더 도달을
검사하는 회귀 테스트를 요구해 다음부터는 게이트에서 걸리게 했습니다.

## 8. 잔여 과제

### 8.1 flaky 테스트 (세션 중 해소)

`tests/test_evaluations_api.py` 의 `assert "999" not in response.text` 가
flaky 했습니다. NG2b 재작업 워커가 자기 범위 밖인데도 제보했고 세션 안에서
고쳤습니다(`833f369`).

`999` 는 센티넬입니다. 클라이언트가 `price_score: 999`, `total_score: 999` 를
보내고 서버가 그 값을 되돌려주지 않는지 검사합니다. **의도는 맞지만 대상이
틀렸습니다.** 응답 본문 전체를 문자열로 훑어 타임스탬프나 금액이나 ID 에
우연히 `999` 가 들어가면 실패했습니다.

파싱한 JSON 을 순회하며 **값이 정확히 999 인 자리만** 모으는 헬퍼로 바꿨고
되돌아온 경로를 실패 메시지에 담았습니다. 불리언은 정수와 비교되지 않도록
먼저 걸러냅니다. 센티넬은 `SENTINEL_SCORE` 상수로 단일화했습니다.

검증한 네 경우입니다.

| 입력 | 결과 |
| --- | --- |
| `price_score: 999` 되돌아옴 | 탐지 (경로 포함) |
| 문자열 `"999"` 되돌아옴 | 탐지 |
| `2026-09-10T11:59:99.999123`, 금액 `999000000` | 오탐 없음 |
| `True`, `0`, `None`, `"x999y"` | 오탐 없음 |

**같은 패턴을 다시 쓰지 마십시오.** 응답 원문 문자열에서 값을 찾는 검사는
언제든 무관한 자리의 우연한 일치로 깨집니다. 값 검사는 파싱한 구조에서
하십시오.

### 8.2 NG2b 테스트 커버리지 (세션 중 해소)

`tests/test_negotiation_stats.py` 가 2건뿐이고 `isolated_db`(SQLite)만 타서
운영 MySQL 경로와 변종 배제 로직이 고정돼 있지 않았습니다. 세션 안에서
11건으로 보강했습니다(`53fb6af`).

**MySQL 을 띄우지 않고 그 분기를 덮었습니다.** `sqlalchemy.dialects.mysql.dialect()`
로 `select` 문을 **컴파일만** 해서 나온 SQL 에 `LPAD` 와 `json_unquote` 가
들어 있는지 봅니다. 실행하지 않으므로 Docker 가 내려가 있어도 돕니다.
SQLite 쪽은 같은 방식으로 `printf` 를 확인합니다.

덮은 회귀입니다.

| 회귀 | 왜 위험한가 |
| --- | --- |
| MySQL 분기 미실행 | 테스트는 SQLite 만 타고 운영은 MySQL 만 탄다 |
| `STANDARD` 가 전체를 삼킴 | 마커가 빈 문자열이라 나머지 셋 부정 배제가 깨지면 3,975건이 4,999건이 된다 |
| `ENGINEERING` 이 건설엔지니어링을 잡음 | 괄호 구분이 깨지면 두 변종이 섞인다 |
| 경계 `50`·`110` | 포함이어야 한다. `49`·`111` 만 검사하면 경계 자체는 안 덮인다 |
| 0건·미지 변종 | `statistics.median` 이 빈 목록에서 터진다 |

독립 리뷰가 각 테스트에 대해 **해당 회귀를 일부러 깨뜨렸을 때 실패하는지**
논증하도록 요구했고 12항목 전부 통과했습니다.
