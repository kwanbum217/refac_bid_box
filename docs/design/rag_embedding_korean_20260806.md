# RAG 임베딩 한국어 대응 실측과 교체

> **작성일**: 2026-08-06
> **대상**: `src/rag/embeddings.py`, `src/app/services/kb_builder.py`, `src/rag/vector_store.py`
> **상태**: 교체·운영 재색인 완료

---

## 1. 발단

KB 커버리지 확대(최근 1년 50만 건)를 검토하면서, 4.8시간·2.25GB 를 쓰기 전에 검색 품질부터 확인하려고 1만 건을 격리 경로에 적재해 실측했습니다.

**그 실측이 커버리지보다 앞선 문제를 드러냈습니다.**

---

## 2. 측정 방법

정답을 아는 질의를 씁니다. 색인된 공고 100건을 시드 42 로 뽑고, 각 공고의 `공고명 + 수요기관` 을 그대로 질의해 **그 문서가 상위 몇 번째에 오는지** 셌습니다. 정답이 색인 안에 있으므로 상위권에 나와야 정상입니다.

---

## 3. 결과: 현행 임베딩은 한국어에서 작동하지 않습니다

| top-k | ONNXMiniLM_L6_V2 (현행) | bge-m3 |
| --- | ---: | ---: |
| top-1 | 1.0% | **89.0%** |
| top-3 | 3.0% | **99.0%** |
| **top-5 (운영값)** | **4.0%** | **100.0%** |
| top-20 | 11.0% | 100.0% |
| 정답 순위 중앙값 | 9 | **1** |

정답을 그대로 물어봐도 상위 5개 안에 나올 확률이 4% 였습니다.

---

## 4. 원인 규명

문서 임베딩이 서로 구분되지 않았습니다.

| 지표 | MiniLM | bge-m3 |
| --- | ---: | ---: |
| 문서 간 코사인 유사도 평균 | 0.894 | **0.622** |
| 유사도 0.9 이상 비율 | **60.5%** | **0.1%** |

원인이 문서 템플릿 때문인지 모델 때문인지 분리하려고, 같은 모델에 짧은 문구만 넣어 대조했습니다.

| 쌍 (무관한 주제) | MiniLM | bge-m3 |
| --- | ---: | ---: |
| "도서관 건축공사" vs "상수도 배관 정비" | 0.829 | 0.519 |
| "교통계획 수립 용역" vs "청사 경비 용역" | 0.806 | 0.669 |
| "서울특별시" vs "경상북도 봉화군" | 0.628 | 0.328 |
| `library construction` vs `water pipe maintenance` | **0.129** | - |
| `traffic planning service` vs `building security service` | **0.314** | - |

**같은 모델인데 영어는 0.13~0.31 로 잘 구분하고 한국어는 0.81~0.83 으로 붙습니다.** `all-MiniLM-L6-v2` 는 영어 전용이며, 한국어에서는 벡터가 의미가 아니라 "한국어 텍스트"라는 공통 신호에 지배됩니다. 문서 템플릿이 아니라 모델이 원인입니다.

---

## 5. 비용은 오히려 줄었습니다

| 항목 | MiniLM | bge-m3 |
| --- | ---: | ---: |
| 1만 건 적재 | 345.5초 | **213.6초** |
| 처리량 | 초당 28.9건 | **초당 46.8건** |
| 벡터 차원 | 384 | 1,024 |

파라미터가 25배 큰 모델인데 더 빠릅니다. Ollama 가 Metal GPU 를 쓰고 기존 ONNX 모델은 CPU 에서 돌기 때문입니다. **품질과 속도 사이에 트레이드오프가 없습니다.**

새 파이썬 의존성은 없습니다. Ollama `/api/embed` 를 `httpx` 로 호출하며 `httpx` 는 이미 사용 중입니다.

---

## 6. 기존 "임베딩 교체 금지" 제약의 재검토

교체를 금지한 근거는 "기존 19개 컬렉션이 원래 임베딩으로 색인돼 있다" 였습니다. 현재 사실관계가 다릅니다.

| 당시 전제 | 2026-08-06 실측 |
| --- | --- |
| 19개 컬렉션 | **1개** (`bidding_kb`) |
| 원본 임베딩 보존 필요 | 운영 컬렉션은 이미 재구축된 500건 |
| - | 원본 10건은 `data/backups/chroma_source` 에 **별도 스냅샷 보존** |

G1 무손실은 원본 스냅샷이 담당하며 `verify_migration.py` 가 그쪽 체크섬을 대조합니다. 운영 컬렉션은 `rebuild_knowledge_base` 로 언제든 다시 만드는 파생물이므로, 임베딩 교체가 무손실 원칙에 저촉되지 않습니다.

---

## 7. 구현

### 7.1 단일 진입점

`src/rag/embeddings.py` 의 `get_embedding_function()` 과 `get_collection()` 만 씁니다.

| 호출자 | 용도 |
| --- | --- |
| `kb_builder.rebuild_knowledge_base` | 색인 |
| `vector_store.retrieve_semantic_context` | 질의 |
| `verify_migration.probe_chroma_query` | 검증 프로브 |

**색인과 질의가 다른 임베딩을 쓰면 예외 없이 결과만 엉망이 됩니다.** `client.get_collection(name)` 을 그냥 부르면 ChromaDB 가 기본 함수를 끼워 넣으므로, 반드시 이 모듈을 거치도록 배선하고 테스트로 고정했습니다.

### 7.2 설정

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `EMBEDDING_PROVIDER` | `ollama` | `default` 로 두면 ChromaDB 내장 MiniLM 으로 되돌립니다 |
| `EMBEDDING_MODEL` | `bge-m3` | Ollama 모델명 |

테스트는 `conftest.py` 에서 `default` 로 고정합니다. 운영 기본값을 쓰면 테스트가 로컬 Ollama 에 의존해 CI 에서 깨집니다.

## 8. 부수 발견: 검증이 규모를 부풀리고 있었습니다

재색인 후 검증이 운영 1,500건을 보고했는데 실제 컬렉션은 500건이었습니다.

| 세그먼트 | 임베딩 | 상태 |
| --- | ---: | --- |
| `8a914f3c` | 500 | 현재 컬렉션 |
| `4d4bd3c0` | 500 | 고아 (삭제된 컬렉션 잔재) |
| `f088fb5c` | 500 | 고아 |

`read_chroma_stats` 가 `embeddings` 테이블을 통째로 세고 있었습니다. `segments`, `collections` 와 조인해 **살아 있는 컬렉션만** 세도록 고쳤습니다. 이전에 "운영 1,000건"으로 보고되던 것도 실제로는 500건이었습니다.

---

## 9. 검증

| 항목 | 결과 |
| --- | --- |
| 운영 재색인 | 500건 / 20.3초 |
| G1 무손실 | `verify_migration.py` **4/4** (질의 프로브 포함) |
| 전량 테스트 | **747 passed / 2 skipped** |
| 신규 테스트 | `tests/test_rag_embeddings.py` 10건 |

교체 직후 `verify_migration` 이 차원 불일치(1024 대 384)를 실패로 잡아냈고, 재색인 후 통과했습니다. 검증이 실제로 동작한다는 확인이기도 합니다.

## 10. 되돌리기

```
EMBEDDING_PROVIDER=default
```

환경변수를 바꾼 뒤 `rebuild_knowledge_base(db, full=True)` 를 한 번 돌리면 원상 복구됩니다. 재색인 직전 컬렉션은 별도 백업해 두었습니다.

## 11. 다음 단계

이제 커버리지 확대를 재논의할 수 있습니다. 검색이 동작하므로 문서를 늘리는 것이 의미를 갖습니다.

| 규모 | 적재 시간 | 디스크 |
| --- | ---: | ---: |
| 1만 건 (실측) | 213.6초 | 71.6MB |
| 10만 건 | 약 36분 | 약 0.70GB |
| 50만 건 (최근 1년 전량) | 약 3시간 | 약 3.49GB |

MiniLM 대비 적재는 1.6배 빠르고 디스크는 1.55배 늘어납니다(50만 건 기준 2.25GB -> 3.49GB). 차원이 2.7배인데 디스크가 그만큼 늘지 않는 것은 문서 본문과 메타데이터가 함께 저장되기 때문입니다.

증분 색인이 이미 들어가 있어 초기 적재만 한 번 비싸고 이후 야간 재색인은 변경분에 비례합니다.
