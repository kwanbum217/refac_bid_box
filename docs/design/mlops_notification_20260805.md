# MLOps 알림 설계

> **작성일**: 2026-08-05
> **버전**: v1.0.0
> **상태**: 설계만 완료. 구현 미착수
> **예상 작업량**: 1시간 이내

---

## 1. 왜 필요한가

원본 `bid_box`는 Harness(SaaS)가 실행 엔진이었고 대시보드로 상태를 볼 수
있었습니다. 리팩토링에서 실행 백엔드를 Arq 로 바꾸면서 **자율성과 재현성을
얻고 운영 가시성을 내줬습니다.**

| 잃은 것 | 현재 상태 |
| --- | --- |
| 관리 UI | DB 직접 조회 또는 로그 |
| 실패 알림 | **없음** |
| 승인 게이트 | 없음 (수동 `promote()`) |
| 감사 로그 | 남지 않음 |

이 중 **알림 부재가 가장 큰 구멍입니다.** 두 가지 이유입니다.

**첫째, 실패가 조용합니다.** 주간 재학습(`weekly_retrain_task`, 매주 월요일
03:00)이 실패해도 아무도 모릅니다. `retrain_logs` 에 기록은 남지만 보는 사람이
없으면 의미가 없고, 실제로 그 표가 오랫동안 비어 있던 전력이 있습니다
(`retrain_task.py:75`). **주간 크론이 실환경에서 완주한 이력이 아직
없습니다.**

**둘째, 승격이 수동인데 신호가 전달되지 않습니다.** 재학습 태스크는
`PROMOTE_CHALLENGER` / `REJECT_CHALLENGER` 권고만 남기고, 실제 서빙 루트 교체는
사람이 `src/ml/promotion.py::promote()` 를 호출해야 합니다. 그런데 **승격할 만한
모델이 나왔다는 사실 자체가 어디로도 전달되지 않습니다.** 알림이 그 고리를
잇습니다.

승격 수동화 자체는 의도된 설계이며 근거가 있습니다. 2026-08-05 에 `num_leaves`
127 이 승격 게이트 4개를 전부 통과하고 홀드아웃에서 champion 을 이겼으나, 운영
쌍대 비교에서 제곱오차가 유의하게 나빴습니다(t=2.13). 자동 승격이었다면 서비스가
조용히 나빠졌을 것입니다.

## 2. 방식 선택

| 방식 | 작업량 | 새 의존성 | 판정 |
| --- | --- | --- | --- |
| **웹훅 (Slack/Discord)** | 작음 | 없음 (`httpx`) | **채택** |
| 조회 화면 | 중간 | 없음 | 보완재. 능동 조회만 가능 |
| 챗봇 통합 | 중간 | 없음 | 보완재. 사람이 묻지 않으면 모름 |
| 이메일 (SMTP) | 중간 | 표준 라이브러리 | 설정 부담이 큼 |

웹훅을 택한 이유입니다.

- `httpx` 가 이미 의존성에 있어 **새 라이브러리 협의가 불필요**합니다
  (`api_collector.py`, `automation_tasks.py`, `rag/llm.py` 에서 사용 중)
- `AUTOMATION_CALLBACK_BASE_URL` 이라는 **선례가 config 에 이미 있어** 같은
  패턴을 따르면 됩니다
- 실패를 **밀어서** 알려주므로 사람이 보러 갈 필요가 없습니다

조회 화면과 챗봇 통합은 **알림을 대체하지 못합니다.** 사람이 묻지 않으면
여전히 모르기 때문입니다. 보완재로만 검토합니다.

## 3. 설계

### 3.1 설정

```python
# src/app/core/config.py
# 비면 알림을 보내지 않습니다. 개발 장비에서 끄기 위한 장치이며
# ML_WEEKLY_RETRAIN_ENABLED 와 같은 규약입니다.
MLOPS_WEBHOOK_URL: str = ""
```

`.env` 에 실제 URL 을 둡니다. **문서와 코드에 실제 값을 적지 않습니다**
(AGENTS.md 금지 4항).

### 3.2 발신 모듈

신설: `src/tasks/notifier.py`

```python
async def notify(title: str, lines: list[str], *, level: str = "info") -> None:
    """웹훅으로 한 건 보냅니다.

    **알림 실패가 본 작업을 되돌리면 안 됩니다.** 웹훅이 죽어 있다고 재학습
    결과가 날아가면 본말전도입니다. 예외를 삼키고 로그만 남깁니다.
    """
```

| 결정 | 근거 |
| --- | --- |
| 예외를 삼킨다 | 알림은 부가 기능. 본 파이프라인을 막으면 안 됩니다 |
| 타임아웃 10초 | 워커가 웹훅 응답을 오래 기다릴 이유가 없습니다 |
| URL 이 비면 즉시 반환 | 개발 장비 기본 동작 |
| 재시도 없음 | 실패해도 `retrain_logs` 에 원본 기록이 남습니다 |

### 3.3 통합 지점

| 위치 | 시점 | 내용 |
| --- | --- | --- |
| `retrain_task.run_retrain_pipeline_task` | `_record` 직후 | 재학습 결과와 승격 권고 |
| `retrain_task` 예외 경로 | `except` | 실패 사유 |
| `scheduled_tasks.weekly_retrain_task` | `except` | 스케줄 실패 |
| `scheduled_tasks.nightly_schedule_task` | `except` | 야간 수집 실패 |

야간 수집을 함께 태우는 이유입니다. **02:00 수집이 실패하면 03:00 재학습은 옛
데이터로 돌고, 그것도 조용히 지나갑니다.**

## 4. 무엇을 알릴 것인가

**성공보다 실패와 조치 필요 사항이 중요합니다.** 매주 "정상 완료" 만 오면 사람이
읽지 않게 됩니다.

| 사건 | 수준 | 알릴 이유 |
| --- | --- | --- |
| 재학습 예외·실패 | 경고 | 파이프라인이 멈춘 상태 |
| **`PROMOTE_CHALLENGER` 권고** | **조치 필요** | 승격이 수동이므로 사람이 움직여야 합니다 |
| `holdout_is_overfit` | 경고 | 표본 부족 신호. 지표를 믿을 수 없습니다 |
| 학습 데이터가 비었음 | 경고 | 수집 파이프라인 이상 |
| 야간 수집 실패 | 경고 | 다음 재학습이 옛 데이터로 돕니다 |
| `REJECT_CHALLENGER` | **보내지 않음** | 정상 동작. champion 유지 |

`REJECT_CHALLENGER` 를 제외하는 것이 핵심입니다. 대부분의 재학습은 기각으로
끝나므로 그것까지 보내면 알림이 소음이 됩니다.

### 4.1 메시지에 담을 것

승격 권고 알림이 가장 중요하므로 **바로 판단할 수 있는 정보**를 담습니다.

```
[조치 필요] 용역 모델 승격 권고
  champion  v_20260805_052203_525  R2 0.6824 / RMSE 2.6998
  challenger v_20260812_030512_118  R2 0.6901 / RMSE 2.6670
  표본 917,629 / 트리거 weekly_schedule

  승격 전 운영 경로 쌍대 비교를 거치십시오.
    scripts/compare_servc_models_paired.py
```

마지막 줄이 중요합니다. 2026-08-05 에 홀드아웃 개선이 운영에서 **세 번 연속**
재현되지 않았으므로, 알림이 곧바로 승격을 권하는 문구가 되면 안 됩니다.

## 5. 테스트 계획

| 대상 | 검증 |
| --- | --- |
| URL 미설정 | 호출해도 아무 일이 없고 예외도 없을 것 |
| 웹훅 응답 500 | 예외가 밖으로 새지 않을 것 |
| 웹훅 타임아웃 | 본 작업이 계속될 것 |
| `REJECT_CHALLENGER` | 발신하지 않을 것 |
| `PROMOTE_CHALLENGER` | 발신하고 두 버전 지표를 담을 것 |

`httpx` 응답은 `monkeypatch` 로 대체합니다. 실제 네트워크를 태우면 테스트가
외부 상태에 묶입니다.

## 7. 범위 밖

이번 설계에 넣지 않는 것들입니다.

| 항목 | 이유 |
| --- | --- |
| 자동 승격 | 의도적으로 수동 유지 (1장 근거) |
| 감사 로그 | 1인 작업이라 승인 주체가 하나뿐 |

| 재시도·큐잉 | `retrain_logs` 에 원본이 남으므로 과잉 |
| 챗봇 통합 | 능동 조회라 알림을 대체하지 못함. 보완재로 후순위 |
