# SSE 첫 토큰 지연 진단과 대책

> **작성일**: 2026-08-05
> **버전**: v1.0.0
> **상태**: 대책 적용 완료. 2026-08-06 병합 상태에서 P95 3.01초 재현 확인 (4.1절)

---

## 1. 무엇이 잘못 진단돼 있었나

Phase 7 검증에서 SSE 첫 토큰 P95 11.06초가 목표 3초에 미달했고, 인수인계서는 원인을 로컬 LLM 프리필로 지목하며 **"애플리케이션 최적화로는 도달 불가"** 라고 적었습니다. 근거는 질의별 분해 측정이었습니다.

| 질의 | 검색 | LLM 첫 토큰까지 |
| --- | ---: | ---: |
| 적격심사 기준이 어떻게 되나요 | 51ms | 6,924ms |
| 수요기관별 낙찰 금액 상위 | 62ms | 10,101ms |

검색이 50~65ms 이므로 검색을 0으로 만들어도 6초 아래로 못 간다는 결론이었습니다. **측정은 맞았고 해석이 틀렸습니다.** "LLM 첫 토큰까지" 안에 무엇이 들어 있는지를 쪼개지 않았습니다.

---

## 2. 실제 원인 두 가지

Ollama 는 응답에 `load_duration`, `prompt_eval_duration`, `eval_duration` 을 실어 줍니다. 그것으로 쪼갠 결과입니다.

### 2.1 사고(thinking) 단계

`gemma4:e4b` 는 사고형 모델입니다. 스트리밍 청크를 그대로 찍어 보면 이렇습니다.

```
0.57s 청크1 keys=['role','content','thinking'] thinking='Here' content=''
0.59s 청크2 keys=['role','content','thinking'] thinking="'"    content=''
```

**사고 토큰은 0.57초에 이미 나옵니다.** 우리 클라이언트가 읽는 `message.content` 는 사고가 끝난 뒤에야 시작되므로, 그 사이 화면에는 아무것도 뜨지 않습니다.

| 조건 | 첫 토큰 (5개 질의 평균) |
| --- | ---: |
| 사고 켜짐 (기본값) | 10.53초 |
| `think: false` | **0.38초** |

전체 답변 시간도 35.4초에서 18.3초로 줄었고, 같은 질의에 대한 답변 품질은 대등했습니다(2,235자 대 1,954자, 구성과 정확도 유사).

### 2.2 모델 로드 (콜드 스타트)

| 회차 | 모델 로드 | 프리필 | 첫 토큰 |
| --- | ---: | ---: | ---: |
| 콜드 | 11.78초 | 0.15초 | 11.92초 |
| 웜 | 0.51초 | 0.10초 | 0.61초 |

Ollama 기본 `keep_alive` 는 5분입니다. 질의가 뜸한 시간대의 첫 사용자가 매번 12초를 냅니다.

### 2.3 프리필은 원인이 아니었습니다

| 프롬프트 | 토큰 | 프리필 |
| --- | ---: | ---: |
| 인위적 대형 프롬프트 | 2,168 | 3.13초 |
| **실제 운영 프롬프트** | 약 300 | **0.1초 미만** |

실제 프롬프트는 `SYSTEM_PROMPT` 813자에 질의별 컨텍스트 128~414자입니다. 프리필은 1.4ms/토큰이므로 여기서 깎을 것이 없습니다.

## 3. 적용한 대책

| 대책 | 위치 | 기본값 |
| --- | --- | --- |
| 사고 끄기 | `src/rag/llm.py` `_payload` 가 `think: false` 를 실음 | `LLM_THINKING=false` |
| 모델 상주 | 요청마다 `keep_alive` 명시 | `OLLAMA_KEEP_ALIVE=-1` |
| 기동 예열 | `src/app/main.py` lifespan 배경 태스크 | `LLM_WARMUP_ON_STARTUP=true` |
| 집계 캐시 | `src/rag/structured_data.py` `_cached_aggregate` | TTL 1시간 |

`keep_alive` 는 문자열이 아니라 숫자로 보내야 합니다. `"-1"` 을 그대로 보내면 Ollama 가 `missing unit in duration` 으로 400 을 내며, 값이 무시되는 것이 아니라 **요청 자체가 실패**합니다. `_coerce_keep_alive` 가 이 변환을 담당합니다.

집계 캐시는 3,405,928행 위의 COUNT/AVG/SUM 이 질의당 190ms 이고 한 요청에 아홉 번 돌아 1.72초를 쓰기 때문입니다. 캐시 적중 시 0.571초에서 0.0008초가 됐고 값은 동일했습니다.

## 4. 결과

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| LLM 첫 토큰 (5개 질의 평균, 계층 단독) | 10.53초 | **0.38초** |
| SSE 첫 토큰 P95 (30회, 부하 4.4) | 11.06초 | **3.05초** |
| SSE 첫 토큰 P50 | - | 0.75초 |
| SSE 전체 P95 | 13.19초 | 4.41초 |

**측정 신뢰도에 단서를 답니다.** 같은 벤치마크를 장비 부하 6.5에서 다시 돌렸을 때 P95 가 5.57초로 튀었습니다. 병렬 세션이 모델 학습으로 CPU 를 점유하는 중이었습니다.

### 4.1 병합 후 재측정 (2026-08-06)

`main` 병합 상태에서 10회로 다시 쟀습니다. 병렬 학습 세션이 없는 상태였습니다.

| 지표 | 값 | 목표 |
| --- | ---: | ---: |
| 첫 토큰 P50 | 1.14초 | - |
| 첫 토큰 P95 | **3.01초** | 3.00초 |
| 전체 응답 P95 | 7.39초 | 20.00초 |

08-05 의 3.05초가 병합 상태에서 재현됐습니다. 개선은 특정 실행의 우연이 아닙니다. 목표선을 10ms 넘겼으나 표본 10회에서 P95 는 사실상 최댓값 근처이므로, 이 차이를 유의미한 미달로 보지 않습니다.

남은 꼬리는 전부 DB 집계 경로입니다. 08-05 에는 `2025년 물품 낙찰 평균 낙찰률` 계열이, 08-06 재측정에서는 최장 3건이 모두 `공사 부문 최근 낙찰 동향` 이었습니다. **다음 개선 대상은 LLM 이 아니라 이 집계 쿼리입니다.**

### 4.2 상위 N 실시간 경로 캐시 (2026-08-06)

4.1 의 꼬리를 단계별로 쪼갠 결과, **집계(COUNT/AVG/SUM)는 병목이 아니었습니다.** `retrieve_structured_data` 전체가 콜드 121ms / 웜 11ms 였습니다. 실제 2초를 쓰는 것은 상위 N `GROUP BY` 와 손상 탐지 `LIKE` 였고, 이들만 캐시를 거치지 않고 있었습니다.

| 질의당 소요 | 값 |
| --- | ---: |
| `bid_ntce_nm` 상위 N GROUP BY | 777ms |
| `dminstt_nm` 상위 N GROUP BY | 402ms |
| 손상 탐지 LIKE 2건 | 644ms |

원인은 `_snapshot_scope` 가 **날짜 필터가 붙는 순간 사전 집계 스냅샷을 포기**한다는 데 있습니다. "2026년" 같은 흔한 표현이 곧 날짜 필터이므로 실시간 경로가 자주 탔고, 같은 질의를 두 번 물어도 1,967ms 가 그대로 다시 들었습니다.

`_top_rows` 의 실시간 경로에 집계와 같은 TTL 캐시를 붙였습니다. 손상 탐지 결과도 함께 담습니다. 순위만 담으면 적중할 때마다 탐지 질의가 다시 돌아 절반만 아낍니다.

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| 동일 질의 반복 시 정형 조회 | 1,967ms | **5ms** |
| SSE 첫 토큰 P95 (10회) | 3.01초 | **2.66초** |
| SSE 첫 토큰 P50 | 1.14초 | 1.12초 |
| SSE 전체 P95 | 7.39초 | 6.39초 |

**목표 3초를 달성했습니다.** 콜드 첫 질의는 여전히 약 2초를 쓰며, 이는 캐시 설계상 남는 비용입니다. 더 줄이려면 스냅샷이 날짜 창을 포기하지 않도록 사전 집계 축을 넓혀야 하고, 그때는 조합 폭발을 어디서 끊을지 따로 정해야 합니다.

## 5. 목표 재설정에 대하여

3초라는 목표는 Gemini(클라우드) 기준으로 잡혔다가 2026-08-01 Ollama 전환 때 그대로 남은 값입니다. 이번 결과는 **로컬 LLM 을 유지한 채로도 그 목표가 사정권이라는 것**을 보여 줍니다. 따라서 목표를 낮춰 잡을 이유가 없어졌습니다.

다만 사고를 끈 대가가 있습니다. 복잡한 추론이 필요한 질의에서 품질이 떨어질 수 있으며, 이번 비교는 질의 한 건에 대한 정성 평가입니다. 품질 회귀가 관찰되면 `LLM_THINKING=true` 로 되돌리되, 그때는 첫 토큰이 10초로 돌아간다는 것을 함께 감수해야 합니다.

## 6. 회귀 방지

`tests/test_llm_first_token.py` 가 `think: false` 와 `keep_alive` 가 요청에 실리는지, 예열 실패가 기동을 막지 않는지 고정합니다. `tests/test_structured_data_cache.py` 는 캐시가 값을 바꾸지 않고 조건이 다른 질의가 서로의 값을 물려받지 않는지 고정합니다.

두 번째가 특히 중요합니다. 물품 집계가 용역 답변에 실리면 조용히 틀린 답이 됩니다.
