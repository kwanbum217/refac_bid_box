# 용역 예측구간 기준선 불일치 감사

> **작성일**: 2026-08-11
> **버전**: v1.0.0
> **상태**: 원인 확정
> **대상**: `servc_loss_function_20260807.md` 8.3과 2026-08-11 운영 경로 재측정

---

## 1. 결론

`1.6706%p / 89.56%`와 `1.6385%p / 89.47%`의 차이는 **모델 변경이나
2025년 원본 데이터 증분 때문이 아닙니다.** 두 측정이 서로 다른 표본 수를 썼고,
그 사이 호스트 측정 DB가 MariaDB 3307에서 MySQL 8 Docker 3306으로 바뀌어
`ORDER BY RAND(42)`가 사실상 다른 표본을 만들었습니다.

| 원인 후보 | 판정 | 근거 |
| --- | --- | --- |
| 표본 조건 | **주원인** | 9,000건 대 4,000건이며 DB 엔진 전환으로 같은 seed의 추출 집합도 달랐습니다 |
| 2025년 DB 증분 | **아님** | 두 DB의 2025년 적격 풀은 모두 104,065건이고 8월 7일 이후 추가 적격 행은 0건입니다 |
| 모델 변경 | **아님** | 두 측정 모두 `v_20260807_043210_535`이며 q10/q90 가중치가 그대로입니다 |

따라서 두 값은 같은 고정 표본의 재현 실패가 아니라 **서로 다른 운영 표본의
요약값**입니다. 0.09%p의 피복률 차이는 두 표본의 이항 표준오차를 합친 약
0.58%p보다 훨씬 작아 표본 변동 범위 안입니다.

## 2. 측정 조건 대조

두 스크립트는 `scripts/eval_servc_api_path.py`의 `collect()`를 공유합니다.
공통 조건은 `Servc`, 2025년 개찰, `sucsf_bid_rate > 0`, seed 42이며
`bid_ntce_no`로 공고와 결과를 조인합니다. 차이는 다음과 같습니다.

| 항목 | 2026-08-07 8.3 | 2026-08-11 재측정 |
| --- | --- | --- |
| 실행 스크립트 | `compare_servc_models_paired.py` | `eval_servc_interval_by_group.py` |
| DB | 호스트 MariaDB 3307 | MySQL 8 Docker 3306 |
| 요청 표본 | 9,000건 | 4,000건 |
| 채점 표본 | 8,995건 | 3,998건 |
| 제외 | 두 모델 중 하나라도 예측 불가인 5건 | 금액 미공개 등 예측 불가 2건 |
| 연도 / seed | 2025 / 42 | 2025 / 42 |
| 하한율 필터 | 없음 | 없음 |
| 구간 폭 집계 | 중앙값 | 중앙값 |
| 결과 | 1.6706%p / 89.56% | 1.6385%p / 89.47% |

8월 7일 측정 당시 호스트 `.env`는 MariaDB 3307을 가리켰습니다. 8월 9일
`docs/ops/db_dedup_host_container_20260809.md`의 조치로 호스트 기본 연결을
MySQL 8 Docker 3306으로 바꿨습니다. 따라서 seed 숫자가 같아도 DBMS가 달라
동일 표본이라는 보장이 없습니다.

실제로 보존된 두 DB에서 같은 조회를 다시 실행해 공고 ID와 결과 ID의 교집합을
비교했습니다.

| 요청 수 | MariaDB와 MySQL의 교집합 | 교집합 비율 | 순서 완전 일치 |
| ---: | ---: | ---: | --- |
| 4,000 | 168 | 4.20% | 아니요 |
| 9,000 | 760 | 8.44% | 아니요 |

`RAND(seed)`는 한 DB 실행 안에서는 재현에 도움이 되지만 DBMS 종류, 실행 계획,
물리 행 순서가 바뀐 뒤까지 표본 ID를 고정하지는 않습니다.

## 3. DB 증분 판정

8월 9일 이중화 제거 전 감사에서 MySQL 8은 MariaDB보다 공고 47건, 결과 22건이
많았습니다. 차이는 모두 2026년 최근 수집분이었고 모든 연도에서 MySQL 8이
MariaDB 이상이었습니다.

이번 감사에서 8월 7일 측정과 같은 2025년 적격 풀을 다시 확인했습니다.

| 항목 | MariaDB 3307 | MySQL 8 3306 |
| --- | ---: | ---: |
| 2025년 Servc 적격 조인 행 | 104,065 | 104,065 |
| 2026-08-07 15:14 이후 수집된 2025년 적격 행 | 0 | 0 |

따라서 **2025년 원본 행 증분은 불일치를 설명하지 못합니다.** 8월 9일에는
MySQL 8의 `institution_win_rate_stats`를 35,408행에서 38,765행으로
재생성했지만, 재생성 결과는 당시 MariaDB의 38,765행과 일치했습니다. 현재 두
집계의 키도 같고 값이 다른 키는 11개뿐이므로, 이번 두 수치의 주된 차이는 집계
증분이 아니라 서로 다른 무작위 표본입니다.

## 4. 모델 버전 판정

8월 7일 `quantile(0.5)` 점 모델 `v_20260807_043210_535`를 승격한 뒤 8월 11일
재측정 사이에 Servc 승격은 없었습니다. 현재 서빙 메타데이터도 같은 버전입니다.

예측구간은 점 모델이 아니라 `(q10 + q90) / 2`를 중심으로 만들고 등각 배율
`1.151263`을 적용합니다. 8월 7일 승격은 점 모델만 바꿨으며 q10/q90은 이전
서빙본과 동일합니다.

| 파일 | 현재 SHA256 | 직전 백업과 동일 |
| --- | --- | --- |
| `model_q10.bin` | `fcd237c42acfc718e4f620d5a372cf72a4393272149bb4a116647634b73b161f` | 예 |
| `model_q90.bin` | `b89e90b5abe6c1beaab077cf5f8ff8e24d4bda51d32e39e90a334c3218088c6e` | 예 |

그러므로 **모델 변경은 원인이 아닙니다.** 8.3의 base와 challenger 구간이 완전히
같았던 것도 두 모델이 같은 q10/q90과 배율을 썼기 때문입니다.

## 5. 재측정 교차 확인

현행 MySQL 8과 동일 모델에서 표본 수만 바꿔도 중앙값과 피복률이 움직였습니다.

| DB / 요청 표본 | 채점 | 구간 폭 중앙값 | 피복률 |
| --- | ---: | ---: | ---: |
| MariaDB 3307 / 4,000 | 3,999 | 1.7286%p | 89.40% |
| MariaDB 3307 / 9,000 | 8,995 | 1.6706%p | 89.56% |
| MySQL 8 3306 / 4,000 | 3,998 | 1.6385%p | 89.47% |
| MySQL 8 3306 / 9,000 | 8,998 | 1.6975%p | 89.98% |

첫째 행은 2026-08-06 기록을 현존 MariaDB에서 재현한 값이고, 둘째 행은 8.3의
기록입니다. 셋째와 넷째 행은 이번 감사에서 현행 운영 DB와 같은 모델로
재측정했습니다. 고정 ID 목록 없이 `RAND(seed)`와 표본 수만 기록한 요약값은
장기 기준선으로 사용할 수 없음을 보여 줍니다.

## 6. 기준선 권고

두 값 중 하나를 **현행 운영 기준선**으로 인용해야 한다면 최신 운영 연결과 문서화된
기본 명령을 따른 **`1.6385%p / 89.47%`**를 사용합니다. 반드시 다음 조건을
같이 적습니다.

```text
2026-08-11, MySQL 8 Docker 3306, Servc 2025년, seed 42,
4,000건 요청 / 3,998건 채점, v_20260807_043210_535
```

`1.6706%p / 89.56%`는 폐기할 오류값이 아닙니다. 이 값은 8월 7일
`quantile(0.5)` 승격 쌍대 검정에서 **base와 challenger의 구간이 바뀌지
않았음**을 입증하는 실험 기록으로만 인용합니다. 현행 서비스의 단독 절대
기준선으로는 쓰지 않습니다.

향후 날짜 간 비교에서는 seed만 기록하지 말고 채점 공고 ID 목록, DB 엔진과
스냅샷 시각, 제외 ID와 사유, q10/q90 체크섬을 함께 고정해야 합니다.
