## 1. 개요 및 목적

`scripts/run_data_reconciliation.py`의 4단계 정합성 검사(`verify_reconciliation`)에서 DB 낙찰결과 식별자 집합(`BidResult.bid_ntce_no`)을 ChromaDB `bidding_kb` 색인 식별자 집합과 차집합하여 비교하는 과정에서 불일치(`diff_chroma` > 0)가 발생해 파이프라인이 실패(fail-closed)하는 현상이 보고되었습니다(2026-09-04 백필 당시 103건).

본 조사는 코드를 수정하지 않고 현재 상태를 판정하는 읽기 전용 조사로서, 다음 목적을 수행합니다.
1. 현재 DB 기준 대응 공고 없는 낙찰 건수 재조회 시도 및 연결 실패 사유 명시
2. 코드로 확인 가능한 구조적 모집단 불일치와 DB 미접속으로 인한 실제 데이터 정규화 결함 여부의 구분
3. 1건의 누락도 숨김없이 검출할 수 있는 시정 방향 후보 제시 및 장단점 비교
4. 후속 시정 Task에서 즉시 활용 가능한 확정 사실과 미확정 사실의 엄밀한 분리 정리

## 3. 낙찰 데이터 성격 및 원인 규명: 구조적 모집단 차이 vs 데이터 정규화 결함

### 3.1 코드로 확인된 구조적 원인: 모집단 불일치 (Population Mismatch) [확정]

코드 및 아키텍처 분석으로 확인된 근본 원인은 다음 세 가지 비대칭성에 기인한 **정합성 검사 모집단 정의의 불일치(확정)**입니다.

1. **색인 대상 모델의 비대칭**:
   - ChromaDB `bidding_kb`는 원본 RAG 지식베이스로서 `BidAnnouncement`(공고) 문서를 기반으로 텍스트 및 메타데이터를 구성하여 색인합니다.
   - 반면 `scripts/run_data_reconciliation.py:199-204`의 `verify_reconciliation`은 `db_notice_nos`를 `get_db_result_notice_numbers`(즉, `BidResult` 낙찰 테이블)에서만 추출합니다.
   - 공고 테이블이 아닌 낙찰 테이블의 식별자 집합을 공고 기반 색인 저장소(ChromaDB)에 대해 차집합하므로, 공고가 없는 낙찰은 구조적으로 ChromaDB에 존재할 수 없습니다.

2. **증분 수집 구간의 시차 비대칭 (Temporal Asymmetry)**:
   - 공공조달 업무 특성상 공고일시(`bid_ntce_dt`)와 개찰/낙찰일시(`rl_openg_dt`) 간에는 수일~수주일(재공고나 심사 지연 시 수개월)의 시차가 존재합니다.
   - 특정 증분 구간(`collected_since` 이후)으로 백필이나 일일 수집을 수행할 경우, 해당 구간에 수집된 낙찰건의 원 공고는 이미 이전 구간에 공고/수집되어 현재 증분 공고 집합(`announcements_by_collected_delta`)에 포함되지 않습니다.

3. **공고-낙찰 API 데이터 범위 비대칭**:
   - 수의계약, 직권 공시 등 일부 조달청 데이터의 경우 일반 입찰공고 없이 낙찰 결과만 통보되는 경우가 존재합니다.

### 3.2 식별자 표기 및 정규화 결함 가능성 [미확정]

- **코드 및 스키마 검토**:
  - `BidResult.bid_ntce_no`와 `BidAnnouncement.bid_ntce_no`는 모두 `String(50)` 컬럼으로 정의되어 있습니다.
  - `src/app/models/bids.py:265-270`의 `matching_announcement` 메서드에서는 차수 자릿수 차이(`"00"` vs `"000"`)를 해결하기 위해 `lstrip("0")` 정규화를 수행하지만, `run_data_reconciliation.py`는 차수를 배제하고 순수 `bid_ntce_no`만 비교합니다.
  - ChromaDB 추출 정규식은 `r"\[(?:공고번호|낙찰공고번호)\]\s*([0-9A-Za-z]+)"`로 표준 공고번호 규격을 매칭합니다.
- **실제 데이터 레벨의 미확정성**:
  - 스키마 타입이 동일하다고 해서 실제 DB에 적재된 데이터 값 레벨의 앞뒤 공백(leading/trailing whitespace), 접두부 차이, 표기 불일치(대소문자/특수문자) 가능성을 완전히 배제할 수는 없습니다.
  - 현재 DB 연결 실패로 인해 실제 레코드 값을 직접 조회·비교하지 못했으므로, **실제 데이터 상의 식별자 정규화 결함 존재 여부는 미확정** 상태로 유지합니다.

## 4. 시정 방향 후보 비교 및 누락 검출 보장 방안

> [!CAUTION]
> 단순 예외 목록(하드코딩된 공고번호 세트)으로 차집합에서 제외하여 경고를 가리는 방식은 실제 색인 누락을 은폐하므로 절대 채택하지 않습니다.

### 후보 1: 대상 저장소별 도메인 정합 기대 집합 분리 (권장)

- **설계 내용**:
  - **ChromaDB 검사**: DB 공고(`BidAnnouncement`) 집합 vs ChromaDB 색인 식별자 집합 대조
  - **Meilisearch 공고 검사**: DB 공고(`BidAnnouncement`) 집합 vs Meilisearch `dataset="announcement"` 식별자 집합 대조
  - **Meilisearch 낙찰 검사**: DB 낙찰(`BidResult`) 집합 vs Meilisearch `dataset="result"` 식별자 집합 대조
- **장점**:
  - 각 저장소의 색인 목적과 데이터 모델이 1:1로 정확히 일치하여 논리적 무결성 확보
  - 공고 색인 누락과 낙찰 색인 누락을 분리하여 정확한 실패 원인 파악 가능
- **단점**:
  - `run_data_reconciliation.py`에 공고 식별자 조회 함수(`get_db_announcement_notice_numbers`) 추가 및 검사 인터페이스 확장 필요
- **실제 누락 1건 검출 보장 메커니즘**:
  - DB에 수집된 공고 중 1건이라도 ChromaDB에 색인되지 않으면 `db_announcement_nos - chroma_notice_nos`에 남아 검증이 즉시 중단(fail-closed)됩니다.
  - Meilisearch 역시 공고 및 낙찰 각각에 대해 1건이라도 누락 시 차집합이 비어 있지 않아 종료 코드 1로 실패합니다.

### 후보 2: 대응 공고가 존재하는 낙찰로 검사 범위 한정 + 고아 낙찰 분리 계측

- **설계 내용**:
  - ChromaDB 검사 기대 집합을 `BidResult` 중 `BidAnnouncement`에 실제로 존재하는 건(`BidResult INNER JOIN BidAnnouncement`)의 식별자로 한정
  - 대응 공고가 없는 낙찰(Orphan Results)은 `orphan_results_count` 지표로 분리하여 로그 및 요약에 기록
- **장점**:
  - 기존 `BidResult` 중심의 검증 흐름을 크게 바꾸지 않고 최소 수정으로 정상화 가능
  - 고아 낙찰 추이를 모니터링 가능
- **단점**:
  - ChromaDB는 공고 전체를 담는 저장소인데 검사는 낙찰과 겹치는 공고만 보게 되어, 낙찰되지 않은 일반 공고의 색인 누락을 잡아내지 못함
- **실제 누락 1건 검출 보장 메커니즘**:
  - 대응 공고가 존재하는 낙찰 중 1건이라도 ChromaDB에 없으면 차집합에 걸려 실패합니다.
  - 단, 낙찰 없는 공고의 누락은 감지하지 못하는 한계가 있습니다.

### 후보 3: ChromaDB 색인 대상에 낙찰 결과 문서 포함 (기각)

- **설계 내용**: ChromaDB `bidding_kb`에 공고뿐 아니라 낙찰 결과 요약 문서도 신규 색인
- **기각 사유**:
  - G1 데이터 무손실 원칙 및 기존 `bidding_kb` 컬렉션 스냅샷 보존 정책에 위배될 위험
  - 임베딩 비용 및 벡터 검색 쿼리 지연 시간(P95) 증가 위험
  - RAG 검색 프롬프트 및 컨텍스트 정합성에 대한 전면 재평가 필요

## 5. 후속 시정 Task를 위한 사실 분류표

### 5.1 확정 사실 (Confirmed Facts)

1. `scripts/run_data_reconciliation.py:199-214`의 `verify_reconciliation`은 `db_notice_nos`를 `BidResult`(낙찰결과)에서만 조회하며, 이를 공고 기반 ChromaDB 색인 집합과 직접 차집합합니다.
2. ChromaDB `bidding_kb` 컬렉션은 `BidAnnouncement`(공고)를 원천으로 문서를 생성하여 색인합니다.
3. 공고 기반 색인 지식베이스에 대해 낙찰 식별자 집합을 검증 기대치로 사용하는 **모집단 불일치(Population Mismatch)**가 구조적으로 존재합니다.
4. 2026-09-04 8일치 백필 당시 기록(`docs/ops/handoff_20260904_docker_check_and_amount_integrity.md`)에 따르면 수집된 낙찰 4,806건 중 대응 공고가 없는 건이 103건이었고 불일치 건수도 103건이었습니다(과거 실측 이력).
5. 읽기 전용 및 공유 자원 점유 회피 원칙에 따라 Docker 컨테이너나 MySQL 서비스를 임의 기동하지 않았으며, 127.0.0.1:3306 포트 연결 거부(Connection refused) 상태만 확인했습니다.

### 5.2 미확정 사실 (Unconfirmed Facts / Hypotheses)

1. **현재 DB 기준 대응 공고 없는 낙찰 건수**: 127.0.0.1:3306 연결 거부로 인해 DB 재조회가 불가능하여 현재 정확한 수치는 **미확정**입니다.
2. **실제 데이터 레벨의 식별자 정규화 결함 여부**: 스키마 컬럼 타입(`String(50)`)은 동일하나, 실제 저장된 데이터의 공백(whitespace), 접두부, 표기 차이 여부는 DB 미접속으로 확인하지 못했으므로 **미확정**입니다.
3. **MySQL 서비스/컨테이너 가동 상태**: 127.0.0.1:3306 연결 거부 사실만 확인되었으며, 컨테이너 정지 여부, 포트 포워딩 또는 네트워크 설정 문제는 직접 확인하지 않았으므로 컨테이너 비가동으로 단정할 수 없습니다.
4. 대응 공고 없는 낙찰이 조달청 API 자체에서 공고 없이 발표된 데이터(수의계약/직권공시)인지, 증분 수집 기간 시차 때문인지는 DB 접속 후 세부 조회가 필요합니다.

## 6. 후속 시정 Task 사양 권고

후속 시정 작업(Fix Task)에서는 다음 변경을 권고합니다.
1. `scripts/run_data_reconciliation.py`:
   - `get_db_announcement_notice_numbers` 함수 신설 (`BidAnnouncement.bid_ntce_no` 조회)
   - `verify_reconciliation` 함수를 개편하여:
     - `diff_chroma = db_announcement_nos - chroma_notice_nos`
     - `diff_meili_ann = db_announcement_nos - meili_announcement_nos`
     - `diff_meili_res = db_result_nos - meili_result_nos`
