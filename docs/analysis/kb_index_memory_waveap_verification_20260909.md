> **작성일**: 2026-09-09
> **작성자**: 코디네이터 (직접 실측)
> **대상 커밋**: `4e40bd1` (AP1·AP2·AP3·AP5 전량 병합본)
> **판정**: **통과**. AP4 판정 기준 3항 충족. 16GiB 와 14GiB 두 조건 모두 확인
> **선행 문서**: [`kb_index_memory_verification_20260909.md`](kb_index_memory_verification_20260909.md)

## 1. 결론

단일 `update_kb_task` 1회가 **959초에 정상 완료**했고 worker 컨테이너 피크는
**4,323MB** 입니다. 2026-09-09 오전의 10,762MB 소멸 곡선이 재현되지 않았습니다.

색인은 처음으로 끝까지 도달했습니다. `knowledge_base_status` 가 `failed` 에서
`ready` 로 바뀌었고 증분 판정이 실데이터에서 동작함이 확인됐습니다.

## 4. 색인 결과

```
최근 1년 데이터 기준 500000건 인덱싱 완료
(증분: 갱신 1751건 / 유지 498249건 / 삭제 40322건)
(source=announcements_by_notice_date)
```

증분 판정과 `unseen_ids.discard` 삭제 대상 계산이 **실데이터에서 처음으로
검증됐습니다.** 지금까지 색인이 끝난 적이 없어 이 경로는 단위 테스트로만
확인된 상태였습니다. 폴백도 공고일 기준(`announcements_by_notice_date`)으로
정상 동작했습니다.

### 4.1 문서 수 감소에 대한 판단

`source_bid_count` 가 종전 기록 535,702 에서 500,000 으로 줄고 40,322건이
삭제됐습니다. **이는 상한 정책의 결과이며 데이터 손실이 아닙니다.**

- `KB_MAX_DOCUMENTS` 기본값이 500,000 이고 환경변수 미설정입니다.
- 최근 1년 공고가 상한을 넘었고, 공고일 내림차순 정렬이라 오래된 40,322건이 제외됐습니다.
- 삭제 비율 7.5% 로 `MAX_REMOVAL_RATIO` 0.5 이내입니다.
- 컬렉션 표본 10만 건의 id 접두는 전량 `bid_` 이며 종류가 뒤섞이지 않았습니다.
- 종전 기록 535,702 는 `status=failed` 인 색인이 남긴 값이라 기준선으로 삼기에 부적절합니다.

원본 DB 와 모델 가중치는 건드리지 않으므로 G1 대상이 아닙니다. KB 는 파생물입니다.
커버리지를 늘리려면 `KB_MAX_DOCUMENTS` 를 올리는 별도 판단이 필요합니다.

## 5. 측정 조건

| 항목 | 값 |
| --- | --- |
| Docker Desktop 메모리 | 16,384MiB (오전 측정과 동일) |
| 투입 방식 | 단일 `update_kb_task`, job_id `kb-waveap-verify-20260909` |
| 사전 정리 | arq 큐 비움. 재시도 잔재 없음 |
| 동시 작업 | `run_schedule_catchup_task` 가 재시작 직후 발화. AP5 잠금으로 직렬 실행됨 |

**두 작업은 겹치지 않았습니다. AP5 의 잠금이 직렬화했습니다.** 처음에는 겹친 것으로
읽었으나 시각을 대조하니 그렇지 않습니다.

| 작업 | 큐 투입 | 완료 | arq 기록 소요 |
| --- | --- | --- | ---: |
| `run_schedule_catchup_task` | 13:24:44 | 13:40:51 | 966.90초 |
| `update_kb_task` | 13:25:50 | 13:41:50 | 959.63초 |

`update_kb_task` 의 959초는 **잠금 대기를 포함한 값**입니다. arq 는 큐에서 뽑은
시점부터 재므로, 13:25:50 에 뽑혀 catchup 이 끝나는 13:40:51 까지 약 900초를
대기하다 실제 실행은 59초였다는 뜻입니다. 두 번째 측정의 단독 색인이 82초인 것과
같은 범위입니다.

따라서 **13:28~13:40 구간의 상승과 2.6GB 고원, 그리고 4,323MB 피크는 catchup
(`run_mode=refresh_data`, 수집과 색인을 함께 수행)의 것입니다.** 두 작업의 합산이
아닙니다. `update_kb_task` 단독 피크는 이 측정에서 분리되지 않으며, 6장의 1,027MB 가
그 값에 가깝습니다.

이것은 AP5 단일 실행 잠금이 **운영에서 처음으로 실증된 기록**이기도 합니다. 무거운
태스크 둘이 같은 창에 들어왔고 직렬로 실행됐습니다.

원본 worker 로그는 이후 `docker compose down` 으로 컨테이너가 재생성되며 사라졌으므로,
위 판단은 남아 있는 완료 시각과 소요 기록, 메모리 곡선에 근거한 재구성입니다.

## 6. Docker 메모리 원복 후 재측정 (14,336MiB)

측정 조건을 운영 기본값으로 되돌려 한 번 더 실측했습니다. `MemoryMiB` 를 14,336 으로
낮추고 Docker Desktop 을 재기동한 뒤(`docker info` MemTotal 14,635,569,152 = 13,957MiB)
같은 방식으로 단일 색인을 투입했습니다. 원본은
[`kb_index_worker_mem_waveap_14g_20260909.tsv`](../../data/benchmarks/kb_index_worker_mem_waveap_14g_20260909.tsv)
입니다.

| 항목 | 값 |
| --- | --- |
| 소요 | **82.34초** 정상 완료 |
| 피크 | **1,027.2MB** (14:26:04) |
| 컨테이너 소멸 | 없음. 표본 285건 전량 `UP` |
| KB 갱신 | `ready`, 500,000건, `2026-09-09 05:26:58` |
| 색인 내역 | 증분: 갱신 0건 / 유지 500,000건 / 삭제 0건 |
| 겹친 작업 | 없음. 기동 시 catchup 미발화로 순수 단일 조건 |

곡선은 투입 후 20초에 걸쳐 1,024MB 까지 오른 뒤 그 값에서 평탄하게 유지되다가
14:26:27 에 399MB 로 떨어지고 380MB 로 안정됩니다. 상승 구간이 계단이 아니라
유계 고원입니다.

**이 측정의 한계를 밝힙니다.** 갱신 0건이므로 임베딩을 한 건도 수행하지 않았습니다.
따라서 이 수치는 임베딩 부하를 뺀 **조회 계층만의 상주량**입니다. 다만 그것이 곧
AP2 가 고치려던 축입니다. announcements 500,000건을 Pass 1(removed_ids 소거)과
Pass 2(임베딩 판정)로 두 번 순회하면서 상주가 1GB 를 넘지 않았습니다. 임베딩까지
포함한 부하는 5장의 4,323MB 가 보여줍니다. 두 측정은 상보적입니다.

**여유로 통과한 것이 아닙니다.** 오전 실패는 Docker 메모리를 14GiB 에서 16GiB 로
올린 뒤에도 재현됐고, 이제 14GiB 로 되돌린 조건에서 통과했습니다. 통과의 원인은
메모리 여유가 아니라 코드 수정입니다.
