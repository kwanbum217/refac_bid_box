## 3. 무효 판정의 근거

### 3.1 지식베이스에 정답이 없습니다

답변 가능 24문항의 기대 근거 문서를 ChromaDB `bidding_kb` 에서 직접 열어
확인한 결과입니다.

| 확인 항목 | 결과 |
| --- | ---: |
| 기대 근거 문서가 컬렉션에 존재 | 24/24 |
| 그 문서의 `has_result` 메타데이터가 참 | **2/24** |
| 그 문서 본문에 낙찰금액 문자열 포함 | **2/24** |

22개 문서의 본문은 `[낙찰상태] 진행 중 또는 결과 미수집` 로 끝납니다. fixture 가
묻는 낙찰업체·낙찰금액·낙찰률이 **문서에 존재하지 않습니다.** MySQL 에는
있지만 색인된 판본이 낙찰 결과 도착 이전 시점입니다.

### 3.2 결손 규모가 실측값을 정확히 설명합니다

우연이 아닙니다. 세 수치가 같은 분모에서 나옵니다.

| 관측 | 값 | 산출 |
| --- | ---: | --- |
| KB 에 낙찰 정보가 있는 문항 | 2/24 | 위 3.1 |
| evidence recall | 0.083 | 2 / 24 |
| 문항 단위 통과 (두 모델 동일) | 2/24 | 근거가 있는 문항만 통과 |
| numeric 정답률 | 8.3% | 4 / 48 = 2문항 × 2팩트 |

**두 모델의 문항 통과 수가 2/24 로 완전히 같습니다.** 모델을 바꿔도 결과가
움직이지 않는다는 것은 병목이 모델 밖에 있다는 뜻입니다.

### 3.3 모델은 정직하게 실패했습니다

근거가 없을 때 지어내지 않았습니다. 이 축들은 오히려 기준을 통과합니다.

- forbidden 리터럴 위반 **0건** (두 모델, 전 회차)
- 거절 정확도 **8/8** (두 모델, 전 회차)
- 과잉응답 **0건** (거절 기대 문항에서 답변 생성 없음)

과잉거절 17건과 14건은 **결함이 아니라 올바른 동작입니다.** 근거가 없는
질문에 "찾을 수 없다" 고 답한 것이며, 이 fixture 에서는 실제로 근거가
없었습니다.

### 3.4 원인은 두 겹입니다

| 원인 | 내용 | 책임 위치 |
| --- | --- | --- |
| fixture 생성기 결함 | 근거 문서의 **존재**만 확인하고 그 문서가 **묻는 사실을 담고 있는지**(`has_result=True`)는 확인하지 않았다 | `scripts/build_generalization_fixture.py` |
| 지식베이스 낡음 | 2026-08-27 백필로 MySQL 에 낙찰 결과가 들어왔으나 ChromaDB 가 재색인되지 않았다 | 수집 파이프라인 후속 단계 |

두 번째가 근본입니다. DB 대조로 확인한 결과, 24문항의 낙찰 결과
`collected_at` 은 **2026-08-27 이 22건, 2026-08-13 이 2건**입니다. 오늘 들어온
22건이 정확히 KB 에 없는 22건입니다.

## 4. 이 측정으로 하지 말아야 할 것

| 하지 말 것 | 이유 |
| --- | --- |
| e2b 승격 철회 | 8.3% 대 10.4% 는 48팩트 중 4개 대 5개다. 근거가 없는 조건에서의 차이이며 변별력이 없다 |
| e4b 가 더 낫다는 결론 | 같은 이유. 두 모델의 문항 통과 수가 2/24 로 동일하다 |
| 이 수치를 CURRENT_STATE 성능 지표로 인용 | 무효 측정이다 |
| P50 4,700ms/5,317ms 를 레이턴시 회귀 근거로 사용 | 거절 응답이 다수라 응답 길이 분포가 정상 운영과 다르다 |

원시 결과 파일은 **삭제하지 않고 결함의 증거로 보존**합니다. 설계서 9.2 절의
즉시 삭제 대상(동결 위반, 모델 불일치)에는 해당하지 않으며, 무효 사유가 본
문서에 기록되어 있습니다. 다만 **모델 판정 근거로는 어떤 경우에도 인용하지
않습니다.**

## 5. 재측정 조건

아래를 모두 충족한 뒤 동일 절차로 다시 측정합니다. 판정 기준(설계서 5장)은
**바꾸지 않습니다.** 측정 후 기준을 손대는 것은 금지입니다.

| 조건 | 조치 |
| --- | --- |
| KB 가 최신 낙찰 결과를 담을 것 | `rebuild_knowledge_base(db, collected_since=...)` 델타 색인. 델타는 결과가 새로 들어온 공고를 함께 집어 오므로 대상 22건이 갱신된다 |
| fixture 가 답 가능한 문항만 담을 것 | 생성기에 `has_result=True` 및 본문 낙찰금액 포함 검사를 추가하고 재생성한다 |
| 재생성 후 근거 유효성 재확인 | 기대 근거 문서 전건에 대해 `has_result` 와 본문 포함을 확인한다 |
| 호스트 부하 | 코어당 중앙 30% 이하, 최대 50% 이하 |
| 저장소 동결 | 측정 중 병합·재시작·재색인 금지 |

재측정 전에 fixture 를 고치지 않으면 KB 를 갱신해도 같은 함정에 다시 빠질 수
있습니다. **두 조치는 함께 가야 합니다.**

## 6. 이번 측정이 실제로 알려준 것

모델 판정은 못 했지만 **운영 결함 하나를 실증했습니다.** 이것이 이 측정의
산출물입니다.

> **수집된 낙찰 결과가 지식베이스에 반영되지 않으면, 챗봇은 최근 공고의 낙찰
> 정보를 답할 수 없습니다.** 오늘 백필한 9,798건의 낙찰 결과가 여기 해당하며,
> 재색인 전까지 사용자가 그 공고를 물으면 "찾을 수 없다" 는 답을 받습니다.

수집 파이프라인의 야간 경로는 색인을 포함하지만
`scripts/backfill_from_g2b.py` 는 포함하지 않습니다. 수동 백필 후 색인을
빠뜨리면 조용히 이 상태가 됩니다. **백필 스크립트에 색인 단계를 추가하거나,
최소한 색인이 필요하다는 경고를 출력해야 합니다.**
