## 1. 작업 개요

외부 보안 감사에서 지적된 P1 결함(자동화 실행 확인 토큰 단일 소비 부재 및 동시성 중복 큐잉 가능성)을 해결하기 위해, 인메모리 집합 기반 소비 기록을 전면 제거하고 Redis `SET NX EX` 원자적 명령과 DB 조건부 `UPDATE`를 결합한 2단계 멱등성 보장 구조를 구축하였습니다.

## 2. 결함 분석 및 해결 내용

### 2.1 기존 구현의 한계
1. `src/app/services/automation_tokens.py`의 `_consumed_confirmation_tokens`가 모듈 수준 Python `set`으로 관리되어, 다중 워커 프로세스(`WEB_CONCURRENCY > 1`) 환경에서 프로세스 간 소비 상태가 공유되지 않았습니다.
2. `src/app/api/v1/automation.py`에서 `is_confirmation_token_consumed` 검사와 `mark_confirmation_token_consumed` 기록이 두 번의 호출로 분리되어 있어, 동시 요청 간 경쟁 상태(Race Condition)가 발생할 수 있었습니다.
3. `src/app/services/automation_orchestrator.py`의 `confirm_automation_request`에서 `confirmed_at`을 메모리 객체 속성 조회 후 단순 대입하는 Read-Modify-Write 방식으로 처리하여 DB 레벨 동시성 안전성이 결여되어 있었습니다.

### 2.2 개선 사항
1. **Redis `SET NX EX` 원자적 소비 함수 (`consume_confirmation_token`) 도입**:
   - `_consumed_confirmation_tokens` 및 분리된 검사/기록 함수를 완전 삭제하고 단일 원자적 함수로 대체하였습니다.
   - 키 포맷: `bidbox:automation:consumed_token:{sha256(token)}`
   - 만료 TTL: 1800초 (30분, 토큰 서명 유효시간과 일치)
   - Fail-Closed 정책: Redis 연결 불가 또는 통신 오류 시 즉시 `AutomationError`를 발생시켜 요청을 거부(HTTP 403)합니다.
2. **API 계층 단일 원자적 검증**:
   - `POST /api/v1/automation/job/{job_id}/confirm`에서 토큰 서명 검증 직후 `consume_confirmation_token`을 1회 호출하여 소비를 원자적으로 확정합니다.
3. **DB 레벨 조건부 `UPDATE` 멱등성 보장**:
   - `UPDATE automation_requests SET confirmed_at = :now, status = 'queued', result_summary = '...' WHERE id = :id AND confirmed_at IS NULL`
   - 영향 행 수(`rowcount`)가 1일 때만 `start_automation_request`를 통해 Arq 태스크 큐에 작업을 등록하고, 0일 경우 큐잉을 생략합니다.
