## 1. 결론

**탐침은 확실히 사라졌습니다. 총 시간이 줄었다고는 말할 수 없습니다.**

| 항목 | 적용 전 | 적용 후 | 판정 |
| --- | ---: | ---: | --- |
| `corrupted_probe_ms` 합계 (콜드 4건) | 144,541ms | **0ms** | **확정** |
| `cursor_count` (콜드) | 11~12 | **9** | **확정** |
| `sql_ms` 콜드 4건 합계 | 392,745ms | 327,322ms | **미확정** |

앞의 두 줄은 구조적 사실이라 타이밍 잡음과 무관합니다. 탐침 질의 2~3건이
그대로 사라졌고 그것이 `cursor_count` 감소로 확인됩니다.

**세 번째 줄을 개선 효과로 인용하지 마십시오.** 이유는 3장입니다.

## 2. 선행 조건: 마커가 있어야 효과가 납니다

측정 전에 `rebuild_ranking_snapshots(force_weekly=True)` 를 실행했습니다.
165행, 367초. 그 결과 마커 15건이 생겼습니다.

| 차원 | 적용 전 마커 | 적용 후 마커 |
| --- | --- | --- |
| `announcement/bid_ntce_nm` (5 카테고리) | **없음** | `metric_count=0` |
| `announcement/dminstt_nm` (5 카테고리) | **없음** | `metric_count=0` |
| `result/bidwinnr_nm` (5 카테고리) | 2건만 있음 | 5건 전부 (`1,1,0,0,0`) |

**재구축을 돌리지 않으면 효과는 0 입니다.** 마커가 없으면 코드가 종전대로
탐침을 실행합니다(설계상 조합 5). 운영에서는 야간 스케줄이 이 역할을 합니다.

## 3. 총 시간을 개선으로 읽으면 안 되는 이유

### 3.1 남은 쿼리의 분산이 효과보다 큽니다

같은 쿼리가 회차마다 10배씩 흔들립니다.

| 구간 | 적용 전 (최악 트레이스) | 적용 후 (3개 트레이스) |
| --- | ---: | --- |
| `top_rows_2` | 43,853ms | 19,536 / 3,341 / 22,055ms |
| `cached_aggregate_2` | 22,070ms | 40,984 / 1,665 / 26,109ms |

`cached_aggregate_2` 는 오히려 적용 후에 41초를 찍은 회차가 있습니다. 탐침
144.5초가 사라졌는데 총합은 65.4초만 줄었습니다. 나머지가 그만큼 느려졌다는
뜻이며, 이 잡음 폭 안에서는 어떤 효과 크기도 주장할 수 없습니다.

### 3.2 두 측정의 조건이 다릅니다

정직하게 적습니다. 이 비교는 교란돼 있습니다.

- 두 측정 사이에 스냅샷 재구축(367초, 165행 쓰기)이 있었습니다. 버퍼풀 상태가
  같지 않습니다.
- 적용 후 측정 직전에만 Redis 를 비웠습니다. 적용 전에는 비우지 않았습니다.
- 각 조건은 1회 실행입니다. 반복이 없습니다.

**따라서 방어 가능한 주장은 구조적 사실 둘뿐입니다.**

---

## 4. 남은 것

콜드 `sql_ms` 는 여전히 최대 103초입니다. 탐침이 사라진 뒤의 구성은 이렇습니다.

| 구간 | 적용 후 비중 (최악 트레이스) |
| --- | ---: |
| `cached_aggregate_2` | 39.7% |
| `cached_aggregate_1` | 22.6% |
| `top_rows_2` | 18.9% |
| `top_rows_3` | 15.7% |

**다음 대상은 `_cached_aggregate` 두 호출입니다.** 이번 계측은 호출 단위까지만
보므로 그 안의 SQL 형태와 실행계획은 아직 보지 않았습니다.

그리고 **효과 크기를 재려면 측정 설계를 먼저 고쳐야 합니다.** 1회 실행 두 개를
빼는 방식으로는 이 분산을 이길 수 없습니다. 같은 조건에서 반복 회차를 늘리고
버퍼풀과 Redis 상태를 양쪽에 동일하게 맞춘 뒤에야 비교가 성립합니다.

## 5. 리뷰어의 비차단 지적 반영

grok-4.6 리뷰어가 차단 결함 없이 pass 판정하면서 비차단 항목을 하나 남겼습니다.
**마커 부재 경로의 탐침 캐시 테스트가 약해졌다**는 지적입니다.

`tests/test_rag_structured_data.py` 의 `test_probe_outcome_is_cached` 가
`marker=0` 을 쓰고 있었습니다. 이 값은 이제 "확인했고 깨끗함" 을 뜻해 탐침을
건너뛰므로, 그 테스트는 docstring 이 말하는 "탐침 결과까지 함께 캐시된다" 를
더 이상 검증하지 못했습니다. 통과는 하지만 공회전이었습니다.

`marker=None` 으로 바꿔 탐침이 실제로 도는 상태를 복원하고,
`assert db.probe_executions == 1` 을 추가해 **판정 조건이 또 바뀌어도 테스트가
조용히 무의미해지지 않게** 못박았습니다.
