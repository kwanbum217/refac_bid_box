## 1. 무엇을 했나

`src/rag/` 와 `src/app/` 전체에서 SQLAlchemy `.contains()` 호출 13건을 전수 조사해 7개 그룹으로 분류하고, 각 그룹의 의도·컴파일 형태·실측 비용·대체 후보·의미 변화 위험을 표와 근거로 정리했다. 접두 일치 전환이 실패시키는 실제 사례를 DB 쿼리로 건수화했고, Meilisearch 위임 응답 시간과 매칭 분포도 측정했다.

## 2. 무엇을 발견했나

- `.contains()` 호출은 4개 파일 (`structured_data.py`, `ranking_snapshots.py`, `bid_queries.py`, `dashboard.py`) 13회. 9개가 `LIKE '%...%'` 로 컴파일되며 어떤 인덱스도 range 스캔하지 못한다.
- 손상값 probe (LIMIT 1) 3건은 정상 상태에서 매 질의당 약 27초를 합산한다 (`bid_announcements.bid_ntce_nm` 단독으로 20~23초 실측). ground_truth 의 "최대 27,668ms" 와 일치.
- "거제시" 같은 부분 토큰 입력은 `bid_announcements.dminstt_nm` 10,148건 중 접두 일치로는 36건만 잡힌다. **99.6% 회귀**. 정식 호칭 "경상남도" 은 0.7% 만 잃는다.
- 가장 비용 대비 위험이 낮은 개입은 G2 (손상 probe 3건 제거). 이미 `bid_ranking_snapshots.rank=0` 슬롯과 `get_skipped_count` 가 손상값 마커를 관리하므로 중복 비용이다.
- G5·G6 (자유 검색 q 매칭) 은 Meilisearch 위임이 가능. `_meili_enabled()` 분기가 이미 존재하므로 `MEILI_ENABLED=true` 만 켜면 풀스캔을 우회한다.
- G1 (RAG 기관명), G3 (스냅샷 손상 제외), G7 (대시보드 제외) 는 의도 자체가 G1(데이터 무손실)과 충돌하므로 SQL 변경 없이 풀스캔을 없앨 수 없다.
