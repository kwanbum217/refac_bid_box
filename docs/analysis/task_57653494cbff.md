## 1. 개요 및 배경

`gemma4:e2b` 모델의 승격 근거가 24문항 fixture v1(`data/eval/llm_quality_fixture_v1.json`) 안에서만 성립하여, fixture 밖의 미노출 분포에 대한 일반화 성능 측정이 요구되었습니다. `docs/ops/llm_generalization_measurement_design.md`에 확정된 설계 사양(2장, 3장)에 따라 실제 DB와 ChromaDB를 연계한 32문항 blind fixture v2 생성기(`scripts/build_generalization_fixture.py`)를 개발하고, 32문항 초안(`data/eval/llm_quality_fixture_v2_draft.json`)을 생성하여 무결성을 검증하였습니다.

## 2. 주요 구현 내용

### 2.1 fixture 생성기 (`scripts/build_generalization_fixture.py`)
- **CLI 옵션 지원**: `--output`, `--exclude-notice-ids`, `--v1-fixture`, `--limit` (기본 24), `--refusal-limit` (기본 8), `--min-context-sufficient` (기본 15).
- **v1 중복 자동 배제**: v1 fixture 파일에서 사용된 `expected_evidence_ids`(17건)와 `공고번호`를 자동으로 파싱하여 신규 문항 선정 대상에서 완전 제외.
- **ChromaDB 실재 검증 결박**: 로컬 ChromaDB `bidding_kb` 컬렉션의 실재 embedding ID(`bid_{ann.id}`)를 조회하여 지식베이스에 실제 존재하는 공고만 답변 가능 후보로 선별.
- **안전한 DB 질의**: SELECT 쿼리만 사용 (데이터 무손실 G1 및 DB 불변성 원칙 준수).
- **공고 차수 정규화**: `bid_announcements`와 `bid_results` 조인 시 `bid_ntce_no` + `category` + `zfill(3)[-3:]` 차수 정규화 적용 (`src/ml/dataset.py` 규약 준수).
- **다양성 스트라타(층화) 보장 선별 알고리즘**:
  - 탐욕적 점수 기반 선별(Greedy quota scoring)을 통해 5대 차원(업무구분, 기관유형, 금액구간, 지역, 낙찰률구간)의 최소 할당을 100% 충족.
  - 스트라타 미충족 시 예외를 발생시키며 종료 코드 1로 실패하도록 fail-closed 설계.

### 2.2 거절 문항 생성기 (`generate_refusal_items`)
- 설계서 2.4절에 명시된 6대 거절 유형 8문항 생성:
  1. 미래 시점 공고/낙찰 (2건)
  2. 해외 조달 (1건)
  3. 미개찰 공고 (2건)
  4. 비공개 내부 정보 (1건)
  5. 결과 없는 공고 (1건)
  6. 기관 미등록 공고 (1건)
- `expected_facts[0].fact_type`을 `refusal`로 두고, `context_sufficient=False`, `refusal_expected=True`, `expected_evidence_ids=[]`로 일관되게 구성.
- `semantic_forbidden_claims`에 '자기모순' 및 환각 제재 규칙 명시.

### 2.3 설계서 기술 불일치 확인 및 바로잡음 (Evidence ID 사양)
- **설계서 기술 내용**: `docs/ops/llm_generalization_measurement_design.md` 3.2절에서는 `expected_evidence_ids`를 `bid_{bid_ntce_no}` 형태라고 기술함.
- **실제 코드 및 데이터**:
  - ChromaDB 문서 ID는 `src/app/services/kb_builder.py:310`에서 `f"bid_{ann.id}"` (`ann.id`는 `bid_announcements` 테이블의 PK)로 생성됨.
  - v1 fixture(`data/eval/llm_quality_fixture_v1.json`)의 `expected_evidence_ids` 역시 `bid_10015927` 등 PK 형태임.
- **조치**: 생성기는 실제 정본인 PK 기반 `bid_{ann.id}`로 `expected_evidence_ids`를 생성하도록 구현하였으며, 설계서 3.2절의 기술이 사실과 다름을 본 보고서에 기록함.
