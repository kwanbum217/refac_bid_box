# KB 색인 상한을 520,000 으로 올리고 실측으로 확인했다

> **작성일**: 2026-09-09
> **작성자**: 코디네이터 (직접 실측)
> **대상 커밋**: `173d95a`
> **판정**: **통과**. 최근 1년 전량이 삭제 없이 색인됨
> **선행 문서**: [`kb_index_memory_waveap_verification_20260909.md`](kb_index_memory_waveap_verification_20260909.md)

---

## 1. 왜 올렸는가

최근 1년 공고가 **505,271건**인데 상한이 500,000 이라 창의 가장 오래된
**5,271건(1.04%)** 이 색인에서 빠지고 있었습니다. 잘리는 구간은 2025-09-09 ~ 09-12 로
1년 창의 앞쪽 3.3일치입니다.

"최근 1년" 이라는 창의 의미와 실제 색인 범위가 어긋난 상태였고, 상한을 그대로 두면
데이터가 늘수록 격차가 커집니다. Wave AP 로 메모리 폭주가 해소돼 여유가 생겼으므로
(14GiB 조건 조회 계층 1,027MB) 데이터 증가분을 흡수할 마진을 두어 **520,000** 으로
정했습니다. 현재 여유는 14,729건입니다.

---

## 2. 함께 고친 구조 결함

상한이 `kb_builder.py` 와 `kb_document_builder.py` 에 **각각 독립 정의**돼 있었습니다.
실제 판정은 `kb_document_builder._max_documents()` 가 하므로, `kb_builder` 쪽만
고치면 조용히 무시됩니다. 값이 어긋나도 아무도 알아채지 못하는 구조였습니다.

`kb_document_builder` 를 단일 정의로 삼고 `kb_builder` 는 import 해 재수출하도록
바꿨습니다. 회귀 테스트 `test_max_documents_single_definition` 이 `kb_builder.py`
소스에 `DEFAULT_MAX_DOCUMENTS = ` 문자열이 다시 생기면 실패시킵니다.

## 3. 실측 결과

원본은 [`kb_index_worker_mem_520k_20260909.tsv`](../../data/benchmarks/kb_index_worker_mem_520k_20260909.tsv) 입니다.

| 항목 | 값 |
| --- | --- |
| Docker Desktop 메모리 | 14,336MiB (운영 기본값) |
| 소요 | **243.66초** 정상 완료 |
| 피크 | **4,051.8MB** (15:12:01) |
| 컨테이너 소멸 | 없음. 표본 391건 전량 `UP` |
| 겹친 작업 | 없음. 큐를 비우고 단독 투입 |

색인 결과입니다.

```
최근 1년 데이터 기준 505271건 인덱싱 완료
(증분: 갱신 5271건 / 유지 500000건 / 삭제 0건)
(source=announcements_by_notice_date)
```

`knowledge_base_status.source_bid_count` 와 ChromaDB `bidding_kb` 실제 문서 수가
모두 **505,271** 로 일치합니다. **삭제 0건**이므로 기존 색인을 건드리지 않고 빠져
있던 5,271건만 더해졌습니다. 예측한 수치와 정확히 같습니다.

## 4. 이전 측정과의 비교

| 회차 | 상한 | 소요 | 피크 | 임베딩 |
| --- | ---: | ---: | ---: | --- |
| 14GiB 1차 | 500,000 | 82초 | 1,027MB | 갱신 0건. 조회만 |
| **14GiB 2차** | **520,000** | **243.66초** | **4,051.8MB** | 갱신 5,271건 |

**수치 상승은 상한 때문이 아니라 임베딩 수행 여부 때문입니다.** 1차는 갱신이 없어
조회 계층만 측정했고, 2차는 새로 들어온 5,271건을 bge-m3 로 임베딩했습니다. 따라서
2차가 **임베딩을 포함한 단독 부하의 정본**입니다. 14GiB 조건에서 4,051.8MB 로
소멸 없이 완료했으므로 여유는 충분합니다.

곡선은 15:10:45 에 938MB 까지 오른 뒤 약 1분간 평탄하다가 15:12:01 에 4,051MB 로
한 번 뛰고, 이후 3,478MB 부근에서 안정됩니다. 무한 상승이 아니라 유계입니다.

## 5. 측정 오염에 대한 기록

이번 회차는 큐를 비우고 단독으로 투입했습니다. 측정 중 저장소 작업(git 병합, 전량
테스트)도 하지 않았습니다.

같은 날 1차 회차에서는 `run_schedule_catchup_task` 가 같은 창에 들어와 피크가
그 작업의 것이었습니다. AP5 의 단일 실행 잠금이 직렬화해 메모리 합산은 피했지만,
`update_kb_task` 의 arq 기록 소요 959초에 잠금 대기 900초가 포함돼 시간 지표가
왜곡됐습니다. 무거운 태스크끼리는 잠금이 막지만 가벼운 태스크, 다른 컨테이너,
호스트 프로세스는 막지 않으므로 **측정 창에는 다른 작업을 넣지 않는 것이 원칙**입니다.
