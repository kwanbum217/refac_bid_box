## 1. 요약 (결론)

1. **수집기·적재 경로는 정상 작동한다.** 원인은 조달청 낙찰정보 API(`getScsbidListSttus*`) 자체에 대형 공고의 개찰결과가 등록되지 않거나 크게 늦어지는 **상류 공백**이다. 소형 공고 매칭률은 2026-08-31 주까지 57%대로 안정적이어서 적재 파이프라인의 결함이 아니다.
2. **`inqryDiv=1` 은 개찰일시가 아니라 낙찰결과 등록일시 기준 조회다.** API 직접 조회로 확인했으며(4.1절), 수집 창이 등록일 기준으로 최근 구간을 계속 재조사해 왔음을 DB 수집 이력이 뒷받침한다(3.3절). 코드의 체크포인트가 개찰일(`MAX(rl_openg_dt)`) 기준인 것과 창이 등록일 기준인 것의 미스매치는 구조적 누락을 만들지 않는다(개찰일시는 항상 등록일시 이하이므로, 4.3절).
3. **대형 공고(2.3억 이상, 취소공고 제외) 매칭률은 2026-07~08-10 주 44.8~50.9%(2025 같은 시기 47.5~53.4%)로 정상**이다가 08-17 주 38.2%로 떨어지고 09-07 주 23.0%, 09-14 주 11.8%로 급락했다. 사례 공고 `R26BK01661664`(개찰 2026-09-14) 등 표본 5건은 개찰 후 최장 7주가 지난 9/26 기준으로 **등록일 창과 공고일 창 조회 모두에서 API 에 존재하지 않는다**(4.2절).
4. **최근 2주(09-14, 09-21)의 급락에는 자연 등록 지연이 섞여 있다.** 대형 결과는 원래 개찰 직후가 아니라 개찰 후 6~30일에 걸쳐 도착한다(4.4절 도착 곡선). 그러나 08-17~08-31 주(보고서 시점 기준 26~40일 경과)의 38~40%는 자연 지연으로 설명되지 않는 영구 결손 성분이다.
5. **부수 리스크**: 수집 실행 기록(`pipeline_executions`)상 8/15~9/5 약 22일, 9/11~9/13, 9/21, 9/23~9/25 의 실행 공백이 확인됐다. 공백이 `MAX_CATCHUP_DAYS=7` 클램프(`collector_service.py:57`, `collector_service.py:174-188`)와 만나면 등록일 창이 영구 구멍이 되지만, 이번 8월 공백 구간은 8/27 비스케줄 적재가 사실상 회수해 관측 결손이 없었다(4.5절). 재발 시에는 클램프로 인한 영구 누락이 실제 위험이다.

1. **페이징 잘림 없음**: 등록일 2026-09-15~09-17 창 `totalCount=939` < `numOfRows=999`, 2페이지는 0건. 8/27 적재 9,185건은 다수 페이지가 정상 처리된 사례. 기각.
2. **조인 키 불일치 없음**: 사례 공고 `R26BK01643657` 은 `bid_announcements` 에 차수 000과 001(재공고)이 모두 있고 결과 행은 양쪽 모두 부재. 차수 정규화 조인 전후 모두 동일. 기각.

4. **수집 창의 재조사 구조 확인**: 최근 `collected_at` 에서 개찰일이 수개월~수년 전인 행이 계속 유입됨(예: 9/26 적재분 최소 개찰일 2024-08-19). 지연 등록된 결과는 이후 실행의 창에서 회수된다.

### 4.3 코드와 API 의 대응 관계 (수집기 결함 아님의 추가 근거)

1. 수집 창은 등록일 기준(`inqryDiv=1`)이고 체크포인트는 개찰일 기준이지만, 개찰일시 ≤ 등록일시이므로 체크포인트가 등록일 frontier 를 앞지를 수 없어 누락 스킵이 없다(3.3절 3번).
2. 지연 등록 결과는 이후 실행의 창에서 계속 회수된다. 08-03 주 개찰 대형 결과의 27%가 개찰 30일 이후 `collected_at` 에 도착했다(4.4절). 이는 창이 등록일 기준으로 계속 재조사됐다는 직접 증거다.
3. 개찰 8/14~8/21 행 수가 정상이고(4.5절), 8월 소형 매칭률이 안정적이므로 8월 수집 공백이 적재 누락으로 이어지지 않았다.

### 4.5 수집 실행 공백과 클램프 리스크

`pipeline_executions`(`source='local_scheduler'`) 기준 수집 스케줄 실행: 8/9(1성공 2실패), 8/14, 9/6(실패), 9/7~9/10, 9/14~9/20, 9/22, 9/26. 즉 **8/15~9/5 약 22일, 9/11~9/13, 9/21, 9/23~9/25 의 실행 공백**이 있다. DB `collected_at` 분포는 이와 일치한다(8/15~8/26, 8/28~9/3, 9/11~9/13, 9/23~9/25 무 적재).

8/27 07:13~07:14 에 9,185건이 적재됐는데 이는 스케줄 실행 기록에 없는 비스케줄(수동/백필 성격) 적재다. 개찰 8/14~8/21 행의 첫 수집이 모두 8/27 임에도 행 수가 인접 주와 동등하다(8/14: 362, 8/17: 2, 8/18: 372, 8/19: 384, 8/20: 351, 8/21: 336건, 용역). 따라서 22일 공백 구간의 등록분도 사실상 회수됐고, 이번 공백이 관측 결손의 주원인은 아니다.

다만 구조적 위험은 남는다. 공백이 `MAX_CATCHUP_DAYS=7` 을 초과하면 창 시작이 `어제-6일` 로 클램프되고(`collector_service.py:174-188`), 클램프 이전 등록일은 그 실행에서 영영 조회되지 않는다. 이번에는 우연히(또는 수동 조치로) 회수됐을 뿐이며, 클램프 발동 시 `collector_service.py:177-186` 의 경고 로그만 남고 별도 알림이 없다.

### 4.6 상류 사유에 대한 한계

API 에 결과가 없는 이유(등록 절차 정책 변경, 대금 지급 이후 등록, 유찰 처리 방식, OpenAPI 반영 지연 등)는 낙찰정보 API 만으로는 판별할 수 없다. 나라장터 화면의 개찰결과 공개 여부와 대조하는 후속 확인이 필요하다.

## 7. 재현 방법

본 보고서의 DB 수치는 모두 `uv run python scripts/db_readonly_query.py --sql "<질의>"` 로 재현한다. 주요 질의 골격:

1. 매칭률(분류×주간×규모): `bid_announcements a LEFT JOIN (SELECT * FROM bid_results WHERE rl_openg_dt >= '<구간 시작>') br ON br.bid_ntce_no = a.bid_ntce_no AND br.category = a.category AND RIGHT(CONCAT('000', TRIM(LEADING '0' FROM a.bid_ntce_ord)),3) = RIGHT(CONCAT('000', TRIM(LEADING '0' FROM br.bid_ntce_ord)),3)` 를 `GROUP BY 분류, 주시작(주의 월요일), 규모(>= 230000000)` 로 집계. 취소공고는 `ntce_kind_nm NOT IN ('취소공고')` 로 제외.
2. 도착 곡선: 같은 조인에 `DATEDIFF(br.collected_at, a.openg_dt)` 버킷(0-1, 2-5, 6-13, 14-30, 30+) 집계.
3. 수집 이력: `SELECT DATE(collected_at), COUNT(*) FROM bid_results WHERE collected_at >= '2026-08-01' GROUP BY 1` 및 `pipeline_executions` 스케줄 실행 이력.
4. API 시맨틱·표본 검증: `getScsbidListSttusServc` 에 `inqryDiv=1`(등록일 창)과 `inqryDiv=2`(공고게시일 창)로 각각 조회. 인증키는 `.env` 에서만 읽고 출력하지 않는다.
