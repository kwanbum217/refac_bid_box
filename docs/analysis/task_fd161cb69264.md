## 1. 출발점

애플리케이션 계측은 이미 끝나 있었다. `src/app/core/observability.py` 에 OTel SDK 초기화,
FastAPI·SQLAlchemy 계측, OTLP HTTP exporter, 민감값 마스킹 래퍼, Arq 워커 span 이 구현돼 있고,
`src/app/main.py` 와 `src/tasks/worker.py` 에서 이미 호출된다. 비어 있던 것은 받는 쪽뿐이었다.
`docker-compose.prod.yml` 의 app 과 worker 블록에는 OTEL 계열 환경변수가 하나도 없었다.
본 Task 는 애플리케이션 코드와 의존성을 건드리지 않고 받는 쪽만 배선한다.

## 3. 결정 근거

- Collector 이미지는 contrib 배포를 쓴다. tail sampling 프로세서가 필요하기 때문이다.
- 세 이미지 모두 SHA 다이제스트로 고정했다. 기존 서비스가 전부 그렇게 고정돼 있다.
  - `otel/opentelemetry-collector-contrib:0.141.0`
  - `grafana/tempo:2.9.2`
  - `grafana/grafana:12.2.0`
- 엔드포인트는 `http://otel-collector:4318/v1/traces` 이다. 앱이 OTLP HTTP exporter 에
  전체 경로를 그대로 넘기므로 경로 포함 형태가 맞다.
- 샘플링은 2층이다. 앱 헤드 샘플링 0.1 로 양을 줄이고, Collector tail sampling 으로
  도착한 오류 span 을 전량 보존한다. 두 층의 역할 차이는 정책 문서 4절에 적었다.
- 보존은 `compactor.compaction.block_retention: 168h` 하나가 정본이다.
- 메트릭 15일은 2단계 예정값이므로 설정으로 만들지 않았다.
- 7일과 0.1 은 통상값이며 실측이 아니다. 정책 문서 6절에 미측정으로 명시하고
  1주 운영 후 `tempo_data` 디스크 사용량을 재어 조정한다고 적었다.
- Grafana 는 익명 접근을 끄고 관리자 비밀번호를 필수 변수로 요구한다. 외부 포트는 열지 않는다.

## 4. 범위 제외

Prometheus 와 Loki 를 추가하지 않았다. 메트릭 계측(Counter·Histogram, `/metrics`) 이
저장소에 없고 로그는 이미 json-file 회전 중이므로 1단계 범위가 아니다.
