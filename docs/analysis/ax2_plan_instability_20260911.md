# compare-stats 매칭 쿼리 실행계획 뒤집힘 원인 분석

> 조사일: 2026-09-11
>
> 상태: 구현 없음, 원인 판정 문서만 작성
>
> 대상: `src/app/services/dashboard.py` 의 `get_compare_stats_data`(484행) 안 매칭 건수 EXISTS 쿼리
>
> 표기 규약: 이 문서에서 `EXPLAIN` 수치는 전부 추정치이고 `EXPLAIN ANALYZE` 수치는 전부 실행 실측이다. 문장마다 어느 쪽인지 명시한다. 실행시간 절대값은 원인 판정 근거로 쓰지 않는다.

## 1. 판정

원인은 미확정이다.

같은 문장, 같은 날짜 bind 대표값(`2025-09-10 00:00:00`)에서 시점만 달라 실행계획이 세 번 갈렸다. `EXPLAIN ANALYZE` 실행 실측 기준으로 au1(2026-09-10 오전)은 `ix_bid_results_dt_cat` 범위 스캔이었고, av1(같은 날 오후)은 `bid_results` 전체 스캔이었으며, 이번 조사(2026-09-11)의 `EXPLAIN ANALYZE` 실행 실측은 다시 범위 스캔이다. 아래 2절의 네 축 관찰이 영속 통계 변화, 수집 데이터 증가, 선택도 민감성 단독 설명을 각각 기각하므로, 남은 후보(일시적 메모리 통계, 실시간 index dive 변동, 동시 테스트 쓰기 영향) 중 어느 것인지 특정할 수 없다. 추측을 원인으로 적지 않으므로 미확정으로 판정한다.

선택도 경계가 실재한다는 점은 확인했다. `EXPLAIN` 추정치 기준으로 계획 전환점이 `2025-08-15`와 `2025-09-01` 사이에 있으며, 대표값의 실제 선택도는 그 경계에서 약 1만 행(약 3%) 아래에 있다. 이는 뒤집힘이 일어나기 쉬운 위치라는 정황이지, 어제 오후에 무엇을 뒤집었는지에 대한 답이 아니다.

## 2. 네 축 관찰

### 2.1 첫째 축: 옵티마이저 통계

`mysql.innodb_table_stats` 조회 실측 결과, 운영 DB(`procurement`)의 두 테이블 영속 통계 갱신 시각은 `bid_results` 2026-09-01 03:50:27, `bid_announcements` 2026-09-01 04:07:23이다. 두 시각 모두 au1과 av1 측정(2026-09-10)보다 앞선다. 따라서 두 측정 사이에 영속 통계가 갱신됐을 가능성은 없다.

같은 조회 실측에서 영속 통계 행 수는 `bid_results` 3,118,641, `bid_announcements` 2,295,025인데, 현재 실제 행 수(`SELECT COUNT(*)` 실행 실측)는 각각 3,431,580과 5,504,119이다. 영속 통계는 현재보다 `bid_results` 약 10.0%, `bid_announcements` 약 139.8% 적게 보고하므로 오래된(stale) 상태이다. `SHOW INDEX` 실행 실측의 cardinality도 영속 통계와 일치한다(`bid_results` PRIMARY 3,118,641, `ix_bid_results_dt_cat` 선두 88,123).

`mysql.innodb_index_stats` 조회 실측에서 `ix_bid_results_dt_cat`의 `n_diff_pfx01` 88,123, `n_diff_pfx02` 151,905 역시 2026-09-01 갱신분이다.

`information_schema.COLUMN_STATISTICS` 조회 실측 결과는 0행이다. 히스토그램이 존재하지 않으므로 히스토그램 변화 가설은 기각한다.

판정: 영속 통계 변화 가설은 기각한다. 통계가 오래된 것은 사실이나, 뒤집힌 두 시점 사이에 통계가 바뀐 적이 없기 때문이다.

### 2.2 둘째 축: 데이터 증가

`SELECT MAX(collected_at)` 실행 실측 결과 두 테이블 모두 2026-09-10 02:04경(`bid_results` 02:04:38, `bid_announcements` 02:04:36)이다. au1(오전)과 av1(오후, DB 시각 13:23:58 UTC) 모두 이 시각보다 뒤이므로, 두 측정 사이에는 수집에 의한 행 추가가 없었다.

날짜 분포 `SELECT COUNT(*)` 실행 실측 결과, 대표값 조건(`rl_openg_dt >= '2025-09-10 00:00:00'`)의 현재 행 수는 309,406이며 au1의 `EXPLAIN ANALYZE` 실행 실측 내부 행 수(309,406)와 정확히 같다. 최근 1년 구간의 데이터 분포는 두 시점 사이에 달라지지 않았다.

판정: 수집 데이터 증가 가설은 기각한다. 단, 다른 워커의 전량 테스트가 간헐적으로 DB에 쓰므로 테스트 쓰기의 영향은 관측하지 못했고 잔여 불확실성으로 남는다.

### 2.3 셋째 축: 인덱스 현황

`SHOW INDEX` 실행 실측 결과 `ix_bid_results_dt_cat(rl_openg_dt, category)`을 포함한 후보 인덱스가 모두 존재하고, 이번 조사의 `EXPLAIN` 추정치 10건 전체에서 `possible_keys`에 두 날짜 인덱스(`bid_results_rl_openg_dt_00b70e7a`, `ix_bid_results_dt_cat`)가 항상 후보로 올랐다. 인덱스 부재나 후보 집합 변화는 관찰되지 않았다.

판정: 인덱스 현황 변화 가설은 기각한다.

### 2.4 넷째 축: bind 값 민감도

동일한 EXISTS 문장에 날짜 대표값만 바꿔 `EXPLAIN` 추정치로 10개 지점을 측정했다. 사용한 값은 `2020-01-01`, `2024-09-10`, `2025-01-01`, `2025-06-01`, `2025-08-01`, `2025-08-15`, `2025-09-01`, `2025-09-10`, `2026-01-01`, `2026-06-01`이며 시각은 전부 `00:00:00`이다.

| 날짜 bind | 구간 실제 행 수(`SELECT COUNT` 실행 실측) | 전체 대비 | `EXPLAIN` 추정 계획 |
| --- | ---: | ---: | --- |
| 2020-01-01 | 2,065,712 | 60.2% | `ALL`, 추정치 3,118,641 |
| 2024-09-10 | 629,950 | 18.4% | `ALL`, 추정치 3,118,641 |
| 2025-01-01 | 528,259 | 15.4% | `ALL`, 추정치 3,118,641 |
| 2025-06-01 | 388,449 | 11.3% | `ALL`, 추정치 3,118,641 |
| 2025-08-01 | 336,082 | 9.8% | `ALL`, 추정치 3,118,641 |
| 2025-08-15 | 326,635 | 9.5% | `ALL`, 추정치 3,118,641 |
| 2025-09-01 | 316,101 | 9.2% | `range ix_bid_results_dt_cat`, 추정치 724,130 |
| 2025-09-10 | 309,406 | 9.0% | `range ix_bid_results_dt_cat`, 추정치 724,782 |
| 2026-01-01 | 208,854 | 6.1% | `range bid_results_rl_openg_dt_00b70e7a`, 추정치 517,518 |
| 2026-06-01 | 71,386 | 2.1% | `range bid_results_rl_openg_dt_00b70e7a`, 추정치 152,258 |

전환점은 `2025-08-15`(추정치 `ALL`)와 `2025-09-01`(추정치 `range`) 사이에 있다. 대표값(2025-09-10)의 실제 구간 행 수는 경계 바로 위 지점보다 약 1만 행(약 3%) 적을 뿐이다. 추정치의 입자도 거칠다. `2025-09-01`과 `2025-09-10`의 실제 행 수는 6,695행 차이나는데 추정치는 724,130과 724,782로 사실상 같으며, 실제(309,406) 대비 약 2.3배 과대 추정이다.

판정: 선택도 경계의 존재는 `EXPLAIN` 추정치로 확인했다(실측 아님). 그러나 au1과 av1은 같은 bind 값에서 실행계획이 갈렸으므로, 선택도 민감성 단독 설명은 기각한다.

## 3. 같은 bind의 세 관찰 정리

| 관찰 | 방법 | `bid_results` 계획 | 행 수 표기 |
| --- | --- | --- | --- |
| at4 원형 IN | `EXPLAIN` 추정치 | `ALL` | 추정치 3,118,641 |
| au1 EXISTS | `EXPLAIN ANALYZE` 실행 실측 | `range ix_bid_results_dt_cat` | 실행 실제 309,406 |
| av1 EXISTS | `EXPLAIN ANALYZE` 실행 실측 | 전체 스캔 | 실행 실제 3.43e+6 |
| 이번 조사 EXISTS | `EXPLAIN ANALYZE` 실행 실측 | `range ix_bid_results_dt_cat` | 추정치 724,782, 실행 실제 309,406, 최종 327,686 |
| 이번 조사 원형 IN | `EXPLAIN` 추정치 | `range ix_bid_results_dt_cat` | 추정치 724,782 |

이번 조사의 `EXPLAIN ANALYZE` 실행 실측은 대표값에서 범위 스캔으로 돌아왔으므로, av1의 전체 스캔은 그 시점의 일시적 선택이었다. 원형 IN 문장의 `EXPLAIN` 추정치도 at4 시점 `ALL`에서 현재 `range`로 바뀌었는데, 영속 통계는 그 사이 갱신된 적이 없다. 즉 추정치 자체도 같은 문장·같은 bind에서 시점에 따라 갈렸다.

이번 조사에서 `EXPLAIN ANALYZE` 실행 실측의 최상위 소요는 약 5,905ms로 관측됐으나, 동시 실행 중인 전량 테스트의 부하가 섞여 있으므로 원인 판정 근거로 쓰지 않는다. 판정 근거는 계획 선택(어느 인덱스, type, 예상 행 수)이며 그것은 부하에 둔감하다.

## 4. 대책 후보

구현하지 않았으며 효과는 전부 추정치이다. 실측 전제로만 검토한다.

- 후보 1. 매칭 쿼리 실행계획 안정화용 복합 인덱스(`bid_results(rl_openg_dt, bid_ntce_no)` 등) 검토. 기대 효과는 추정치이며 인덱스 크기·수집 쓰기 비용·옵티마이저 선택의 실측 비교가 전제이다.
- 후보 2. 옵티마이저 힌트나 계획 고정으로 경계 부근 흔들림 차단. 기대 효과는 추정치이며 힌트가 버전·데이터 분포 변화에 고착될 위험의 검토가 전제이다.
- 후보 3. 기관별 상위 10 집계 경량화. av1의 `EXPLAIN ANALYZE` 실행 실측에서 1순위(약 2.23초)였으므로 기대 효과는 추정치이나 귀속 순위는 실측이다.
- 후보 4. 영속 통계 주기 갱신. 현재 통계가 오래된 것은 실측이나, 갱신이 뒤집힘을 막는다는 점은 추정치이다. `ANALYZE TABLE`은 관찰 대상을 바꾸는 쓰기이므로 실행하지 않았고, 필요 시 별도 승인(escalation)으로 제안한다.

후보에서 제외한 것. 캐시 TTL 연장은 미적중 1회 비용을 줄이지 않으므로 후보가 아니다(제약).

## 5. 다음 실험

- 동일 bind 대표값으로 `EXPLAIN` 추정치를 시간을 두고 반복 측정해 추정치 자체의 흔들림을 직접 관측한다(미확인).
- 옵티마이저 트레이스로 범위 대 전체 스캔의 비용 계산 내역을 비교한다. 세션 설정 변경이 필요하면 실행하지 말고 escalation으로 제안한다(미확인).
- 전량 테스트 쓰기 구간과 실행계획 선택의 시간 상관관계를 분리 측정한다(미확인).
- `ANALYZE TABLE` 실행 여부 자체를 escalation으로 제안하고, 승인 전에는 실행하지 않는다(미확인).

## 6. 작업 범위 준수

`ANALYZE TABLE`을 실행하지 않았고 코드·인덱스·마이그레이션 변경이 전혀 없다. DB 조회는 전부 `uv run python scripts/db_readonly_query.py --sql` 형태만 썼다. 근거는 `docs/analysis/au1_compare_stats_exists_verification_20260910.md`, `docs/analysis/av1_compare_stats_cost_accounting_20260910.md`, `docs/analysis/at4_compare_stats_optimization_20260910.md`의 인용과 이번 조사의 읽기 전용 질의뿐이다.
