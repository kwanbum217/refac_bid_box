# 콜드 SQL 총량 지표 강등 (2026-09-01)

> **작성일**: 2026-09-01
> **결정**: 콜드 SQL 총량을 G3 게이트에서 제외하고 **관찰 지표**로 강등합니다.
> **결정 근거**: 동일 조건 재측정이 재현되지 않음 (아래 1절)
> **규약 반영**: [`../ops/latency_gate_protocol.md`](../ops/latency_gate_protocol.md) 5.4 절

---

## 1. 재현되지 않습니다

같은 HEAD, 같은 fixture(sha `2c98c636a478`), 같은 명령, 같은 32문항 x 3회입니다.

| 측정 | HEAD | 버퍼풀 | cold 총 SQL | 최대 단일 쿼리 |
| --- | --- | ---: | ---: | ---: |
| E4 (2026-08-30) | `7dcc771` | 128MB | 223.77초 | 29.67초 |
| OFF-1 (2026-09-01) | `d3cad6c` | 128MB | 333.19초 | 49.28초 |
| OFF-2 (2026-09-01) | `d3cad6c` | 128MB | **432.99초** | **92.14초** |

**OFF-1 과 OFF-2 는 조건이 완전히 같습니다.** 그런데 99.8초(30%) 벌어졌고, 세
측정이 단조 증가합니다. 무작위 흔들림이 아니라 누적되는 형태입니다.

세 측정 모두 `canonical=true`, `failed_gates=[]`, 요청 실패 0 입니다. **규약을
지켰는데도 재현되지 않았다는 뜻이며, 규약에 빠진 조건이 있었다는 뜻입니다.**

---

## 2. 코드는 원인이 아닙니다

E4 이후 `src/rag/structured_data.py` 를 건드린 커밋은 다섯 건입니다
(`19f0c6f`, `33bfdf8`, `9d38a2a`, `259d9d3`, `dbd1fb2`). 이 중 `19f0c6f` 와
`33bfdf8` 은 Wave E5 손상 제외 힌트 복원으로 실제 코드를 바꿨습니다.

**그런데 실행되는 SQL 은 같습니다.** 근거는 digest 대조입니다.

| 항목 | 값 |
| --- | ---: |
| E4 digest 수 | 38 |
| 현재 digest 수 | 38 |
| 신규 digest | **0** |
| 소멸 digest | 1 (0.00초) |

digest 는 정규화된 쿼리의 해시이므로 조건이 하나라도 추가·삭제되면 값이 달라집니다.
최대 증가 digest `6f07b00e` 는 양쪽 산출물에 **동일하게 존재**합니다. 즉 같은
쿼리가 4.09초에서 49.28초로 느려진 것이며, 쿼리가 바뀐 것이 아닙니다.

---

## 3. 원인: 버퍼풀 128MB 대 데이터 27GB

`innodb_buffer_pool_size` 가 MySQL 기본값 **128MB** 였고 `docker-compose.yml` 의
`db` 서비스는 이 값을 지정하지 않았습니다(`--innodb-redo-log-capacity` 만 지정).

| 항목 | 값 |
| --- | ---: |
| `bid_announcements` 데이터 | 27,272MB |
| `bid_results` 데이터 | 1,060MB |
| 버퍼풀 | **128MB** |

작업 세트가 버퍼풀의 200배를 넘으면 매 측정이 디스크 I/O 상태에 그대로 휘둘립니다.
가장 크게 튄 낙찰업체 집계는 EXPLAIN 상 `type=ALL`, 3,118,641행, `filtered 2.78%`
로 **항상 전체 스캔**입니다. 날짜 필터가 없어 E1 의 날짜 인덱스 힌트 조건
(날짜 있음 AND category 없음)에 걸리지 않습니다. E4 에서 4.09초였던 것은 이
쿼리가 빨라서가 아니라 그때 데이터가 캐시에 있었기 때문입니다.

**조치**: `--innodb-buffer-pool-size=${MYSQL_BUFFER_POOL_SIZE:-2147483648}` 로
2GB 를 배선했습니다. Docker VM 13.6GB 중 여유를 감안한 보수적 값이며 환경 변수로
조정할 수 있습니다.

## 4. 이 사실이 무효화하는 서술

| 종전 서술 | 정정 |
| --- | --- |
| ngram 선행필터가 콜드를 6.38초 **악화**시켰다 | 6.38초는 회차 간 변동폭(99.8초)의 6% 로 **노이즈 이하**입니다. 기각 결론은 유지되나(19배 개선이라면 수백 초가 줄었어야 함) 이 수치를 근거로 쓰지 마십시오 |
| E4 대비 109초 **회귀**가 발생했다 | 비교 대상이 안정적이지 않아 성립하지 않습니다. 회귀가 아니라 지표 불안정입니다 |
| 콜드 SQL 개선이 G3 컷오버의 선행 조건이다 | 관찰 지표로 강등합니다. 컷오버는 재현되는 지표로 판정합니다 |

---

## 5. 강등 이후 취급

| 항목 | 규정 |
| --- | --- |
| 게이트 판정 | **쓰지 않습니다** |
| 기록 | 추세 관찰용으로 계속 남깁니다 |
| 비교 조건 | 버퍼풀 크기와 DB 연속 가동 시간이 같은 측정끼리만 비교합니다 |
| 대규모 DDL 직후 측정 | 하지 않습니다. 버퍼풀과 파일시스템 캐시가 교란됩니다 |

---

## 6. 측정 함정

| 함정 | 실제 |
| --- | --- |
| `canonical=true` 면 비교 가능한 값이다 | 규약이 덮지 않는 조건(버퍼풀)이 다르면 비교할 수 없습니다 |
| 두 측정의 차이는 코드 변경 때문이다 | digest 대조 없이 단정하지 마십시오. 여기서는 코드 기여가 0 이었습니다 |
| 한 번 측정으로 회귀를 판정한다 | 동일 조건 재측정 없이는 변동폭을 모릅니다. 효과보다 변동폭이 크면 판정 불가입니다 |
