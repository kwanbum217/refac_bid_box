> **작성일**: 2026-09-02
> **대상**: Phase 7 컷오버 잔여 항목 3.1 G1 검증 — `scripts/verify_migration.py` 의 5단계 누적 행 수 하한 검사가 수집 성장분에 가려져 이행 시점 유실을 못 잡는 결함

## 1. 배경 — 누적 하한 검사가 가리는 결함

`scripts/verify_migration.py` 의 5단계 `verify_row_counts` 는 `bid_announcements`·`bid_results` 두 테이블의 **누적 행 수**가 `BASELINE_ROW_COUNTS` 대비 `MIN_ROW_COUNT_RATIO = 100.0%` 이상인지(즉, 하한 검사)만 본다. 이는 의도된 설계다 — 수집이 계속 돌아 행이 늘기 때문에 정확 일치로 바꾸면 매번 검증이 실패한다. 다만 그 설계는 **이행 시점 데이터가 유실돼도 성장분이 가리는** 결함을 동반한다.

`docs/context/CURRENT_STATE.md` 129행이 이를 명시한다:

> **행 수 판정은 여전히 하한 검사입니다.** 수집이 계속 돌아 행이 늘기 때문에 의도된 설계이며 정확 일치로 바꾸지 마십시오. 성장 데이터와 이행 원본을 구분하는 reconciliation 은 아직 없습니다.

이번 작업은 **누적 하한을 유지**하면서 별도의 6단계 reconciliation 으로 **이행 시점 이전에 수집된 행**을 따로 세어 baseline 과 대조하는 검증을 추가한다.

## 2. 조치 — 6단계 reconciliation 추가

### 2.1 데이터 모델 — `collected_at` 을 경계로 사용

`src/app/models/bids.py` 를 재확인했다.

- `BidAnnouncement.collected_at: DateTime NOT NULL default=utcnow` (line 345)
- `BidResult.collected_at: DateTime NOT NULL default=utcnow` (line 208)

**수집 시점이 행마다 존재**한다. 이를 이행 시점 경계로 사용해 다음 두 구간을 분리한다.

- `collected_at < MIGRATION_CUTOVER_TS` 인 행 = **이행 원본** (refac_bid_box 이전 시스템에서 들어왔어야 할 데이터)
- `collected_at >= MIGRATION_CUTOVER_TS` 인 행 = **수집 성장분** (refac_bid_box 운영 중 신규 수집)

이렇게 정의하면 `BASELINE_ROW_COUNTS` 는 그대로 **이행 원본의 기준선** 역할을 유지하고, 누적 행 수는 **원본 + 성장분**으로 해석된다. 검증이 둘로 갈라진다.

### 2.2 이행 시점 경계의 단일 출처

스키마 서명 baseline 이 따르는 구조를 그대로 따른다. **여러 곳에 하드코딩하지 않는다**.

```python
# scripts/verify_migration.py
MIGRATION_CUTOVER_TS: datetime = datetime(2026, 7, 31, 6, 20, 49, tzinfo=UTC)
MIGRATION_CUTOVER_BASELINE_PATH: Path = (
    PROJECT_ROOT / "data" / "backups" / "row_count_reconciliation_baseline.json"
)
RECONCILIATION_TABLES: tuple[str, ...] = ("bid_announcements", "bid_results")
```

근거 주석에 명시: `data/backups/data_assets_checksums.json` 의 `generated_at = "2026-07-31T06:20:49.674634+00:00"` 와 동일한 시각을 1차 기준점으로 둔다 — 원본 `bid_box` 자산을 동결·체크섬화한 시점이며, 이 시점 이전에 수집된 행이 "이행 원본"이다. 운영에서 더 정확한 시점이 확인되면 baseline 파일을 갱신한다.

baseline 파일은 스키마 서명 baseline 과 같은 디렉터리(`data/backups/`)에 둔다.

### 2.3 검증 동작 규약

`verify_reconciliation()` 함수가 6단계의 본체다. 분기별 동작은 다음 표와 같다.

| 조건 | 판정 | 출력 |
| --- | --- | --- |
| DB 조회 실패 (연결 자체 불가, `session.execute` 예외) | **FAIL** | `"reconciliation DB 조회 실패 (...)"` |
| DB 가 비어있음(두 테이블 누적 0행) | **PASS (건너뜀)** | `"DB 가 비어있어 reconciliation 건너뜀 (누적 0행)"` |
| baseline 파일 없음 + `auto_save_baseline=True` | **PASS (최초 기준선 기록)** | `"최초 기준선 기록 — 원본 X행 / Y행 (...)"` |
| baseline 파일 없음 + `auto_save_baseline=False` | **FAIL** | `"기준선 파일 없음: <path>"` |
| baseline 파일 있고 원본 ≥ baseline | **PASS** | `"원본/성장분 대조 일치 — ..."` |
| baseline 파일 있고 원본 < baseline | **FAIL** | `"이행 원본 행 수 부족: <details>"` |
| baseline 파일 로드 실패(JSON 파싱 등) | **FAIL** | `"reconciliation baseline 로드 실패: ..."` |
| baseline 파일 형식 오류(테이블 키/타입) | **FAIL** | `"... baseline 형식 오류"` |

DB 부재는 **통과로 위장하지 않는다**. 빈 DB 인 경우에만 baseline 비교 대상이 무의미하므로 "DB 가 비어있어 reconciliation 건너뜀" 메시지를 남기고 PASS 한다 — 빈 DB 자체의 판정은 5단계가 담당한다.

### 2.4 main() 의 5단계-6단계 게이팅

5단계(누적 행 수)가 FAIL 이면 6단계는 실행하지 않고 5단계의 FAIL 만 남긴다. 이유: 누적 행이 부족한 상태에서 reconciliation 의 baseline 비교도 같은 원인이 두 번 보고되어 판정을 흐린다. 원인을 단일화한다.

```python
step5_ok, step5_msg = verify_row_counts()
if step5_ok:
    step6_ok, step6_msg = verify_reconciliation(baseline_path=args.reconciliation_baseline_path)
else:
    step6_ok, step6_msg = (False, "5단계 실패로 reconciliation 생략 (누적 행 수 부족 판정 유지)")
```

### 2.5 baseline 파일 포맷

```json
{
  "schema_version": "1.0.0",
  "cutover_timestamp": "2026-07-31T06:20:49+00:00",
  "rationale": "data/backups/data_assets_checksums.json 의 generated_at 와 ...",
  "tables": {
    "bid_announcements": <원본 행 수>,
    "bid_results": <원본 행 수>
  }
}
```

### 2.6 누적 0 / 빈 DB 동작

`verify_reconciliation` 자체는 6단계의 판정만 책임진다. 빈 DB 의 판정은 5단계(`verify_row_counts`)가 누적 하한으로 별도 보고한다. 5단계가 FAIL 이면 6단계는 위 2.4에 따라 실행되지 않으므로 "DB 가 비어있어 reconciliation 건너뜀" 분기는 **5단계가 PASS 인 상태에서 누적 0인 특이 케이스**(테스트 환경 등)에서만 발현한다.

## 3. 검증 통과 조건

기존 4단계 + 5단계(누적 하한) + 6단계(reconciliation) 이다. **어떤 단계도 통과 조건이 완화되지 않았다**.

| 단계 | 검증 | 판정 변경 여부 |
| --- | --- | :---: |
| 1 | ML 가중치 4종 SHA256 체크섬 | 불변 |
| 2 | ChromaDB 컬렉션 무결성 | 불변 |
| 3 | DB 필수 테이블 존재 | 불변 |
| 4 | DB 전 테이블 스키마 서명 | 불변 |
| 5 | 데이터 행 수 하한 | **불변 (정확 일치 회귀 없음)** |
| 6 | G1 reconciliation: 원본/성장분 분리 대조 | **신규** |

`MIN_ROW_COUNT_RATIO = 100.0`, `BASELINE_ROW_COUNTS` 의 두 값 모두 그대로다. 5단계는 여전히 하한 검사다.

## 4. DDL / DML 금지 — read-only 검증

6단계는 `SELECT COUNT(*)` 만 실행한다. baseline 파일 기록 외에는 어떤 DDL 이나 DML 도 실행하지 않는다. 회귀 단언은 `tests/test_g1_reconciliation.py::test_reconciliation_does_not_run_ddl_or_dml` 가 담당하며, 호출 전후의 행 수가 같음을 확인한다.

`verify_migration.py` 안에서 6단계가 호출하는 모든 SQL 은 두 컬럼(`total`, `original`)을 `SELECT` 로 가져오는 집계 쿼리 하나다:

```python
select(
    func.count(model_cls.id).label("total"),
    func.sum(
        case((model_cls.collected_at < MIGRATION_CUTOVER_TS, 1), else_=0)
    ).label("original"),
)
```

테스트 픽스처가 세션 팩토리를 가짜로 주입하면 `_count_rows_by_cutover` 의 `session.execute(stmt)` 가 예외를 일으키고, 6단계는 즉시 FAIL 로 보고한다 — 통과로 위장하지 않는다.

## 5. 테스트 — `tests/test_g1_reconciliation.py`

9건의 단언으로 운영 read-only 경로의 모든 분기를 검증한다.

| 테스트 | 분기 | 단언 |
| --- | --- | --- |
| `test_reconciliation_creates_baseline_and_passes` | baseline 부재 + PASS | baseline 파일 생성, 기록된 행 수 일치, PASS |
| `test_reconciliation_passes_when_baseline_matches` | 2회차 baseline 일치 | PASS |

| `test_reconciliation_ignores_growth_rows` | baseline 3/3 + 원본 3행 + 성장분 1,000행 | **PASS + "성장분 1,000행" 관측값** |
| `test_reconciliation_fails_when_db_session_factory_raises` | DB 조회 자체 실패 | **FAIL + "DB 조회 실패"** (통과 위장 금지) |
| `test_reconciliation_skips_when_db_is_empty` | 누적 0행 | PASS + "DB 가 비어있어 ... 건너뜀" |

| `test_reconciliation_baseline_path_constant_is_single_source` | 경계 단일 출처 | 정의 1건, baseline 디렉터리 = schema baseline 디렉터리 |

`test_reconciliation_ignores_growth_rows` 가 **수집 성장분이 가리지 않음**의 핵심 단언이다. baseline 3/3 상태에서 원본 3행만 유지하고 성장분 1,000행을 추가해도 PASS 여야 한다 — 5단계 누적 하한 검사가 그랬듯 6단계도 **수집으로 인한 행 증가는 검증 결과에 영향을 주지 않는다**.

## 8. 한계와 후속

- 운영 환경에서 실측한 더 정확한 이행 시점이 확인되면 `MIGRATION_CUTOVER_TS` 또는 baseline 파일을 갱신한다. 단일 출처(상수 + 파일) 구조는 그대로 유지한다.
- 빈 DB 인 경우 "건너뜀" 분기는 빈 DB 자체의 판정 책임이 5단계에 있음을 전제한다. 향후 5단계가 비어있는 운영 DB 를 다르게 판정하게 바뀐다면 6단계의 빈 DB 분기도 함께 갱신해야 한다.
- 이 검증은 두 테이블(`bid_announcements`, `bid_results`)만 본다. 다른 수집 테이블도 같은 패턴으로 확장하려면 `RECONCILIATION_TABLES` 에 추가하면 된다.
