## 1. 개요 및 배경

### 1.1 결함 배경
2026-09-03 외부 감사에서 기존 복원 리허설 도구인 `run_restore_drill`이 **이름만 리허설**이고 실제로는 아카이브를 해제하거나 DB 클라이언트를 호출하지 않은 채 계획 검증 및 매니페스트 체크섬 확인만 수행하고 있던 점이 P1 결함으로 지적되었습니다.

복원 가능 여부가 입증되지 않은 백업은 신뢰할 수 없는 백업입니다. 이에 따라 격리된 환경에서 실제로 아카이브를 풀고, 임시 데이터베이스에 데이터를 import한 후, 기존의 G1 무손실 검증 스크립트([`scripts/verify_migration.py`](../../scripts/verify_migration.py))를 재사용해 복원 무결성을 완전히 실측·검증하는 도구로 전면 고도화하였습니다.

### 1.2 요구사항 및 원칙
1. **실제 복원 실행**: 격리 대상 디렉토리에 ChromaDB 및 모델 아카이브를 풀고, 격리된 MySQL DB에 덤프를 실제로 복원.
2. **G1 무손실 검증 재사용**: 복원 완료 후 `scripts/verify_migration.py`를 재사용하여 ML 가중치, ChromaDB, 스키마, 행 수, reconciliation 6단계를 전량 검증.
3. **격리 가드 (Fail-Closed)**: 운영 프로젝트 루트, 상위/하위 경로, 현재 작업 디렉토리(cwd), 운영 DB 접속 대상 침범을 원천 차단.
4. **산출물 안전 정리 (Cleanup)**: 성공 및 실패 시 임시 DB와 임시 디렉토리를 자동 정리하되, 오직 `--keep-artifacts` 명시 플래그 지정 시에만 보존.
5. **단계별 소요 시간 및 RPO 시차 계측**: 아카이브 해제, DB import, G1 검증, 정리 각각의 시작·종료 시각 및 소요 시간과 스냅샷 `consistency_window`와의 시차를 기록.
6. **합격 판정 유예**: RPO/RTO 공식 목표치가 미확정이므로 인위적인 threshold 비교 판정 코드를 두지 않고 측정값만 기록.

## 2. 주요 변경 사항 및 설계

### 2.1 저수준 유틸리티 분할 및 안전 함수 추가 (`scripts/backup_recovery_core.py`)
- **`create_mysql_database`**: 임시 격리 DB 생성 (`CREATE DATABASE IF NOT EXISTS`) 지원.
- **`drop_mysql_database`**: 임시 격리 DB 삭제 지원. 운영 DB(`procurement`) 또는 시스템 DB에 대한 삭제 요청 시 `ValueError`로 즉시 거부하는 안전 가드 내장.
- **`cleanup_drill_target_dir`**: 리허설 산출물 정리 전용 함수. 대상 경로가 비어있거나, 루트(`/`), 프로젝트 루트, 상위/하위 경로, 작업 디렉토리와 겹치면 절대 삭제하지 않고 `ValueError`로 차단하는 fail-closed 가드 내장.
- **라인 수 캡 준수**: `test_backup_recovery_split.py`의 상한선(298줄)을 엄격히 준수하여 260줄로 최적화.

### 2.2 복원 리허설 실측 엔진 구현 (`scripts/backup_recovery.py`)
- **`run_drill_g1_verification`**: `scripts/verify_migration.py`를 격리 환경변수(`DB_NAME`, `DATA_ASSET_ROOT`, `CHROMA_DB_PATH`, `MODEL_FILES_DIR`)로 서브프로세스 호출하여 기존 검증 로직 100% 재사용.
- **`run_restore_drill`**:
  - 스냅샷 무결성 사전 검증 (부분 백업 또는 `recovery_trusted: false` 시 즉시 실패 종료)
  - 2단계 아카이브 해제 (`chroma_db.tar.gz`, `models.tar.gz`)
  - 3단계 DB 임포트 (`create_mysql_database` -> `restore_mysql_database`)
  - 4단계 G1 무손실 검증 (`run_drill_g1_verification`)
  - 5단계 안전 정리 (`try ... finally` 블록에서 `drop_mysql_database` 및 `cleanup_drill_target_dir` 호출)
- **라인 수 캡 준수**: `test_backup_recovery_split.py`의 상한선(513줄)을 엄격히 준수하여 449줄로 최적화.

### 2.3 CLI 서브커맨드 확장
- `--db-name`: 격리 대상 DB 이름 오버라이드 지원 (기본값: `<운영DB>_restore_drill`)
- `--keep-artifacts`: 리허설 산출물 보존 명시 플래그 (기본값: False)
