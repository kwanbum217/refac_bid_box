## 1. 수행 내용

`verify_reconciliation`이 낙찰 기준 단일 집합을 공고 기준 ChromaDB 색인과 차집합하던 모집단 불일치를 제거하고 저장소마다 그 저장소가 실제로 담는 도메인과 1:1로 대조하게 만들었습니다. 4장 후보 1을 채택하고 후보 2와 3은 채택하지 않았습니다.

## 2. 변경 사항

- `get_db_announcement_notice_numbers` 신설: `BidAnnouncement.bid_ntce_no` 조회, `collected_since`가 있으면 `collected_at`으로, 없고 `start_date`가 있으면 `bid_ntce_dt`로 구간 필터. 기존 `get_db_result_notice_numbers` 구조를 그대로 따릅니다.
- Meilisearch 조회기를 `dataset` 인자를 받는 `get_meilisearch_notice_numbers` 하나로 정리하고 페이지네이션 구조를 재사용합니다. `get_meilisearch_result_notice_numbers`와 `get_meilisearch_announcement_notice_numbers`는 얇은 전달기로 유지됩니다.
- `verify_reconciliation`은 세 대조를 각각 독립 수행합니다. 하나: DB 공고 대 ChromaDB. 둘: DB 공고 대 Meilisearch announcement. 셋: DB 낙찰 대 Meilisearch result. 하나라도 비어 있지 않으면 `passed`는 거짓입니다.
- `execute_consistency_check`와 `run_reconciliation`의 요약 출력이 새 지표를 반영합니다. 실패 메시지는 공고 누락과 낙찰 누락을 분리 표기하고 성공 시 반환 사전 전체를 출력합니다.
- 예외 공고번호 목록은 두지 않았고 조회 실패는 기존대로 `RuntimeError`로 올립니다.

## 4. 검증

- 세 대조 각각에 1건 누락 시 `passed`가 거짓이 되는 테스트 3건을 `fetcher` 주입 방식으로 추가했고 실제 저장소에 접속하지 않습니다.
- 검증 명령 네 개를 전면에서 실행했고 결과는 `worker_done.json`의 `verification`에 기록했습니다.
