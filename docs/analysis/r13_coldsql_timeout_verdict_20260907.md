## 3. 미충족 게이트와 그 원인

미충족은 `no_request_failures` 와 `trace_correlation_passed` 둘입니다.
**후자는 전자의 결과이며 독립 결함이 아닙니다.** 성공 응답 93건과 서버 로그 96건의
차이가 1:1 대조를 깨뜨린 것입니다.

`fixture_sha256_canonical`, `limit_zero`, `item_count_full`, `repetitions_minimum`,
provenance 결박(start/end SHA, clean, 모델, 포트)은 전부 통과했습니다.

### 3.1 실패 3건은 전부 타임아웃입니다

| 문항 | 콜드 | 반복 | 소요 | 사유 |
| --- | :---: | :---: | ---: | --- |
| q03 | 예 | 0 | 120,011ms | timeout |
| q25 | 예 | 0 | 120,007ms | timeout |
| q31 | 예 | 0 | 120,003ms | timeout |

분리 집계는 **전송 실패 3건, 트레이스 헤더 누락 0건** 입니다. 셋 다 첫 반복의 콜드
회차이고 소요가 120초 상한에 붙어 있습니다.

**서버는 끝까지 처리했습니다.** 컨테이너 세그먼트 로그는 96건이 모두 남았고 그중
`sql_ms` 최대가 166,625ms 입니다. 따라서 실패 3건의 실제 소요는 120초가 아니라
**그보다 큰 미지의 값**입니다. 클라이언트가 처리 중인 요청을 끊었을 뿐입니다.

이 세 문항은 2026-08-30 GPT 보고서가 느린 문항으로 지목한 `q03·q08·q25·q31` 과
겹칩니다. 별개 관찰이 같은 대상을 가리켰습니다.

### 3.2 이 판정은 선행 하네스로는 불가능했습니다

종전 하네스는 실패 시 정수 카운터만 남기고 예외와 소요 시간과 문항을 버렸습니다.
2026-09-06 측정이 "8회 중 2회 HTTP 실패" 로만 기록돼 원인을 판정할 수 없었던 이유가
이것입니다. 2026-09-07 커밋 `6f6ab0a` 가 실패 회차별 사유·소요·문항 기록과 사유
분리 집계를 넣은 뒤 첫 실행에서 곧바로 원인이 나왔습니다.

## 4. 콜드 지연은 소수 문항 현상입니다

`sql_ms` 구간 분포입니다.

| 구간 | n | P50 | P95 | P99 | max |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전체 | 96 | 14.5ms | 1,316.2ms | 157,940.9ms | 166,625.2ms |
| 콜드 | 29 | 19.6ms | 1,465.9ms | 78,751.1ms | 108,739.9ms |
| 웜 | 64 | 13.1ms | 34.2ms | 64.6ms | 100.7ms |

**콜드 P50 이 19.6ms 입니다.** 콜드 요청 대부분은 웜과 차이가 없고 P95 를 넘어서면서
수만 ms 로 튑니다.

종전 관찰치 "콜드 `sql_ms` P50 86,539ms" 는 **콜드 표본이 2건뿐이라 그 소수 문항에
표본이 쏠린 결과**입니다. 이번 29건 표본은 같은 지표를 전혀 다르게 규정합니다.
개선이 일어난 것이 아니라 종전 수치의 대표성이 없었던 것입니다.

**이 문서는 콜드 SQL 총량을 게이트로 되돌리자고 제안하지 않습니다.** 2026-09-01
결정대로 관찰 지표로 유지합니다. 다만 최적화 대상이 "콜드 전반" 이 아니라 특정
문항의 쿼리 형태라는 점이 이번에 좁혀졌습니다.

## 5. 2차 측정: 정본 확보와 그 한계

타임아웃을 300초로 올려 같은 조건으로 재측정했습니다.

| 항목 | 값 |
| --- | --- |
| 측정 커밋 | `ed5d40c` (start·end 동일, clean) |
| 결과 | `canonical: true`, `status: ok`, 실패 게이트 0건 |
| 요청 | 96건 전량 성공. 전송 실패 0, 헤더 누락 0 |
| trace 대조 | 응답 96 대 로그 96, 1:1 통과 |

**R-13 의 정본 자격 요건은 이것으로 충족됐습니다.** 1차에서 끊겼던 q03·q25·q31 이
모두 완주했습니다.

### 5.1 그러나 이 정본은 버퍼풀 콜드 조건이 아닙니다

같은 `sql_ms` 지표가 두 실행에서 이렇게 다릅니다.

| 구간 | 1차 (13:09) | 2차 (13:31) |
| --- | ---: | ---: |
| 콜드 P50 | 19.6ms | 12.9ms |
| 콜드 P99 | 78,751.1ms | 240.6ms |
| 콜드 max | 108,739.9ms | **320.3ms** |
| q25 콜드 | 타임아웃(>120,000ms) | **320.3ms** |

**같은 커밋, 같은 질의, 22분 차이입니다.** 코드가 바뀌지 않았으므로 원인은 DB 상태
하나뿐입니다.

DB 컨테이너는 12:58:02 에 기동해 두 실행 사이에 재기동하지 않았습니다. 1차는 기동
11분 뒤라 버퍼풀이 비어 있었고, 2차는 1차의 96요청이 버퍼풀을 채운 뒤였습니다.

**하네스의 `is_cold` 는 버퍼풀 상태가 아니라 문항별 첫 반복을 뜻합니다.** 따라서
canonical 게이트를 전부 통과해도 그 산출물이 버퍼풀 콜드를 측정했다는 보장은
없습니다. 게이트에 그 조건이 없기 때문입니다.

### 5.2 이 결과를 어떻게 읽어야 하는지

| 읽어도 되는 것 | 읽으면 안 되는 것 |
| --- | --- |
| 웜 버퍼풀에서 `sql_ms` 는 콜드·웜 구분 없이 P99 240ms 이내다 | 콜드 SQL 문제가 해소됐다 |
| 1차의 100초대 값은 재현 가능하며 버퍼풀이 비었을 때 나타난다 | 1차 수치가 오측정이었다 |
| 타임아웃 120초는 버퍼풀 콜드 조건에서 부족하다 | 300초면 충분하다(콜드 조건에서 미검증) |

**2차는 버퍼풀 콜드 조건을 재현하지 않았으므로 1차를 대체하지 않습니다.** 두 실행은
서로 다른 조건의 측정이며 둘 다 보존합니다.

## 6. 다음 측정의 조건

정본 자격은 확보했으므로 남은 것은 **버퍼풀 콜드 조건의 재현**입니다.

`--timeout-sec` 기본값은 **아직 올리지 마십시오.** 2차가 콜드 조건이 아니었으므로
q03·q25·q31 의 콜드 실제 소요는 여전히 미지수입니다. 1차에서 알 수 있는 것은
"120초보다 크다" 뿐이고, 2차의 320ms 는 콜드 값이 아닙니다.

순서는 이렇습니다.

1. DB 컨테이너를 재기동해 버퍼풀을 비운 뒤 타임아웃 300초로 측정합니다. 이 실행의
   목적은 **콜드 조건에서 q03·q25·q31 의 실제 소요를 얻는 것**입니다.
2. 그 값을 근거로 타임아웃 기본값을 정합니다.
3. 하네스가 버퍼풀 상태를 provenance 에 기록하도록 보강하는 것을 검토합니다. 지금은
   같은 게이트를 통과한 두 산출물이 전혀 다른 조건을 측정해도 구분되지 않습니다.

**근거 없이 기본값부터 올리지 마십시오.** 숫자만 바꾸면 다음 사람이 그 값의 출처를
확인할 수 없습니다.
