## 3. 미충족 게이트와 그 원인

미충족은 `no_request_failures` 와 `trace_correlation_passed` 둘입니다.
**후자는 전자의 결과이며 독립 결함이 아닙니다.** 성공 응답 93건과 서버 로그 96건의
차이가 1:1 대조를 깨뜨린 것입니다.

`fixture_sha256_canonical`, `limit_zero`, `item_count_full`, `repetitions_minimum`,
provenance 결박(start/end SHA, clean, 모델, 포트)은 전부 통과했습니다.

### 3.1 실패 3건은 전부 타임아웃입니다

| 문항 | 콜드 | 반복 | 소요 | 사유 |
| --- | :---: | :---: | ---: | --- |
| q03 | 예 | 0 | 120,011ms | timeout |
| q25 | 예 | 0 | 120,007ms | timeout |
| q31 | 예 | 0 | 120,003ms | timeout |

분리 집계는 **전송 실패 3건, 트레이스 헤더 누락 0건** 입니다. 셋 다 첫 반복의 콜드
회차이고 소요가 120초 상한에 붙어 있습니다.

**서버는 끝까지 처리했습니다.** 컨테이너 세그먼트 로그는 96건이 모두 남았고 그중
`sql_ms` 최대가 166,625ms 입니다. 따라서 실패 3건의 실제 소요는 120초가 아니라
**그보다 큰 미지의 값**입니다. 클라이언트가 처리 중인 요청을 끊었을 뿐입니다.

이 세 문항은 2026-08-30 GPT 보고서가 느린 문항으로 지목한 `q03·q08·q25·q31` 과
겹칩니다. 별개 관찰이 같은 대상을 가리켰습니다.

### 3.2 이 판정은 선행 하네스로는 불가능했습니다

종전 하네스는 실패 시 정수 카운터만 남기고 예외와 소요 시간과 문항을 버렸습니다.
2026-09-06 측정이 "8회 중 2회 HTTP 실패" 로만 기록돼 원인을 판정할 수 없었던 이유가
이것입니다. 2026-09-07 커밋 `6f6ab0a` 가 실패 회차별 사유·소요·문항 기록과 사유
분리 집계를 넣은 뒤 첫 실행에서 곧바로 원인이 나왔습니다.

## 4. 콜드 지연은 소수 문항 현상입니다

`sql_ms` 구간 분포입니다.

| 구간 | n | P50 | P95 | P99 | max |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전체 | 96 | 14.5ms | 1,316.2ms | 157,940.9ms | 166,625.2ms |
| 콜드 | 29 | 19.6ms | 1,465.9ms | 78,751.1ms | 108,739.9ms |
| 웜 | 64 | 13.1ms | 34.2ms | 64.6ms | 100.7ms |

**콜드 P50 이 19.6ms 입니다.** 콜드 요청 대부분은 웜과 차이가 없고 P95 를 넘어서면서
수만 ms 로 튑니다.

종전 관찰치 "콜드 `sql_ms` P50 86,539ms" 는 **콜드 표본이 2건뿐이라 그 소수 문항에
표본이 쏠린 결과**입니다. 이번 29건 표본은 같은 지표를 전혀 다르게 규정합니다.
개선이 일어난 것이 아니라 종전 수치의 대표성이 없었던 것입니다.

**이 문서는 콜드 SQL 총량을 게이트로 되돌리자고 제안하지 않습니다.** 2026-09-01
결정대로 관찰 지표로 유지합니다. 다만 최적화 대상이 "콜드 전반" 이 아니라 특정
문항의 쿼리 형태라는 점이 이번에 좁혀졌습니다.

## 6. 3차 측정: 버퍼풀 가설의 반증

버퍼풀을 실제로 비우고 같은 조건으로 다시 측정했습니다.

### 6.1 콜드 조건을 어떻게 만들었는지

**단순 재기동으로는 콜드가 되지 않습니다.** InnoDB 는 기본값이
`innodb_buffer_pool_dump_at_shutdown=ON`, `innodb_buffer_pool_load_at_startup=ON`
이라 종료 시 적재 페이지 목록을 `ib_buffer_pool` 로 덤프하고 기동 시 되읽습니다.
실제로 2026-09-06 자 덤프 파일 302KB 가 볼륨에 남아 있었습니다.

세 단계로 처리했습니다.

1. `SET GLOBAL innodb_buffer_pool_dump_at_shutdown = OFF`
2. `docker compose stop db` 후 볼륨의 `ib_buffer_pool` 제거
3. `docker compose start db`

| 시점 | `Innodb_buffer_pool_pages_data` |
| --- | ---: |
| 재기동 전 | 121,120 |
| 재기동 후 | **1,192** |
| 측정 종료 시점 | 1,383 |

버퍼풀 크기는 2GB 이며 데이터는 건드리지 않았습니다. `ib_buffer_pool` 은 페이지 ID
목록일 뿐입니다. 측정 후 `dump_at_shutdown` 은 `ON` 으로 되돌렸습니다.

### 6.2 결과: 콜드 버퍼풀에서 가장 빨랐습니다

| 구간 | 1차 (웜풀) | 2차 (웜풀) | **3차 (콜드풀)** |
| --- | ---: | ---: | ---: |
| 콜드 `sql_ms` P50 | 19.6ms | 12.9ms | **11.9ms** |
| 콜드 `sql_ms` P99 | 78,751.1ms | 240.6ms | **63.7ms** |
| 콜드 `sql_ms` max | 108,739.9ms | 320.3ms | **69.3ms** |
| 실패 | 3건(타임아웃) | 0건 | **0건** |
| 판정 | `partial` | `canonical` | **`canonical`** |

문항별 콜드 `sql_ms` 최댓값입니다.

| 실행 | q03 | q08 | q25 | q31 |
| --- | ---: | ---: | ---: | ---: |
| 1차 (웜풀) | 타임아웃 | 108,739.9ms | 타임아웃 | 타임아웃 |
| 2차 (웜풀) | 21.6ms | 12.7ms | 320.3ms | 12.6ms |
| **3차 (콜드풀)** | **18.2ms** | **26.6ms** | **69.3ms** | **9.3ms** |

**버퍼풀을 비운 실행이 세 번 중 가장 빠릅니다.** 따라서 1차의 10만 ms 대 값은
InnoDB 버퍼풀 콜드로 설명되지 않습니다.

### 6.3 1차의 원인은 아직 규명되지 않았습니다

세 실행은 같은 fixture, 같은 모델, 같은 반복 횟수이고 코드 차이도 측정 대상 경로에
없습니다. 남는 차이는 **1차가 Docker 스택 전체 기동 11분 뒤 첫 실행**이었다는 것뿐
입니다. 그 시점에 동시에 진행됐을 수 있는 것은 호스트·VM 파일시스템 캐시 미적재,
다른 컨테이너의 초기화 I/O, 버퍼풀 덤프 파일 로드 등입니다.

**그중 무엇인지는 측정하지 않았으므로 단정하지 않습니다.** 확정된 것은 둘입니다.

- InnoDB 버퍼풀 상태는 원인이 **아닙니다** (3차가 반증)
- 1차 조건은 아직 재현 방법이 없습니다

이는 콜드 SQL 총량을 2026-09-01 에 게이트에서 관찰 지표로 강등한 결정을 뒷받침
합니다. **아무도 분리하지 못한 환경 요인이 지표를 지배합니다.**

## 7. 다음 측정의 조건

정본은 3차(`rag_segments_coldpool_20260907.json`)를 씁니다. 같은 게이트를 통과하면서
버퍼풀 상태까지 검증된 유일한 산출물입니다. 2차와 1차도 조건이 다른 측정이므로 함께
보존합니다.

**`--timeout-sec` 기본값 120초는 그대로 둡니다.** 재현 가능한 두 조건(웜풀·콜드풀)
에서 `sql_ms` 최댓값이 각각 320.3ms 와 69.3ms 이므로 120초가 부족하다는 근거가
없습니다. 1차에서만 부족했고 그 조건은 재현 방법이 없습니다. **재현하지 못하는 한
번의 관측으로 기본값을 바꾸면 근거 없는 숫자만 남습니다.**

남은 과제는 둘입니다.

1. **하네스가 버퍼풀 상태를 provenance 에 기록**하게 합니다. 지금은 같은 게이트를
   통과한 산출물끼리 조건을 구분할 수 없어, 이번처럼 사람이 컨테이너를 직접 조회해야
   합니다. `Innodb_buffer_pool_pages_data` 한 줄이면 충분합니다.
2. 1차 조건의 재현 방법을 찾을지 판단합니다. 스택 전체를 내렸다 올린 직후 측정하는
   절차를 추가하면 재현될 수 있으나, 그 지표는 이미 게이트가 아니므로 **우선순위는
   낮습니다.**
