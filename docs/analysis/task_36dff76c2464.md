## 1. 문제

워커가 `.orca/` 같은 gitignore 대상 경로를 `git add -f` 로 강제 커밋해도
Level 1 게이트가 실패하지 않았습니다.
원인은 두 가지입니다.

| 위치 | 동작 | 결과 |
| --- | --- | --- |
| 게이트 1 (`run_gate1_changed_files`) | 변경 목록을 수집해 보고만 하고 status 를 항상 `pass` 로 둡니다 | 판정 기능 없음 |
| 게이트 2 (`run_gate2_scope`) | Capsule 의 `allowed_write_files` 만 봅니다. 리뷰 Capsule 은 `review_done.json` 을 허용 쓰기로 두므로 gitignore 대상이어도 통과시킵니다 | 이 결함을 잡을 수 없음 |

## 2. 설계 선택

### 2.1 새 검사의 위치: 게이트 7 (맨 끝 추가)

기존 게이트의 번호·이름·판정을 바꾸지 않고, 기존 순서 중간에 끼워 넣어
번호를 밀지 않기 위해 맨 끝에 `게이트 7 gitignore 검증` 을 추가했습니다.
선택 근거는 다음과 같습니다.

- 게이트 1 에 실패 조건을 넣으면 게이트 1 의 판정(항상 pass)이 바뀌므로 계약 위반입니다.
- 게이트 2 에 합치면 게이트 2 의 판정 로직이 바뀌고, Capsule 범위 위반과
  gitignore 위반이라는 서로 다른 근거가 한 게이트에 섞입니다.
- 중간에 `1b` 등으로 끼우면 `build_json_output` 의 인덱스 대응이 밀려
  뒤 게이트가 잘못된 키로 보고되는 결함이 생깁니다.
  (기존 테스트가 이 키-게이트 정렬을 명시적으로 검사합니다.)
- 맨 끝 추가는 기존 키 대응을 그대로 두고 새 키(`gate7_gitignored`)만
  덧붙이므로 안전합니다.

`build_json_output` 은 인덱스 대응에서 이름 대응으로 바꾸었습니다.
게이트 6 이 생략되는 호출에서 7번째 결과가 `gate6_worker_done` 키로
잘못 보고되던 정렬 문제를 함께 해소하며, 기존 키 이름은 그대로입니다.

### 2.2 판정 근거: `git check-ignore --no-index`

- 경로 패턴을 스크립트에 하드코딩하지 않았습니다.
  `.gitignore` 가 바뀌면 검사도 따라 바뀝니다.
- 검사 대상은 게이트 1 이 구한 `base..branch` 변경 파일 목록뿐입니다.
  작업 트리의 미커밋·미추적 파일은 목록에 없으므로 검사하지 않습니다.
- 종료 코드 규약: `0` 은 무시 대상 있음(위반),
  `1` 은 무시 대상 없음(정상), 그 밖은 도구 오류(`GateToolError` → 종료 코드 2)입니다.
  종료 코드 1 을 오류로 처리하면 정상 브랜치가 전부 실패하므로 구분합니다.
- `--no-index` 가 필요한 이유: 검사 대상은 이미 커밋되어 추적 중인 파일이며,
  기본 `git check-ignore` 는 추적 파일을 보고하지 않고 종료 코드 1 을 냅니다.
  실측으로 확인했으므로 규칙 순수 매칭을 위해 인덱스를 보지 않습니다.
- 위반이 하나라도 있으면 `fail` 이고 위반 경로를 전부 나열합니다. 경고로 낮추지 않습니다.

### 2.3 최종 판정·종료 코드 규약 유지

기존 집계(`pass`/`fail` 건수, `strict` 시 필수 건너뜀 차단)와
종료 코드 규약(0 통과, 1 게이트 실패, 2 도구 오류)을 그대로 유지합니다.
게이트 7 은 일반 게이트로 집계에 포함됩니다.
