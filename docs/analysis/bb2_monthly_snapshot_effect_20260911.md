## 1. 결론

**캐시 미적중 종단이 505ms 에서 4.9ms 가 됐습니다.** 최초 기준선 3,725ms 대비
**760배** 입니다.

| 단계 | 정상상태 wall P50 | 범위 | 산포 |
| --- | ---: | --- | ---: |
| 최초 기준선 (AZ3) | 3,724.8ms | 3,672~4,182 | 510ms |
| 무거운 두 집계 전환 (BA2) | 505.0ms | 492~509 | 18ms |
| **월별 두 집계 전환 (BB2)** | **4.9ms** | **4.8~6.3** | **1.6ms** |

유효 표본 12/12 이며 가열 2회차(61.5ms, 9.2ms)를 정상상태에서 제외했습니다.

**구조 차이는 확정입니다.** 네 집계 구간이 모두 **0.00ms** 입니다. 절대 시간 차이는
판정 규칙상 산포 초과(참고)이며, 범위가 전혀 겹치지 않습니다(492~509 대 4.8~6.3).

## 2. 남은 5ms 의 구성

| 구간 | P50 | 비중 |
| --- | ---: | ---: |
| `announcement_summary` | 1.10ms | 37.2% |
| `result_summary` | 0.47ms | 16.0% |
| `cache_lookup` | 0.14ms | 4.8% |
| `cache_store` | 0.12ms | 4.1% |
| `announce_by_month` | **0.00ms** | 0.0% |
| `result_by_month` | **0.00ms** | 0.0% |
| `agency_announce_top10` | **0.00ms** | 0.0% |
| `matched_count` | **0.00ms** | 0.0% |
| `residual_ms` | 1.75ms | - |

`cursor_ms` 는 1.19ms 이고 `cursor_count` 는 여전히 **8** 입니다. 무거운 집계
네 건이 스냅샷 기본키 조회로 바뀐 것이지 질의 수가 준 것이 아닙니다.

**이 경로의 최적화는 여기서 종료합니다.** 남은 것은 요약 조회 두 건과 캐시
연산뿐이고 합계가 2ms 미만입니다. 같은 서비스의 `GET /api/v1/bids/stats` 웜
레이턴시가 3.34ms 인 것과 같은 수준이며, 더 줄일 대상이 없습니다.

## 3. 값 동등성은 운영 MySQL 에서 확인했습니다

독립 검토는 호출 경로 재사용으로 판정했고, 런타임 확인은 코디네이터 몫으로
남았습니다. 같은 DB 에서 두 경로를 직접 돌려 대조했습니다.

| 스냅샷 | 결과 |
| --- | --- |
| `announce_by_month` | 실시간과 **13행 완전 일치** |
| `result_by_month` | 실시간과 **13행 완전 일치** |

월 버킷 산출이 `_build_monthly_counts` 재사용이라 방언이 갈라지지 않는다는
검토 판정이 실측으로 뒷받침됐습니다.
