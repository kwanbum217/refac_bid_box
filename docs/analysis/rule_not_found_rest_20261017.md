## 2. 측정 방법

### 2.1 정본 명령과 재수집

판정 집계는 서비스 판정 함수(`classify_contract_regime`, `institution_sido`, `resolve_evaluation_rule_from_raw_data`)를 그대로 쓰는 정본 스크립트로만 했다.

```sh
uv run python scripts/report_rule_coverage.py --months 12 --category Servc \
  --method-code 낙030001 --min-announcements 1 \
  --output .cache/task_rule_not_found_rest_20261017.yaml
```

- 실행일 2026-10-17, 원장 `filter` 의 window_from/window_to(2025-10-17 ~ 2026-10-17)와 일치한다.
- 원장에 남지 않는 값(낙찰방법명 `sucsfbidMthdNm`, 공고일 `bidNtceDt`, 교육 계열 여부)은 같은 스크립트의 `collect_records` 를 같은 인자로 import 해 재수집했다(`scripts/report_rule_coverage.py:404-458`). 재수집은 원본 `_to_record`(`scripts/report_rule_coverage.py:372-401`)가 만든 레코드에 관측 필드만 덧붙였고, 판정 함수 호출은 바꾸지 않았다.
- RULE_NOT_FOUND 선별은 원장과 같은 분류 함수 `classify_result`(`scripts/report_rule_coverage.py:143-167`)로 `applied_scope == BLOCKED` 이고 `block_code == RULE_NOT_FOUND` 인 레코드만 골랐다.
- 총계 검산: 기관 항목 RULE_NOT_FOUND 합 536건이며 `--min-announcements 1` 이라 tail 이 없다(`tail.institutions == 0`).
- 536건의 차단 사유 메시지는 17종이며 모두 "공고의 낙찰방법('…')에서 일치하는 일반용역 적격심사 별표를 찾을 수 없습니다" 형태다. 즉 전부 별표 이름 매칭 실패(`src/app/services/evaluation_rules.py:7024-7034`) 경로이고, 축 재선택 실패(`src/app/services/evaluation_rules.py:6602-6613`)나 `공고서참조` 코드 경로는 섞여 있지 않다(`method_source` 는 536건 모두 `ANNOUNCEMENT`, `scope_stage` 는 모두 없음).

## 7. 해석과 후속 후보

- 갈래 2(470건)는 기관 자체 별표가 없는 기관이 대부분이고, 표기 자체가 현행 별표에 없는 경우(임대차·수리ㆍ점검·수요기관 지정형·기타용역·일반 띠 일부)가 섞여 있다. 기관 규칙 등록과 조달청 별표 식별 문자열 보완이 각각 다른 몫을 담당한다.
- 갈래 1(30건)과 갈래 3(36건) 합 66건은 기관 축이 이미 추적 중이거나(갈래 3) 정책상 조달청 기준으로 푸는(갈래 1) 공고라, 남은 문제는 조달청 별표 식별 문자열 커버리지다.
- 상위 5개 표기 438건(81.7%)이 임대차·수리ㆍ점검·수요기관 지정형·추정가격 띠에 몰려 있어, 이 계열의 별표 식별 문자열을 보완하면 잔여 차단의 대부분이 줄어든다. 다만 이 문서는 갈래 분해까지이며 규칙 등록과 코드 수정은 하지 않는다.

## 8. 출처와 범위

- 수치 출처는 DB `bid_announcements` 의 공고 원문(`sucsfbidMthdNm`, `bidNtceDt`, `dminsttCd`), 서비스 판정 함수, 발행 원장, 코드에 선언된 조달청 별표 식별 문자열이다.
- 상업 페이지(bidpro, 비드큐, info21c, 모두입찰 등)와 외부 원문은 쓰지 않았다. 내려받은 원문도 없다.
- 하지 않은 것: 규칙 등록, 코드·규칙·원장·`docs/context/CURRENT_STATE.md` 수정, DB 쓰기, 스키마·데이터 변경.
- 측정용 스크립트와 중간 산출물은 `.cache/` 아래에만 두었고 커밋하지 않는다.
