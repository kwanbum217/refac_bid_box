## 1. 배경 및 실측 현황

2026-08-22 블로킹 I/O 오프로드 후 종단 간 실측에서 낙찰가 예측 API(`concurrency=10`, `rounds=100`)는 다음과 같은 레이턴시 분포를 보였습니다.

| 회차 | 상태 | P50 (ms) | P95 (ms) | P99 (ms) | 평균 (ms) | 목표(100ms) 판정 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **1회차** | 콜드스타트 | 45.1 | 383.1 | 383.7 | 77.0 | **미달** |
| **2회차** | 전이(Warmup) | 40.5 | 122.1 | 123.4 | 46.3 | **미달** |
| **3회차** | 웜(Warm) | 44.5 | 78.6 | 81.6 | 45.8 | **달성** |
| **4회차** | 웜(Warm) | 42.3 | 83.6 | 89.0 | 44.1 | **달성** |
| **5회차** | 웜(Warm) | 40.6 | 69.0 | 72.2 | 43.8 | **달성** |
| **6회차** | 웜(Warm) | 41.0 | 61.9 | 62.8 | 43.2 | **달성** |

### 1.1 주요 실측 사실 (Ground Truth)
1. **종단 간(End-to-End) 지표만 존재**: 실측 데이터는 클라이언트 관점의 회차별 P50/P95/P99 및 평균값뿐이며, DB 연결/스레드 생성/전처리/ML 추론 등 구간별 세부 계측 데이터는 존재하지 않습니다.
2. **소수 요청의 꼬리 형성**: 6개 전 회차에서 P50은 40.5ms ~ 45.1ms 로 일정합니다. 1회차 P95(383.1ms)와 P99(383.7ms)가 거의 일치하며, 동시성 10(c=10) 조건에서 첫 10개 동시 요청 배치가 콜드 경로를 통과하면서 발생한 꼬리 지연입니다.
3. **단계별 기여도 미확정**: 첫 10건 배치가 콜드 경로를 통과했다는 조건은 알 수 있으나, 어느 단계가 383.1ms 중 얼마를 기여했는지는 실측 데이터만으로 확정할 수 없습니다.
4. **웜 상태 수렴**: 3~6회차의 P95는 61.9ms ~ 83.6ms 로 4회 연속 목표(100ms)를 충족했습니다.

## 2. 코드 레벨 첫 호출 지연 후보 분석 (코드상 후보)

코드 정적 분석을 통해 첫 호출 시점에 추가 비용이 발생할 수 있는 후보 지점을 식별했습니다. 단, 코드상 지연 가능성과 실측 383.1ms의 인과관계 및 세부 기여도는 별도 계측 없이는 확정할 수 없으므로 '후보'로 기술합니다.

```
[클라이언트 요청] (c=10 동시 진입)
       │
       ▼
[FastAPI / AnyIO 스레드 풀] ── (후보 2) 워커 스레드 풀 지연 기동 가능성 (추정)
       │
       ▼
[Depends(get_db)] ─────────── (후보 1) SQLAlchemy QueuePool 커넥션 지연 생성 및 DB 핸드셰이크 (추정)
       │
       ▼
[features.py / pandas] ────── (후보 5) 전처리 내부 캐시/초기화 지연 가능성 (추정)
       │
       ▼
[ModelRegistry / ML Model] ── (후보 3) ML 라이브러리 C-Extension 진입 및 내부 버퍼 초기화 (추정)
```

### 2.1 후보 1: SQLAlchemy DB 커넥션 풀 지연 생성 (코드 확인: 지연 풀링 메커니즘 / 실측 기여도: 미확정)
- **코드 위치**: `src/app/core/db.py:18-25`, `src/app/api/v1/predictions.py:74, 85, 139`
- **코드상 확인 사실**:
  - `src/app/core/db.py`의 `create_engine`은 `pool_size=10, max_overflow=20`으로 선언되어 있으나, SQLAlchemy `QueuePool`은 기본적으로 요청 시점에 실제 커넥션을 맺는 지연(Lazy) 방식으로 동작합니다.
  - 앱 기동 시점에는 MySQL 커넥션이 사전 생성되지 않으며, `predict-price` 요청이 `get_db()` 세션을 통해 `db.get(BidAnnouncement, ...)` 또는 DB 조회를 수행할 때 첫 커넥션이 생성됩니다.
- **추정 및 미확정 영역**:
  - 동시성 10 요청이 첫 순간 진입할 때 10개 커넥션 생성(TCP 3-way 핸드셰이크 및 MySQL 인증)이 동시에 발생했을 가능성이 있으나, 383.1ms 중 DB 커넥션 생성 지연이 차지하는 실제 시간은 단계별 계측이 없어 미확정입니다.
- **반복 여부**: 커넥션 풀 메커니즘상 첫 연결 확보 이후에는 `db.close()` 시 풀로 반환되어 재사용되므로, 후속 요청에서는 연결 생성 비용이 반복되지 않는 구조입니다.

### 2.2 후보 2: AnyIO / Starlette 동기 라우트 스레드 풀 지연 기동 (코드 확인: 동기 def 선언 / 실측 기여도: 미확정)
- **코드 위치**: `src/app/api/v1/predictions.py:71, 240`
- **코드상 확인 사실**:
  - `predict_price_api`와 `predict_winning_price`는 동기 `def` 함수로 선언되어 있습니다.
  - FastAPI는 동기 함수를 AnyIO의 워커 스레드 풀(`anyio.to_thread.run_sync`)에 위임하여 실행합니다.
- **추정 및 미확정 영역**:
  - 스레드 풀이 워커 스레드를 요청 시점에 필요에 따라 지연 생성할 경우 스레드 생성 및 스케줄링 비용이 첫 진입 시 발생할 수 있으나, 실제 생성된 스레드 수와 지연 기여도는 미확정입니다.
- **반복 여부**: 풀에 생성된 스레드는 이후 요청에 재사용되므로 첫 기동 이후에는 생성 비용이 발생하지 않는 구조입니다.

### 2.3 후보 3: ML 추론 라이브러리 C-Extension 진입 및 런타임 웜업 (코드 확인: 역직렬화와 첫 추론 분리 / 실측 기여도: 미확정)
- **코드 위치**: `src/ml/model_registry.py:75-98`, `src/ml/predictor.py:170-176`
- **코드상 확인 사실**:
  - `ModelRegistry.load_all_models()`는 `joblib.load()`를 통해 Python 모델 객체를 역직렬화합니다.
  - 역직렬화 시점과 실제 `estimator.predict(X)` 데이터가 C-Extension 인터페이스를 통과하는 시점은 분리되어 있습니다.
- **추정 및 미확정 영역**:
  - LightGBM / CatBoost / scikit-learn 하부 C 라이브러리의 내부 메모리 버퍼 할당 및 런타임 초기화가 첫 추론 시 1회 발생할 가능성이 있으나, 라이브러리 내부 세부 구현 및 실측 기여도는 별도 프로파일링 없이는 단정할 수 없습니다.
- **반복 여부**: 첫 추론 런타임 진입 이후에는 추론 연산 자체(P50 ~42ms)만 반복되는 구조입니다.

### 2.4 후보 4: FastAPI Lifespan 백그라운드 태스크 미대기 구조 (코드 확인: create_task 후 즉시 yield / 실측 기여도: 미확정)
- **코드 위치**: `src/app/main.py:46-81`
- **코드상 확인 사실**:
  - `lifespan` 함수 내에서 `_warm_predictor()`와 `_warm_llm_backend()`를 `asyncio.create_task`로 던진 뒤 완료를 기다리지 않고 `yield`로 제어를 넘깁니다.
  - Uvicorn은 `yield` 도달 즉시 소켓을 열고 외부 HTTP 트래픽 수신을 시작합니다.
- **추정 및 미확정 영역**:
  - 백그라운드 태스크가 `load_all_models`를 마치기 전에 첫 요청 배치가 진입할 경우, 요청 처리 스레드에서 모델 지연 로딩이 직접 발생하거나 락 경합이 발생할 수 있는 구조입니다. 그러나 실측 당시 벤치마크 스크립트 실행 타이밍과 모델 로드 완료 시점의 선후 관계는 로그 계측이 없어 383.1ms 유발 여부를 확정할 수 없습니다.
- **반복 여부**: 서버 기동 직후 초기 유입 타이밍에만 국한되는 구조적 요인입니다.

### 2.5 후보 5: Pandas / Numpy 전처리 내부 초기화 및 캐싱 (코드 확인: 전처리 함수 호출 / 실측 기여도: 미확정)
- **코드 위치**: `src/ml/features.py`, `src/ml/model_registry.py:154-166, 181-198`
- **코드상 확인 사실**:
  - `prepare_full_frame`, `prepare_input_frame`, `apply_categorical_dtypes` 등의 전처리 함수가 호출됩니다.
- **추정 및 미확정 영역**:
  - Pandas `CategoricalDtype` 내부 캐시 및 메모리 블록 구성이 첫 실행 시 초기화될 가능성이 있으나 오버헤드 크기는 미확정입니다.
- **반복 여부**: 첫 호출 이후 재사용 가능성이 높습니다.

### 2.6 후보 6: 마이크로배치 창 및 GC 모드 (반복 비용 또는 지연 요인 배제)
- **코드 위치**: `src/ml/predictor.py:62, 175-176`
- **코드상 확인 사실**:
  - `_PredictionBatcher.BATCH_WINDOW_SECONDS = 0.005` (5ms) 대기 창은 웜 상태에서도 동일하게 동작하므로 383.1ms 꼬리 지연의 차별적 원인이 아닙니다 (반복 비용).
  - `PREDICTION_GC_MODE=freeze`가 적용되어 로드된 모델 객체는 gen2 순회에서 배제됩니다.

## 4. 가설 검증 우선순위 및 기동 시 워밍업 설계 방안

### 4.1 단계별 세부 계측 및 가설 검증 우선순위
콜드스타트 383.1ms의 각 단계별 기여도가 미확정이므로, 임의의 워밍업 코드를 바로 적용하기 전에 구간별 소요 시간을 정밀 계측하여 실제 병목 구간을 검증하는 것이 선행되어야 합니다.

1. **1단계: Lifespan 기동 타이밍 계측**:
   - `_warm_predictor()`의 `load_all_models()` 완료 시점과 Uvicorn 트래픽 수신 시작 시점의 타임스탬프를 비교하여 모델 로드 전 요청 유입 여부 확인.
2. **2단계: DB 커넥션 풀 연결 시간 계측**:
   - 첫 요청 시점의 `get_db()` 세션 획득 및 첫 쿼리(`db.get`) 소요 시간을 로깅하여 DB 핸드셰이크가 차지하는 시간(ms) 실측.
3. **3단계: AnyIO 스레드 풀 기동 및 디스패치 지연 계측**:
   - 동기 라우트 진입부터 실제 함수 실행 시작까지의 디스패치 오버헤드 계측.
4. **4단계: ML 모델 첫 추론 전후 소요 시간 계측**:
   - `features.py` 전처리 시간과 `model.predict()` 첫 호출의 순수 연산 시간을 분리 계측하여 C-Extension 초기화 비용 실측.

### 4.2 기동 시 워밍업 설계 방안 (검증 후 채택 시의 설계안)
가설 검증을 통해 특정 구간의 초기화 비용이 유의미한 병목으로 입증될 경우, 다음과 같은 단계로 워밍업을 구성할 수 있습니다. (설계안이며 현재 구현하지 않고 결정을 유보합니다.)

#### (1) 진입점: FastAPI Lifespan (`src/app/main.py`)
현재의 `asyncio.create_task` 기반 백그라운드 실행을 `await` 기반 동기 완료 대기 구조로 전환하여, 워밍업 완료 후에만 `yield`(트래픽 수신 시작)가 실행되도록 합니다.

```python
# (설계 예시 - 미구현)
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 1. 모델 역직렬화 완료 대기 (ModelRegistry.load_all_models)
    # 2. ML 추론 런타임 웜업 (대표 카테고리 Thng/Servc 더미 데이터 1회 predict 실행)
    # 3. DB 커넥션 풀 사전 연결 (DB ping 및 기본 풀 커넥션 사전 확보)
    # 4. LLM 백엔드 웜업 (옵션)
    await run_startup_warmup()
    try:
        yield
    finally:
        await run_shutdown_cleanup()
```

#### (2) 단계별 워밍업 대상
1. **모델 역직렬화 및 등록 대기**: `ModelRegistry.load_all_models()`를 `await`로 완전히 완료한 후 `gc.freeze()` 적용.
2. **더미 추론 (Dummy Inference)**:
   - `Thng` 카테고리(물품 모델) 및 `Servc` 카테고리(용역 모델)에 대해 더미 특징 딕셔너리로 `predict_optimal_price_with_provenance` 및 `predict_interval` 1회 실행.
   - 기대 효과: 전처리 모듈 및 C 라이브러리 메모리 할당, `_PredictionBatcher` 큐 및 워커 스레드 사전 활성화.
3. **DB 커넥션 풀 사전 연결**:
   - `engine.connect()`를 통해 간단한 쿼리(`SELECT 1`)를 풀 크기(`pool_size=10`)만큼 사전에 실행하여 TCP 커넥션을 미리 확보.
   - 기대 효과: 첫 요청 배치 진입 시의 DB 핸드셰이크 지연 완화.

## 5. 워밍업 도입의 위험 및 운영상 트레이드오프

워밍업을 도입할 경우 발생할 수 있는 위험과 운영상의 주의점입니다.

### 5.1 기동 시간(Boot Time) 증가
- 모델 역직렬화, 더미 추론, DB 커넥션 핸드셰이크, LLM 예열까지 동기 대기할 경우 서버 기동 시간이 수 초에서 길게는 10~20초 이상 증가할 수 있습니다.
- CI/CD 테스트 파이프라인이나 로컬 개발 환경에서 빠른 서버 재기동이 방해받을 수 있습니다.

### 5.2 헬스체크 타이밍 충돌 및 컨테이너 재시작 루프 (CrashLoopBackOff)
- Docker compose의 `healthcheck` 또는 Kubernetes의 `livenessProbe` / `readinessProbe`가 워밍업 완료 전에 `/api/v1/health`를 호출할 수 있습니다.
- Lifespan이 완료되기 전까지 Uvicorn이 포트를 열지 않거나 헬스체크 응답을 주지 못하면, 오케스트레이터가 컨테이너를 비정상 상태(Unhealthy)로 판정하고 강제 kill 후 재시작하는 무한 루프(CrashLoop)에 빠질 위험이 있습니다.
- **대응 필요 조건**: 오케스트레이터의 `start_period` / `initialDelaySeconds`를 워밍업 최대 소요 시간보다 충분히 길게 설정해야 합니다.

### 5.3 실패 처리 정책 (Fail-Fast vs Fail-Open)
- 워밍업 도중 DB 일시 지연, 모델 가중치 파일 일부 결함 등이 발생했을 때:
  - **Fail-Fast (예외 발생 시 기동 중단)**: 불완전한 상태의 서버가 배포되는 것을 막을 수 있으나, 일시적인 네트워크 순단에도 전체 서버 배포가 실패합니다.
  - **Fail-Open (경고 로그 후 기동 지속)**: 서버 기동은 보장되나, 워밍업되지 않은 상태로 트래픽을 수신하여 콜드스타트 지연이 재현됩니다.

### 5.4 기동 순간 자원 스파이크 (Resource Burst)
- 기동 시점에 DB 연결을 일시에 맺고 ML 모델 추론을 수행하면, 컨테이너 기동 순간의 CPU, 메모리, DB 커넥션 사용량이 급증하여 동일 호스트의 다른 서비스에 일시적인 부하를 줄 수 있습니다.

## 6. 요약 및 권고

1. **실측 현황**: 낙찰가 예측 API 실측에서 1회차 콜드스타트 P95(383.1ms) 미달이 발생했으나, 3~6회차 웜 상태에서는 61.9ms ~ 83.6ms 로 목표(100ms)를 연속 충족했습니다.
2. **원인 기여도 미확정**: 코드상 지연 후보로 (1) DB 커넥션 풀 지연 생성, (2) AnyIO 스레드 풀 지연 기동, (3) ML C-Extension 첫 추론 웜업, (4) Lifespan 백그라운드 태스크 미대기가 식별되었으나, 단계별 세부 계측 데이터가 부재하여 각 후보의 실제 383.1ms 기여도는 미확정 상태입니다.
3. **계측 선행 및 결정 유보**: 워밍업 도입은 기동 시간 증가 및 헬스체크 타임아웃(CrashLoopBackOff) 등의 운영 위험을 동반합니다. 따라서 코드 수정을 즉시 진행하지 않고, 향후 단계별 계측을 통한 가설 검증을 선행한 뒤 서비스 안정성 요구사항에 따라 채택 여부를 결정하도록 유보합니다.
