> **원시 데이터**: `data/benchmarks/blocking_io_p95/run1.json`, `run2.json`, `run3.json`
> **대상 커밋**: `e219d9cc537e9d88b6720a62d345e97c65ded9e5`
> **환경**: macOS (arm64), Python 3.12.14, Docker 5개 컨테이너 가동 (FastAPI, MySQL 8, Redis 7 등 healthy)

## 1. 개요 및 측정 목적

`src/tasks/`, `src/app/api/`, `src/rag/` 등 12건의 블로킹 I/O 구간을 `asyncio.to_thread` 로 오프로드한 이후, 실제 기동 중인 FastAPI HTTP 서버(`http://127.0.0.1:8000`)에 대한 종단 간(End-to-End) 레이턴시를 3회 독립 측정하여 현재의 성능 기준선(Baseline)을 확정하고 목표 달성 여부를 검증합니다.

### 1.1 측정 제약 사항 (중요)

- **비교 대상 부재에 따른 개선폭 기재 금지**: `to_thread` 오프로드 수정 이전의 동일 조건 실측 데이터가 존재하지 않으므로, 이전 상태 대비 "몇 % 개선" 또는 "성능 향상폭"과 같은 주장은 일절 기술하지 않습니다. 본 문서는 순수하게 현재 상태의 실측치와 설계 목표 대비 달성 여부만을 기록합니다.
- **측정 도구 및 절차**: 정본 측정 도구인 `scripts/benchmark_latency.py`를 사용하여 30초 이상의 휴지기를 두고 3회 독립 실행하였으며, 각 회차의 P50, P95, P99 및 회차 간 편차를 분석합니다.

### 3.2 상세 통계 (P50 / P95 / P99 / 평균)

#### (1) 정본 SSE 첫 토큰 (`first_token_ms`, 목표 P95 <= 3,000ms)
- **1회차**: P50 = 1,228.2ms (1.23s) / P95 = 2,290.9ms (2.29s) / P99 = 6,467.7ms (6.47s) / 평균 = 1,476.5ms / 오류 = 0건
- **2회차**: P50 = 1,110.0ms (1.11s) / P95 = 1,273.9ms (1.27s) / P99 = 1,318.6ms (1.32s) / 평균 = 997.3ms / 오류 = 0건
- **3회차**: P50 = 772.2ms (0.77s) / P95 = 1,263.4ms (1.26s) / P99 = 1,543.2ms (1.54s) / 평균 = 752.8ms / 오류 = 0건
- **회차 간 편차**: P95 기준 최저 1,263.4ms ~ 최고 2,290.9ms (편차 1,027.5ms). 1회차 초기 콜드스타트 영향 이후 2~3회차에서 1,260~1,270ms 대로 안정화. 전 회차 목표(3,000ms) 충족.

#### (2) 정본 SSE 전체 완료 (`final_ms`, 목표 P95 <= 20,000ms)
- **1회차**: P50 = 4,419.7ms (4.42s) / P95 = 7,654.5ms (7.65s) / P99 = 9,373.0ms (9.37s) / 평균 = 4,546.0ms / 오류 = 0건
- **2회차**: P50 = 4,261.3ms (4.26s) / P95 = 6,365.9ms (6.37s) / P99 = 6,928.3ms (6.93s) / 평균 = 4,068.8ms / 오류 = 0건
- **3회차**: P50 = 3,641.2ms (3.64s) / P95 = 7,194.0ms (7.19s) / P99 = 8,735.0ms (8.73s) / 평균 = 3,598.7ms / 오류 = 0건
- **회차 간 편차**: P95 기준 최저 6,365.9ms ~ 최고 7,654.5ms (편차 1,288.6ms). 전 회차 목표(20,000ms) 여유 있게 충족.

#### (3) 정본 SSE 첫 stage (`first_stage_ms`, 참고값)
- **1회차**: P50 = 3.0ms / P95 = 10.9ms / P99 = 15.8ms / 평균 = 4.4ms / 오류 = 0건
- **2회차**: P50 = 2.2ms / P95 = 11.0ms / P99 = 12.5ms / 평균 = 3.5ms / 오류 = 0건
- **3회차**: P50 = 2.1ms / P95 = 3.4ms / P99 = 5.6ms / 평균 = 2.4ms / 오류 = 0건
- **회차 간 편차**: P95 기준 최저 3.4ms ~ 최고 11.0ms (편차 7.6ms). 이벤트 루프 진입 즉시 첫 stage 이벤트가 전송됨을 확인.

#### (4) 낙찰가 예측 API (`predict`, 목표 P95 <= 100.0ms, concurrency=10, rounds=100)
- **1회차**: P50 = 45.1ms / P95 = 383.1ms / P99 = 383.7ms / 평균 = 77.0ms / 오류 = 0건 (목표 미달)
- **2회차**: P50 = 40.5ms / P95 = 122.1ms / P99 = 123.4ms / 평균 = 46.3ms / 오류 = 0건 (목표 미달)
- **3회차**: P50 = 44.5ms / P95 = 78.6ms / P99 = 81.6ms / 평균 = 45.8ms / 오류 = 0건 (목표 달성)
- **회차 간 편차 및 원인 분석**:
  - P50은 1회차 45.1ms, 2회차 40.5ms, 3회차 44.5ms로 매우 안정적임.
  - 1회차와 2회차에서 P95가 목표치(100ms)를 초과한 주원인은 10개 스레드의 동시 첫 요청 배치(첫 10개 요청)에서 커넥션 생성 및 스레드 풀 초기화 오버헤드로 인해 약 120~380ms 지연이 발생했기 때문입니다.
  - 초기 배치가 완료된 이후의 후속 요청들은 20~50ms 범위로 처리되었으며, 3회차에서는 P95가 78.6ms로 안정화되어 목표를 충족했습니다.

#### (5) 단발 질의 API (`query`, non-streaming, 참고값, rounds=10)
- **1회차**: P50 = 6,792.5ms (6.79s) / P95 = 10,257.0ms (10.26s) / P99 = 10,981.3ms (10.98s) / 평균 = 6,368.8ms / 오류 = 0건
- **2회차**: P50 = 4,132.2ms (4.13s) / P95 = 6,285.3ms (6.29s) / P99 = 6,287.0ms (6.29s) / 평균 = 4,078.2ms / 오류 = 0건
- **3회차**: P50 = 4,885.2ms (4.89s) / P95 = 8,090.8ms (8.09s) / P99 = 8,638.9ms (8.64s) / 평균 = 4,724.5ms / 오류 = 0건
- **회차 간 편차**: P95 기준 최저 6,285.3ms ~ 최고 10,257.0ms (편차 3,971.7ms). 비스트리밍 단발 질의는 RAG 검색 및 LLM 전체 생성 완료를 모두 기다려야 하므로 SSE 대비 체감 대기 시간이 깁니다.

## 4. 본 실측 결과로 말할 수 있는 것과 말할 수 없는 것

### 4.1 본 측정으로 말할 수 있는 것

1. **정본 SSE 스트리밍 레이턴시 목표 충족**:
   - 첫 토큰 P95는 1.26s ~ 2.29s로 목표(3.00s 이내)를 3회 독립 실행 모두 만족합니다.
   - 전체 스트리밍 완료 P95는 6.37s ~ 7.65s로 목표(20.00s 이내)를 3회 독립 실행 모두 만족합니다.
   - 첫 stage 이벤트 전송 P95는 3.4ms ~ 11.0ms로 요청 직후 즉각적인 응답 신호가 전달됩니다.
2. **낙찰가 예측 API의 정상 상태 성능**:
   - P50 중앙값은 40.5ms ~ 45.1ms 수준으로 매우 일정하게 유지됩니다.
   - 스레드 풀 및 연결이 안정화된 3회차에서는 P95 78.6ms로 목표(100.0ms)를 충족함을 확인했습니다.
3. **HTTP 계층 및 이벤트 루프 블로킹 부재**:
   - SSE 스트리밍과 예측 API 모두 HTTP 통신 오류(0건) 없이 전량 정상 처리되어, `to_thread` 오프로드 적용 후 이벤트 루프 차단이나 심각한 데드락 없이 안정적으로 서빙됨을 확인했습니다.

### 4.2 본 측정으로 말할 수 없는 것

1. **`to_thread` 오프로드 이전 대비 성능 개선폭**:
   - 구조 수정 전의 동일 조건 레이턴시 실측 기준선이 없으므로, I/O 오프로드로 인한 개선율(%)이나 단축 수치를 직접 비교하여 주장할 수 없습니다.
2. **동시 다중 사용자 SSE 부하(c4 등)에서의 지연 특성**:
   - 본 SSE 측정은 단일 클라이언트 순차 질의(c1) 기준입니다. Ollama 모델 인스턴스 단일화로 인한 동시 다중 질의 경합 지연은 본 측정 범위에 포함되지 않습니다.
3. **장시간 운영 시 GC 및 메모리 누수 영향**:
   - 본 측정은 회차당 20~100건의 단기 벤치마크이므로, 장시간 연속 부하 환경에서의 메모리 및 GC 누적 영향은 다루지 않습니다.

## 5. 미측정 항목 및 사유

### 5.1 Arq 백그라운드 태스크 처리량 (Throughput)

- **미측정 사유**:
  `src/tasks/scheduled_tasks.py`, `src/tasks/automation_tasks.py`, `src/tasks/retrain_task.py` 등 8건의 Arq 태스크에 적용된 `to_thread` 오프로드는 HTTP 요청-응답 주기가 아닌 Redis 큐 적재 및 비동기 워커 프로세스 소비 경로에서 동작합니다.
  Arq 태스크 처리량을 공정하게 측정하기 위해서는 별도의 큐 적재 배치 스크립트, 워커 프로세스 동시성 설정, 작업 완료 이벤트 추적 프로파일러가 독립적으로 설계되어야 하므로, 이번 HTTP API 요청 경로 P95 벤치마크 범위에서는 제외하였습니다.
