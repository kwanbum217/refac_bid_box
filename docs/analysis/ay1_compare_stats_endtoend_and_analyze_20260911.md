## 1. 종단 wall time 기준선 (R-26)

`GET /api/v1/bids/compare-stats` 를 회차마다 Redis 를 비우고 호출했습니다.
캐시 미적중 경로만 측정합니다.

| 국면 | 회차 | 범위 | 평균 | 산포 |
| --- | ---: | --- | ---: | ---: |
| 버퍼풀 가열 | 5 | 6,466~17,298ms | 11,208ms | 10,832ms |
| **정상상태** | 6 | 5,038~5,928ms | **5,526ms** | **890ms** |

**가열 구간은 단조 감소합니다**(17,298 -> 12,866 -> 11,696 -> 7,712 -> 6,466).
첫 호출과 정상상태가 2.7배 차이 나므로, 회차를 구분하지 않고 재면 어떤 수치도
나올 수 있습니다.

### 1.1 잡음 바닥

**정상상태 산포 890ms 가 compare-stats 최적화의 판정 바닥입니다.** 평균의 16%
입니다. 이보다 작은 개선은 n=6 으로 구별할 수 없습니다. 앞으로 이 경로의 개선을
주장하려면 이 수치를 넘거나 회차를 늘려야 합니다.

### 1.2 잔여 재계산

AV1 이 `EXPLAIN ANALYZE` 로 잰 SQL 합계는 약 4.17초였고, 그때 기준값 6.5초와의
차 2.33초를 잔여로 적었습니다. **그 뺄셈은 성립하지 않았습니다.** 6.5초가 다른
조건의 값이었기 때문이며, AV1 리뷰어가 이미 지적한 대로입니다.

같은 조건에서 다시 재니 종단 정상상태는 5,526ms 이고, SQL 합계 4.17초를 빼면
잔여는 **약 1.4초**입니다. 이 구간은 HTTP 왕복, FastAPI, SQLAlchemy 변환,
파이썬 조립, Redis 쓰기입니다. **2.33초가 아니라 1.4초이며, 숨은 SQL 이 아닙니다.**

## 2. 통계 갱신 실험 (ANALYZE TABLE)

AX2 가 영속 통계가 낡았음을 발견했고(`bid_announcements` 통계 229만 행 대 실제
550만 행), `ANALYZE TABLE` 은 관찰 대상을 바꾸는 쓰기라 실행하지 않고 승인
사항으로 남겼습니다. 코디네이터가 1장 기준선을 먼저 확보한 뒤 실행했습니다.

### 2.1 통계 변화

| 테이블 | 갱신 전 | 갱신 후 | 실제 |
| --- | ---: | ---: | ---: |
| `bid_results` | 3,118,641 | 3,388,123 | 3,431,580 |
| `bid_announcements` | 2,295,025 | 6,377,745 | 5,504,119 |

공고 테이블은 약 139.8% 과소에서 약 15.9% 과대로 바뀌었습니다. InnoDB 통계는
표본 추정이므로 정확값이 아닙니다.

### 2.2 종단 재측정 (동일 절차)

가열 5회 뒤 정상상태 6회로 앞과 똑같이 측정했습니다.

| 조건 | n | 범위 | 평균 | 산포 |
| --- | ---: | --- | ---: | ---: |
| 적용 전 | 6 | 5,038~5,928ms | 5,526ms | 890ms |
| 적용 후 | 6 | 3,889~4,030ms | 3,951ms | **141ms** |

판정 규칙(`ax1_measurement_design_20260911.md` 2.3절)을 적용합니다.

- 범위가 겹치지 않습니다(5,038~5,928 대 3,889~4,030).
- 평균차 1,575ms 가 산포 합 1,031ms 를 넘습니다.
- 따라서 **산포 초과(참고)** 입니다. **확정이 아닙니다.**

**이 1,575ms 를 개선 효과로 인용하지 마십시오.** n=6 이며 적용 전 조건은
통계를 되돌릴 수 없어 표본을 늘릴 수 없습니다.

### 2.3 확정할 수 있는 것: 계획이 안정됐습니다

시간과 달리 실행계획 선택은 부하에 둔감합니다.

| 시점 | 매칭 쿼리 계획 |
| --- | --- |
| at4 (`EXPLAIN` 추정) | `ALL` |
| au1 (`EXPLAIN ANALYZE`) | `range ix_bid_results_dt_cat` |
| av1 (`EXPLAIN ANALYZE`) | 전체 스캔 |
| ax2 (`EXPLAIN ANALYZE`) | `range ix_bid_results_dt_cat` |
| **통계 갱신 후 (`EXPLAIN` 3회)** | **`ALL` 3회 전부** |

**진동이 멈췄습니다.** 다만 **전체 스캔 쪽으로 고정됐습니다.** 산포가 890ms 에서
141ms 로 6.3배 조여진 것이 이와 일치합니다.

### 2.4 매칭 쿼리 단독은 손해도 이득도 없습니다

`EXPLAIN ANALYZE` 2회로 1,584ms, 1,265ms 입니다. av1 의 전체 스캔
1,304~1,316ms 와 같은 계열이고, au1 의 range 854~960ms 보다는 느립니다.

**따라서 종단 1.6초 개선은 매칭 쿼리에서 온 것이 아닙니다.** 남은 세 쿼리(기관별
상위 10, 월별 두 건) 중 어디에서 왔는지는 **이번에 귀속하지 않았습니다.**
쿼리별 재측정이 필요하며 R-29 의 출발점입니다.

## 3. 되돌릴 수 없는 변경

`ANALYZE TABLE` 은 실행됐고 되돌릴 수 없습니다. 적용 전 통계로 복원할 방법이
없으므로 적용 전 조건의 표본을 늘릴 수 없습니다. 이것이 2.2절 판정을 확정으로
올릴 수 없는 이유이기도 합니다.

**다음 측정자는 통계가 2026-09-11 에 갱신된 상태를 기준선으로 삼으십시오.**
이 문서 이전의 실행계획 관찰은 옛 통계 기준입니다.

## 4. 남은 것

- 종단 1.6초 개선의 쿼리별 귀속. 기관별 상위 10 과 월별 두 건을 재측정합니다.
- 계획이 전체 스캔으로 고정된 것이 다른 bind 값에서도 유지되는지 확인.
- 통계 갱신 주기 정책. 이번처럼 오래 방치되면 옵티마이저가 잘못된 전제로 판단합니다.
