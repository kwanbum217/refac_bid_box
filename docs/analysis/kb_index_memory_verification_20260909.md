## 1. 결론

`bf29f3e` 의 청크 스트리밍 수정 이후에도 `update_kb_task` 단일 1회 실행에서 worker
컨테이너가 **10,762MB** 를 쓰고 소멸합니다. 2026-09-08 의 10,509MB 곡선이 그대로
재현됐고 오히려 **253MB 더 높습니다.**

수정은 `_flush` 로 넘기는 배치의 상주를 줄였을 뿐, 색인 대상 문서 집합 자체를 전량
적재하는 경로는 그대로 남아 있습니다. 청크 순회는 이미 메모리에 올라온 리스트를
잘라 쓰는 것이라 피크 메모리를 낮추지 못합니다.

| 2 | 피크가 2026-09-08 의 10,509MB 곡선을 재현하지 않는다 | 10,762MB. 동일 계열이며 +253MB | **실패** |

수학적 동일성 확인은 여전히 실행 검증으로 뒷받침되지 않은 상태입니다.

로그의 `Starting worker for 17 functions` (09:19:57) 로 확인했습니다.

측정 조건은 Docker Desktop `MemoryMiB` **16,384** 입니다. 여유를 준 조건에서도
실패했으므로 상향으로 닫히지 않는다는 2026-09-08 의 결론이 재확인됩니다.

## 4. 남은 상주 요인

Wave AP 인수인계 4장이 지목한 지점이 그대로 남아 있습니다.

```python
target_ids = {make_id(i, it) for i, it in enumerate(items)}
removed_ids = [doc_id for doc_id in existing_hashes if doc_id not in target_ids]
```

`items` 는 청크 순회 이전에 이미 전량 리스트입니다. `_resolve_announcements` 와
`_resolve_delta_announcements` 가 공고 전량을 리스트로 반환하기 때문입니다.
`existing_hashes` 536,002건도 함께 상주합니다. 09:18:15 의 변곡점은 이 전량 적재가
시작되는 지점과 일치합니다.

따라서 다음 수정 대상은 **조회 계층의 페이지 단위 전환**이며, 이는 미착수 Task
`task_e6226318e956` (AP2) 의 범위입니다.
