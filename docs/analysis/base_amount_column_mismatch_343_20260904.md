## 2. 343건의 구성

| 종류 | 건수 | 정체 | 집계 영향 |
| --- | --- | --- | --- |
| `column_null` | 234 | `raw_data` 금액이 문자열 `"0.0"`, 컬럼은 `NULL` | **없음** |
| `value_differs` (소수부) | 107 | `raw` 가 소수점을 가지고 컬럼은 정수로 절단됨 | **합계 107원 미만** |
| `value_differs` (포화) | 2 | 이미 알려진 BIGINT 포화 2건 | **없음** (양쪽 경로 모두 제외) |

카테고리는 `Cnstwk` 236건, `Servc` 107건이고 `collected_at` 은
2026-03-12 17:09 ~ 2026-08-03 03:07 입니다. 표본이 전부 2026-03-12/13 에 몰려 있어
**2026-03 parquet 복구 적재분**이라는 가설과 일치합니다.

### 2.1 `column_null` 234건은 값이 0입니다

234건 전수에서 `raw_data` 금액을 파싱한 값이 **정확히 0**이었습니다. 0이 아닌 것은
한 건도 없습니다.

`SUM` 에서 `NULL` 은 무시되고 `0` 은 합에 영향을 주지 않으므로 두 경로의 결과가
같습니다. 컬럼 기반으로 바꿔도 총액이 변하지 않습니다.

### 2.2 `value_differs` 107건은 소수부뿐입니다

```
20150522437  컬럼 3469575370   raw '3469575370.8'
20150522439  컬럼 691483403    raw '691483403.6'
20180700470  컬럼 158420       raw '158420.9'
20210500474  컬럼 27           raw '27.5'
20241200484  컬럼 5988         raw '5988.67'
```

적재 시점에 정수로 절단되어 저장된 것이고 차이는 전부 **1원 미만**입니다.
107건을 모두 합쳐도 107원을 넘지 않습니다. 조달 금액 단위에서 무의미합니다.

### 2.3 나머지 2건은 이미 알려진 포화 건입니다

```
R25BK01131785  컬럼 9223372036854775807  raw '12240000012240000011'
R25BK01210563  컬럼 9223372036854775807  raw '26849000084793201743'
```

인수인계 6.4절이 기록한 BIGINT 포화 2건입니다. **양쪽 값 모두 이상치 상한
100조를 넘으므로 JSON 경로와 컬럼 경로 모두 집계에서 제외합니다.** 따라서 전환에
따른 총액 변화가 없습니다.

이 두 건의 컬럼 값을 `NULL` 로 바로잡는 것은 별개 과업이며 DB 값 변경이라 승인이
필요합니다. 현재 화면 영향은 없습니다.

## 3. 조사 방법과 이전 세션이 실패한 이유

전수 대조는 550만 행마다 `JSON_EXTRACT` -> `JSON_UNQUOTE` -> `REPLACE` ->
`CAST(DECIMAL(30,0))` 을 수행합니다. 인덱스로 줄일 수 없는 전수 파싱이라
같은 조건에서 통제 재집계가 554초 걸린 것과 같은 성질입니다.

이번에는 조회를 배경으로 돌려 다른 작업과 병행했습니다. 이전 세션은 전경에서
기다리다 20분에 중단(`KILL QUERY`)했습니다. **작업을 바꾼 것이 아니라 기다리는
방식을 바꾼 것입니다.**

### 3.1 읽기 전용 실행기의 오탐

`scripts/db_readonly_query.py` 가 이 질의를 거부했습니다.

```
거부: 금지 키워드가 포함돼 있습니다: REPLACE
```

금지 키워드 검사가 문자열 **함수** `REPLACE(...)` 와 `REPLACE INTO` **문장**을
구분하지 않았습니다. 같은 세션에서 함수 호출 형태만 예외로 허용하고 회귀 테스트를
추가했습니다. 워커도 금액 질의를 하려면 같은 지점에 걸립니다.
