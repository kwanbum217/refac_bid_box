## 1. 개요 및 배경

본 작업은 `.github/workflows/ci.yml`의 공급망 보안 검증 job(`supply-chain`)에 존재하던 세 가지 구조적 결함을 시정하고, 관련 정책 문서 및 기계 검증 사실 원장의 정합성을 복구하기 위해 수행되었습니다.

### 1.1 식별된 핵심 결함
1. **스캐너와 판정자 결합 및 CI 실패 구조 결함**:
   Trivy 스캔 스텝이 `exit-code: '1'`로 설정되어 있어, 취약점 검출 시 해당 스텝이 비정상 종료되었습니다. 후속 `Filter Trivy results against allowlist` 스텝이 `if: always()`로 실행되어 allowlist 대조 후 잔존 취약점이 없어 `exit 0`을 반환하더라도, 앞선 Trivy 스텝의 실패로 인해 GitHub Actions의 job conclusion은 항상 `failure`가 되었습니다. 즉, allowlist에 정당한 예외를 등록하더라도 구조적으로 CI를 통과시킬 수 없는 상태였습니다.
2. **보안 실패 빌드의 SBOM 누락 결함**:
   `Generate application SBOM` 및 `Upload SBOM artifact` 스텝에 실행 조건이 지정되지 않아, 앞선 Trivy 스텝 실패 시 해당 스텝들이 자동으로 skip 되었습니다. 이로 인해 보안 문제가 발생한 바로 그 빌드의 SBOM 감사 증거가 생성 및 보존되지 못했습니다.
3. **allowlist 패키지 단위 대조로 인한 과도한 허용 범위**:
   기존 npm audit 판정 로직이 패키지 이름(`allowed = {e['package'] for e in data.get('npm', [])}`)만 비교하고 있어, 예외 등록된 패키지(`nanoid`)에 전혀 다른 새로운 HIGH/CRITICAL 취약점이 발생하더라도 만료일까지 무조건 자동 통과되는 보안 허점이 존재했습니다. Trivy 판정 로직 또한 CVE ID 단독으로만 비교하고 있었습니다.
4. **기계 원장과 운영 코드의 불일치**:
   `docs/context/current_state_facts.yaml`의 `supply_chain_gate` 항목이 `status: blocked`, `claim: "공급망 스캔은 보고 전용이며 게이트 승격 조건 확인을 대기합니다."`로 기록되어 있었으나, 실제 워크플로와 운영 정책은 이미 차단 모드로 운영 중이었습니다.

## 2. 시정 및 구현 내용

### 2.1 스캐너와 판정자의 분리 (Trivy)
- **스캐너 책임 분리**: `.github/workflows/ci.yml`의 `Scan container image` 스텝을 `exit-code: '0'`으로 변경하여 스캐너는 오직 결과 파일(`trivy-results.json`) 생성만을 담당하도록 책임을 격리했습니다. 심각도 임계값(`CRITICAL,HIGH`)과 `ignore-unfixed: true`는 그대로 유지하여 게이트 강도를 보존했습니다.
- **단독 판정 스크립트 구축**: 워크플로 내 인라인 Python 로직을 `scripts/filter_trivy_results.py`로 추출하고 단위 테스트(`tests/test_filter_trivy_results.py`)를 작성했습니다.
  - **Fail-Closed 원칙**: 결과 파일이 존재하지 않거나 빈 파일/파싱 불가일 경우 즉시 `exit 1`로 차단합니다.
  - **정밀 대조**: (CVE ID + 패키지 이름) 쌍을 기준으로 allowlist와 대조합니다.
  - **차단 및 출력**: 미허용 CRITICAL/HIGH 취약점이 하나라도 존재하면 stderr에 취약점 목록을 출력하고 `exit 1`로 차단합니다.

### 2.2 SBOM 생성 보장 및 실패 전파 무결성
- `Generate application SBOM` 및 `Upload SBOM artifact` 스텝에 `if: always() && steps.build-image.outcome == 'success'` 조건을 적용했습니다.
- 이미지 빌드가 성공한 경우, 보안 스캔 결과의 성공/실패와 무관하게 해당 빌드의 SBOM이 반드시 생성되고 아티팩트로 업로드됩니다.
- 이미지 빌드 자체가 실패한 경우에는 SBOM 스텝이 실행되지 않습니다.
- 판정 스텝이 `exit 1`로 실패했을 경우, 후속 SBOM 스텝이 성공하더라도 GitHub Actions의 job conclusion은 최종적으로 `failure`로 유지되므로 판정 실패가 은폐되지 않습니다.

### 2.3 (패키지 이름 + advisory ID) 쌍 대조 (npm audit)
- 워크플로 인라인 로직을 `scripts/filter_npm_audit.py`로 분리하고 단위 테스트(`tests/test_filter_npm_audit.py`)를 구현했습니다.
- npm audit JSON 출력에서 각 취약점의 advisory 식별자(GHSA 또는 CVE ID)를 추출하여 `(패키지 이름, advisory ID)` 쌍 집합으로 allowlist와 대조합니다.
- 기존 등록된 `nanoid` 예외(`id: GHSA-2v37-7h3g-55p8`)는 정상 통과하며, 동일 패키지에 다른 advisory가 발생한 경우에는 즉시 차단됩니다.

### 2.4 공급망 스캔 정책 및 기계 원장 갱신
- `docs/ops/supply_chain_policy.md`: 스캐너 스텝의 `exit-code: 0` 허용 예외 규정(후속 판정 스텝이 단독 게이트이고 결과 파일 부재 시 fail-closed 조건)과 그 근거를 추가하고 버전(1.1.0)을 갱신했습니다.
- `docs/context/current_state_facts.yaml`: `supply_chain_gate`의 status를 `closed`, claim을 `"공급망 스캔은 모두 차단 모드로 운영하며 CRITICAL 및 HIGH 취약점 차단 게이트를 통과 기준으로 유지합니다."`, document_anchor를 `"공급망 스캔은 모두 차단 모드로 운영"`으로 갱신했습니다.
- `docs/context/CURRENT_STATE.md`: `closed 사실` 섹션으로 `supply_chain_gate`를 이동하고, `blocked 사실` 섹션의 구 서술을 제거했습니다.
