# 레이턴시 게이트 측정 규약

> **성격**: 날짜를 붙이지 않는 **규약 문서**입니다. 이 문서가 정본이며, 개별 측정 문서는 여기에 따릅니다
> **제정일**: 2026-08-14
> **제정 근거**: [`phase7_gate_and_stale_branch_audit_20260814.md`](phase7_gate_and_stale_branch_audit_20260814.md) 감사에서 표본 수·반복·warmup·동시성 기준 4항목 전부 미규정 확인
> **판정 주체**: 코디네이터 (Claude Opus 5)
> **적용 범위**: G3 성능 목표와 Phase 7 컷오버 판정에 쓰이는 모든 레이턴시 측정

---

## 0. 왜 이 문서가 필요한가

**규약이 없으면 통과·미달이 측정 조건 선택으로 결정됩니다.** 2026-08-14 실측이
이것을 증명했습니다. 같은 날 같은 코드가 조건에 따라 이렇게 갈렸습니다.

| 조건 | 표본 | 100ms 초과율 | 판정 |
| --- | ---: | ---: | --- |
| 워밍업 10회, 표본 120~1200 | 5,640 | **0.00%** | 통과 |
| 워밍업 없음, 표본 100 | 1,100 | **23.4%** | 미달 |

두 값은 오차가 아니라 **다른 실험**입니다. 어느 쪽도 그 자체로 부정직하지
않으나, 유리한 쪽을 골라 통과라고 쓰면 부정직해집니다. 근거는
[`phase8_predict_p95_samplesize_effect_20260814.md`](phase8_predict_p95_samplesize_effect_20260814.md)
7.4 절입니다.

## 1. 표본 수

| 항목 | 규정 |
| --- | --- |
| 최소 표본 수 | **회차당 600 요청** |
| 표본 수 미달 측정 | 게이트 판정에 쓰지 않습니다. 탐색용으로만 씁니다 |

### 1.1 600 의 근거

마이크로배칭에서 지연 이벤트 하나는 요청 1건이 아니라 **배치
`MAX_BATCH_SIZE`(현재 10)건을 통째로** 밀어냅니다. 실측에서 100ms 초과 요청의
완료 인덱스가 `33~42`, `77~86` 같은 연속 블록으로 나온 것이 근거입니다.

따라서 P95 오염 여부는 확률이 아니라 산술입니다.

| 표본 수 | 오염 비중(10/n) | P95 경계(상위 5%) 안에 들어오는가 |
| ---: | ---: | --- |
| 100 | 10.0% | **예** |
| 200 | 5.0% | 경계 |
| 300 | 3.3% | 아니오 |
| **600** | **1.7%** | 아니오. 이벤트 2회까지 견딤(3.3%) |

600 은 **지연 이벤트가 2회 나도 P95 가 오염되지 않는 최소 수준**입니다.
`MAX_BATCH_SIZE` 를 올리면 이 값도 함께 올려야 합니다. 규칙은
`n >= MAX_BATCH_SIZE x 60` 입니다.

## 2. Warmup

| 항목 | 규정 |
| --- | --- |
| warmup 요청 수 | **측정 동시성과 같은 수** (c10 이면 10회) |
| warmup 요청 처리 | 표본에서 **제외**합니다 |
| 서버 상태 | 모델 로드 완료 후. 기동 직후 첫 요청은 warmup 에 포함 |

### 2.1 근거

워밍업 없는 측정에서 첫 배치가 그대로 표본에 들어갑니다. 실측
`phase8_predict_batch5_c10` 의 첫 10건 완료 지연이
`67, 90, 90, 90, 90, 90, 91, 89, 91, 89ms` 였고, 같은 코드의 워밍업 측정
P50 은 30.5~35.0ms 였습니다.

**냉시동 지연은 실재하며 숨기지 않습니다.** 다만 그것은 warm P95 게이트가 아니라
별도 항목입니다. 3.3 절을 보십시오.

## 3. 반복 회차와 대표값

| 항목 | 규정 |
| --- | --- |
| 최소 반복 회차 | **3회** |
| 판정 대표값 | **회차별 값 중 최악값(worst)** |
| 회차 간 간격 | 직전 회차 종료 후 30초 이상 |

### 3.1 왜 최악값인가

중앙값을 쓰면 3회 중 2회가 통과하면 통과가 됩니다. 그러나 사용자는 중앙값
회차에 요청하지 않습니다. **게이트는 서비스 약속이므로 나쁜 쪽으로 판정합니다.**

1장의 표본 600 규정이 이미 단일 지연 이벤트를 흡수하므로, 그래도 미달인
회차가 있다면 그것은 표본 오차가 아니라 실재하는 문제입니다.

### 3.2 부수 지표

대표값과 함께 다음을 항상 기록합니다. 하나만 적은 측정은 게이트 근거로
쓰지 않습니다.

| 지표 | 이유 |
| --- | --- |
| P50, P95, P99, 최댓값 | P95 하나로는 꼬리 형태를 알 수 없습니다 |
| **100ms 초과율과 Wilson 신뢰구간 상한** | 표본 수에 흔들리지 않는 유일한 지표 |
| 오류 건수 | 실패를 빠른 응답으로 착각하지 않기 위함 |

### 3.3 냉시동은 별도 항목입니다

warm 게이트와 분리해 기록합니다. 섞으면 어느 쪽도 판정할 수 없습니다.

| 항목 | 측정 | 기준 |
| --- | --- | --- |
| warm P95 | 2장 warmup 후 600회 | 4장 |
| 냉시동 첫 요청 | 서버 기동 후 첫 1회 | 기준 미설정. **기록만 합니다** |

## 4. 동시성 수준과 기준

| 동시성 | P95 기준 | 성격 |
| --- | --- | --- |
| c1 | 회귀 금지 (직전 승격값 대비 +10% 이내) | 단건 응답성 |
| c2 | 회귀 금지 (같음) | — |
| c4 | 회귀 금지 (같음) | — |
| **c10** | **100ms 이하** | **G3 판정 기준** |

c1/c2/c4 에 절대 수치를 두지 않는 이유는 이들이 개선 목표가 아니라 **c10
최적화의 부작용 감시 지점**이기 때문입니다. 배치 창을 늘려 c10 을 개선하면 c1
이 나빠질 수 있고, 그것을 잡는 것이 이 항목의 역할입니다.

## 5. 측정 환경

| 항목 | 규정 |
| --- | --- |
| 동시 실행 작업 | **없어야 합니다.** 다른 에이전트·수집·색인·학습이 도는 중에는 측정하지 않습니다 |
| 계측 | **비활성.** 계측 활성 측정은 게이트 근거가 아닙니다 |
| 프로세스 구성 | 측정 문서에 명시 (Uvicorn 워커 수, 스레드 예산) |
| 커밋 SHA | 측정 문서에 명시 |

### 5.1 계측 비활성 근거

계측 활성 측정은 P50 +2.34ms, P95 +9.97ms 의 오버헤드가 실측됐습니다. 원인
규명에는 필요하나 게이트 판정에는 쓸 수 없습니다.

### 5.2 동시 실행 금지 근거

2026-08-14 세션에서 워커 3대가 같은 장비에 돌고 있었습니다. 그 상태에서 측정한
값은 서비스 지연이 아니라 장비 경합을 재는 것입니다. 이 규정 때문에 그날의 GC
후보 실측을 워커 종료 후로 미뤘습니다.
