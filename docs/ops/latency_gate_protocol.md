## 1. 표본 수

| 항목 | 규정 |
| --- | --- |
| 최소 표본 수 | **회차당 600 요청** |
| 표본 수 미달 측정 | 게이트 판정에 쓰지 않습니다. 탐색용으로만 씁니다 |

### 1.1 600 의 근거

마이크로배칭에서 지연 이벤트 하나는 요청 1건이 아니라 **배치
`MAX_BATCH_SIZE`(현재 10)건을 통째로** 밀어냅니다. 실측에서 100ms 초과 요청의
완료 인덱스가 `33~42`, `77~86` 같은 연속 블록으로 나온 것이 근거입니다.

따라서 P95 오염 여부는 확률이 아니라 산술입니다.

| 표본 수 | 오염 비중(10/n) | P95 경계(상위 5%) 안에 들어오는가 |
| ---: | ---: | --- |
| 100 | 10.0% | **예** |
| 200 | 5.0% | 경계 |
| 300 | 3.3% | 아니오 |
| **600** | **1.7%** | 아니오. 이벤트 2회까지 견딤(3.3%) |

600 은 **지연 이벤트가 2회 나도 P95 가 오염되지 않는 최소 수준**입니다.
`MAX_BATCH_SIZE` 를 올리면 이 값도 함께 올려야 합니다.

#### 1.2 엔드포인트별 최소 표본 수

**허용 이벤트 2회를 고정 기준으로 삼습니다.** 배칭 여부에 따라 이벤트 1회가
오염시키는 요청 수가 다르므로 표본 수도 달라집니다.

| 경로 | 이벤트 1회당 오염 요청 | 규칙 | 최소 표본 |
| --- | ---: | --- | ---: |
| 예측 API (마이크로배칭) | `MAX_BATCH_SIZE` = 10 | `n >= MAX_BATCH_SIZE x 60` | **600** |
| SSE 챗봇 (배칭 없음) | 1 | `n >= 60` | **60** |

일반식은 `n >= (오염 요청 수) x 60` 입니다. `2 x 오염요청수 / n < 0.05` 를
만족하는 최소값입니다.

**요청당 수 초가 걸리는 경로에서 600 을 요구하지 마십시오.** 근거가 없는 과잉이며
측정이 수십 분으로 늘어납니다. 반대로 60 미만으로 줄이지도 마십시오. 2026-08-14
SSE 측정이 회차당 30 으로 수행돼 기준선으로 쓸 수 없었습니다.

## 3. 반복 회차와 대표값

| 항목 | 규정 |
| --- | --- |
| 최소 반복 회차 | **3회** |
| 판정 대표값 | **회차별 값 중 최악값(worst)** |
| 회차 간 간격 | 직전 회차 종료 후 30초 이상 |

### 3.1 왜 최악값인가

중앙값을 쓰면 3회 중 2회가 통과하면 통과가 됩니다. 그러나 사용자는 중앙값
회차에 요청하지 않습니다. **게이트는 서비스 약속이므로 나쁜 쪽으로 판정합니다.**

1장의 표본 600 규정이 이미 단일 지연 이벤트를 흡수하므로, 그래도 미달인
회차가 있다면 그것은 표본 오차가 아니라 실재하는 문제입니다.

### 3.2 부수 지표

대표값과 함께 다음을 항상 기록합니다. 하나만 적은 측정은 게이트 근거로
쓰지 않습니다.

| 지표 | 이유 |
| --- | --- |
| P50, P95, P99, 최댓값 | P95 하나로는 꼬리 형태를 알 수 없습니다 |
| **100ms 초과율과 Wilson 신뢰구간 상한** | 표본 수에 흔들리지 않는 유일한 지표 |
| 오류 건수 | 실패를 빠른 응답으로 착각하지 않기 위함 |

### 3.3 냉시동은 별도 항목입니다

warm 게이트와 분리해 기록합니다. 섞으면 어느 쪽도 판정할 수 없습니다.

| 항목 | 측정 | 기준 |
| --- | --- | --- |
| warm P95 | 2장 warmup 후 600회 | 4장 |
| 냉시동 첫 요청 | 서버 기동 후 첫 1회 | 기준 미설정. **기록만 합니다** |

| 동시성 | P95 기준 | 성격 |
| --- | --- | --- |
| c1 | 회귀 금지 (직전 승격값 대비 +10% 이내) | 단건 응답성 |

### 4.1 100ms 초과율 기준 (예측 API 한정)

P95 만으로는 꼬리가 사라졌는지 알 수 없습니다. c10 P95 를 통과한 기본 모드도
1,800 요청 중 21건(1.167%)이 100ms 를 넘었습니다. 따라서 초과율에 별도 기준을
둡니다.

| 항목 | 기준 |
| --- | --- |
| 관측 초과율 | 3회차 합계(n >= 1,800) 기준 **0.5% 이하** |
| Wilson 95% 상한 | **1.0% 이하** |
| 둘의 관계 | **둘 다** 만족해야 통과입니다 |

**0.5% 의 근거**는 지연 이벤트가 배치 10건을 통째로 미는 구조입니다. n=1,800 에서
0.5% 는 9건이므로 **지연 이벤트 1회까지 허용**하고 2회는 불허합니다. 실측
기준선입니다.

| 모드 | 초과 건수 / 1,800 | 초과율 | 이벤트 환산 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 기본(off) | 21 | 1.167% | 약 2회 | 미달 |
| `batch-disable` | 30 | 1.667% | 약 3회 | 미달 |
| `threshold` | 0 | 0.000% | 0회 | 통과 |
| **`freeze`** (채택) | **0** | **0.000%** | 0회 | **통과** |

`freeze` 는 c1/c2/c4/c10 전 수준 합계 **7,200 요청에서 초과 0건**이며 Wilson
상한 0.053% 입니다.

#### SSE 에는 이 기준을 쓰지 마십시오

100ms 는 예측 API 의 값입니다. SSE 는 LLM 생성이 포함돼 자리수가 다릅니다.
SSE 기준은 `REFACTORING_DESIGN.md:677` 이 정한 **첫 토큰 P95 3초, 전체 P95
20초**이며, **그 목표는 순차(c1) 측정에서 나온 값입니다**
(`scripts/benchmark_latency.py:138` 이 순차 루프). 따라서 c2 이상에 그 수치를
적용해 미달로 판정하지 마십시오. **SSE 의 동시성 수준별 기준은 아직
없습니다.**

#### 왜 Wilson 상한만으로 판정하지 않는가

**관측이 0건일 때 Wilson 상한은 표본 수만의 함수입니다.**

| 표본 수 | 관측 0건일 때 Wilson 상한 |
| ---: | ---: |
| 600 | 0.636% |
| 1,800 | 0.213% |
| 3,600 | 0.107% |
| 7,200 | 0.053% |

즉 상한만을 기준으로 삼으면 **품질이 아니라 표본 수를 늘려 통과하는 길**이
열리고, 반대로 정직한 작은 표본이 0건이어도 미달로 떨어집니다. 그래서 관측
초과율을 주 기준으로 두고 Wilson 상한은 함께 걸어 소표본 과대주장을
막는 보조로 씁니다. **두 값을 모두 기록하십시오.**

c1/c2/c4 에 절대 수치를 두지 않는 이유는 이들이 개선 목표가 아니라 **c10

## 4.3 통제 교차 A/B 쌍대 델타 및 꼬리 안전성 기준 (c1/c2/c4 회귀 판정 보강)

호스트 부하 드리프트나 단발성 스파이크로 인한 위양성(false positive) 회귀 판정을 방지하기 위해, 동일 호스트에서 과거 baseline과 현재 main 컨테이너를 독립 기동하여 교차(alternating) 실행하는 **통제 교차 A/B 벤치마크**를 수행할 수 있습니다.

통제 교차 A/B 수행 시 기존 +10% P95 회귀 판정선에 더하여 아래의 **꼬리 지연 안전성** 규칙을 적용하며, 쌍대 델타 중앙값은 향후 실험용 prospective 보조 지표로 함께 기록합니다 (PASS 판정선에는 포함하지 않음):

| 판정 항목 | 판정 기준 | 목적 및 비고 |
| --- | --- | --- |
| **P95 회귀 한도** | 직전 승격값 대비 **+10% 이내** (기존 유지) | 절대 상한선. c4 PASS의 유일한 정식 판정선 |
| **꼬리 지연 안전성 (50ms)** | 회차당(n=600) **50ms 초과 0건 (0.00%)** | 중간 동시성 이상 지연 스파이크 차단 |
| **꼬리 지연 안전성 (100ms)** | 회차당(n=600) **100ms 초과 0건 (0.00%)** | 절대 지연 파탄 차단 |
| **쌍대 P95 델타 중앙값 (prospective)** | Current P95 - Baseline P95 (보조 기록) | 향후 회귀 예산 정식 수립 전 단계의 관찰 지표. PASS 판정선에 미포함 |

- **규약 시맨틱 유지**: 본 규칙의 정식 PASS 판정선은 +10% P95 한도와 꼬리 안전성이며, 쌍대 델타 중앙값은 관찰용 보조 지표다. 향후 회귀 예산이 정식으로 수립되면 본 표에 추가한다.
- **c4 게이트 판정 기록 (2026-08-22)**:
  - 2026-08-22 통제 A/B 5회 교차 실측([`predict_ab_20260822.md`](predict_ab_20260822.md)) 결과, c4 최악 P95는 34.32ms로 기존 +10% 판정선(36.81ms)을 만족했습니다.
  - Baseline(중앙값 32.29ms) 대비 Current(중앙값 33.88ms)의 쌍대 델타 중앙값(prospective)은 **+1.31ms**로 기록되었습니다.
  - 6,000개 c4 유효 요청(Baseline 3,000 + Current 3,000) 전체에서 >50ms 0건, >100ms 0건으로 꼬리 안전성을 완전 충족했습니다.
  - 정식 P95 회귀 한도(+10%)와 꼬리 안전성 두 기준을 모두 충족했으므로 **c4 예측 게이트는 통과(PASS)**로 기록합니다.
  - **주의**: c4 게이트 통과는 예측 API 중간 동시성에 대한 판정이며, **G3 전체 컷오버(overall G3 cutover) 완료를 의미하지 않습니다.** G3 전체 컷오버는 잔여 엔드포인트 및 다중 동시성/인프라 검증 요건을 별도로 충족해야 합니다.

### 5.1 계측 비활성 근거

계측 활성 측정은 P50 +2.34ms, P95 +9.97ms 의 오버헤드가 실측됐습니다. 원인
규명에는 필요하나 게이트 판정에는 쓸 수 없습니다.

### 5.2 설정이 서버에 실제로 닿았는지 확인하십시오

**측정 대상 설정이 적용되지 않은 채 두 집단을 비교한 사고가 있었습니다.**
2026-08-14 세션에서 `PREDICTION_GC_MODE` 를 끄고 켜서 18회 측정했는데, compose
기본값이 `${VAR:-freeze}` 여서 **양쪽 집단 모두 켜진 상태**였습니다. 스크립트는
정상 종료하고 그럴듯한 숫자가 나왔습니다.

집단마다 시작 시 서버에서 실제 값을 읽고, 기대와 다르면 **측정을 중단**합니다.

```bash
got=$(docker compose exec -T app printenv PREDICTION_GC_MODE | tr -d '\r\n')
[ "$got" = "$expected" ] || { echo "중단: 기대 '$expected' 실제 '$got'"; exit 1; }
```

셸 기본값 표기도 함께 확인하십시오. `${VAR:-기본값}` 은 빈 문자열을 미설정으로
보아 기본값으로 되돌리므로 **끌 수단이 없어집니다.** 끌 수 있어야 하는 설정은
`${VAR-기본값}` 으로 씁니다.

| 표본 간격 | 5초 |
| 지표 | `sysctl -n vm.loadavg` 의 1분 값을 `hw.ncpu` 로 나눈 코어당 사용률 |
| 통과 임계 | **중앙값 30% 이하, 최대 50% 이하** |
| 기록 | 최소·중앙·최대를 측정 문서에 싣습니다 |

```bash
NC=$(sysctl -n hw.ncpu)
L=$(sysctl -n vm.loadavg | awk '{print $2}')
echo "$L $NC" | awk '{printf "코어당 %.1f%%\n", 100*$1/$2}'
```

임계값 근거는 2026-08-14 실측입니다. 14코어 장비에서 다른 세션이 유휴로 살아
있는 동안 c10 벤치마크를 돌린 코어당 사용률이 **중앙값 10.5%, 최대 13.3%**
였습니다. 30% 는 다른 에이전트가 실제로 일하는 상태를 걸러내면서 자기 벤치마크
부하는 통과시키는 선입니다.

임계를 넘으면 측정을 버리고 다시 하십시오. **넘은 값을 그대로 쓰면서 "부하가
있었다" 고 적는 것은 판정 근거가 되지 않습니다.**

## 8. 측정치 보존 방침

규약이 3회차를 요구하므로 성능 조사 한 건마다 원시 측정치가 쌓입니다. 방치하면
어느 파일이 근거이고 어느 것이 탐색 잔여물인지 구분되지 않습니다.

### 8.1 현재 규모

2026-08-14 기준 `data/benchmarks/` 는 JSON 80개와 로그 몇 개로 약 14MB 입니다.
**단일 파일 최대가 0.10MB 이므로 개별 파일이 문제인 상황은 아닙니다.** 증가율은
조사 한 건당 약 1.2MB(15개 파일 내외)입니다.

### 8.2 보존과 폐기

| 구분 | 처분 |
| --- | --- |
| 문서가 기준선 또는 판정 근거로 인용한 측정치 | **보존** |
| 엔드포인트별 최신 기준선 세트 | **보존** |
| 대체된 탐색 측정치 | 폐기 |
| **무효 판정된 측정치** | **즉시 삭제.** 8.3 |
| 요청별 배열이 1MB 를 넘는 계측 원시 파일 | `main` 에 넣지 않고 진단 브랜치에 둡니다 |

마지막 항목의 실례가 `perf/predict-tail` 의 계측 활성 원시 약 13MB 입니다.
근거는 [`phase8_predict_tail_merge_verdict_20260814.md`](phase8_predict_tail_merge_verdict_20260814.md)
5.3 절입니다.

### 8.3 무효 측정치는 남기지 마십시오

**설정이 잘못 적용된 채 측정된 파일은 그 자리에서 지웁니다.** 2026-08-14 세션에서
`PREDICTION_GC_MODE` 가 양쪽 집단 모두 켜진 상태로 18회 측정된 파일이 나왔고
즉시 삭제했습니다. 남기면 다음 사람이 대조군으로 믿고 씁니다. 파일명만으로는
무효임을 알 수 없다는 것이 핵심입니다.

삭제 사실과 이유는 해당 측정 문서에 적습니다. **"측정했다" 와 "그 측정이
유효하다" 를 구분해 기록하십시오.**
