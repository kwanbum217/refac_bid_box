## 0. 정책 결정 요약 (선택지 B 채택)

2026-09-11 코디네이터 판정으로 **선택지 B (신선도 임계 초과 시에만 갱신)** 가 정식 채택되었다 (선택지 A, C 는 기각).

### 0.1 채택 근거 (셋)
1. **측정 기준선 보존**: 신선도 점검 조회가 100% 읽기 전용(`READ ONLY`)이므로 정기 점검이 실행계획 기준선을 건드리지 않는다.
2. **방치 재발 원천 차단**: 이 저장소에서 문서 조항으로만 둔 규칙은 지켜지지 않았고 실제로 139.8% 편차가 열흘을 갔다. 상시 감지를 자동화하여 드리프트 누적을 조기에 포착한다.
3. **되돌릴 수 없는 조작의 무인 실행 방지**: `ANALYZE TABLE` 은 실행계획을 바꾸는 비가역적 조작이므로 절대 자동 실행하지 않고 사람 승인에 남긴다.

### 0.2 상시 감지 아키텍처
- **단일 원천(Single Source of Truth)**: 신선도 판정 로직과 임계값은 `src/app/services/mysql_stats_freshness.py` 에 단일화되었으며, CLI 실행기(`scripts/check_mysql_stats_freshness.py`)는 이를 임포트하여 사용한다.
- **야간 상시 점검**: `src/tasks/scheduled_tasks.py` 의 `nightly_schedule_task` 후속 단계에 읽기 전용 점검이 배치되어 매일 자동 실행된다.
- **실제 행 수 실측 기준**: 데이터가 지속 증가하므로 기준 행 수를 하드코딩하지 않고 점검 시점에 대상 테이블(`bid_results`, `bid_announcements`)의 실제 행 수를 직접 세어 기준으로 삼는다.
- **결과 기록 및 로깅**: 점검 결과는 `outcome["mysql_stats_freshness"]` 에 담기며, 임계 초과 시 `WARNING` 경고 로그, 정상 시 `INFO` 정보 로그를 남긴다. 점검 중 오류가 발생해도 야간 작업 전체는 중단되지 않는다.
- **자동 갱신 배제**: 코드 어디에도 `ANALYZE TABLE` 자동 실행은 없다.

### 0.3 임계 초과 시 사람이 밟을 절차
1. **야간 점검 경고 확인**: 로그에서 `MySQL 영속 통계 신선도 임계 초과 감지` 경고 및 초과 테이블과 편차 상세를 확인한다.
2. **읽기 전용 상태 확인**: 터미널에서 점검 스크립트를 실행하여 현 상태를 확인한다.
   ```sh
   uv run python scripts/check_mysql_stats_freshness.py
   ```
3. **진행 중인 측정 영향 검토**: 현재 실행 중이거나 예정된 벤치마크/실행계획 측정 작업이 없는지 확인한다 (통계 갱신 시 기존 실행계획 기준선이 무효화됨).
4. **사람 승인 및 수동 갱신 실행**: 운영자 승인 후 수동으로 대상 테이블의 통계를 갱신한다.
   ```sh
   # DB 읽기/쓰기 권한을 갖춘 세션에서 수동 실행 (주의: 실행계획 변경됨)
   # ANALYZE TABLE bid_announcements;
   # ANALYZE TABLE bid_results;
   ```
5. **정상 복구 검증**: 점검 스크립트를 다시 실행하여 종료 코드 0 (OK) 및 임계 이내 복구를 확인한다.
   ```sh
   uv run python scripts/check_mysql_stats_freshness.py
   ```

## 1. 무엇이 어긋났는지와 그 규모

2026-09-01 갱신분 영속 통계가 열흘 동안 그대로였고 그 사이 매일 02:00 수집 크론이 적재를 계속했다. 2026-09-11 코디네이터가 `ANALYZE TABLE` 을 실행했고(되돌릴 수 없음) 전후 값은 다음이다.

| 테이블 | 갱신 전 통계 | 갱신 후 통계 | 실제 행 수 | 갱신 전 편차 |
| --- | ---: | ---: | ---: | --- |
| `bid_announcements` | 2,295,025 | 6,377,745 | 5,504,119 | 약 139.8% 과소 |
| `bid_results` | 3,118,641 | 3,388,123 | 3,431,580 | 약 10.0% 과소 |

이 표의 편차는 `(실제 - 통계) / 통계` 로 계산했다. **점검 실행기는 분모가 다르다.** 실행기는 `abs(통계 - 기준) / 기준` 을 쓰므로 같은 갱신 전 상태를 58.3% 로 낸다. 두 값은 같은 사실의 다른 표기이며 섞어 인용하면 안 된다. 아래 3.2 절의 임계 근거는 실행기 공식 기준이다. 공고 테이블은 통계가 실제의 절반도 못 되는 상태로 열흘을 갔고, 결과 테이블도 자동 재계산 임계(10%) 경계에 있었다. 갱신 후에도 표본 추정이라 공고 테이블은 실제 대비 약 15.9% 과대, 결과 테이블은 약 1.3% 과소로 남았다. 통계는 정확값이 아니다.

## 2. 자동 재계산이 왜 막지 못했는지

### 2.1 설정과 상태 관측 (전부 읽기 전용, DB 시각 기준)

- `SHOW VARIABLES LIKE 'innodb_stats%'` 실측: `innodb_stats_auto_recalc` ON, `innodb_stats_persistent` ON, `innodb_stats_persistent_sample_pages` 20, `innodb_stats_transient_sample_pages` 8, `innodb_stats_on_metadata` OFF.
- `information_schema.TABLES` 실측: 두 테이블의 `CREATE_OPTIONS` 가 빈 문자열이라 개별 `STATS_AUTO_RECALC`, `STATS_SAMPLE_PAGES` 재정의가 없다. 전역 기본값을 그대로 상속한다.
- `mysql.innodb_table_stats` 실측: `last_update` 2026-09-10 16:04:24, `n_rows` 6,377,745 과 3,388,123. DB 시각(`SELECT NOW()`) 2026-09-10 23:10 과 대조하면 코디네이터의 2026-09-11 갱신이 반영된 값이다.
- `mysql.innodb_index_stats` 실측: `bid_results` 전 인덱스의 `last_update` 가 같은 시각으로 함께 갱신됐다.
- 배경 확정값: 갱신 전 `last_update` 는 2026-09-01 이었다.

### 2.2 가설 판정

| 가설 | 판정 | 관측 근거 |
| --- | :---: | --- |
| 자동 재계산이 꺼져 있었다 | 기각 | 전역 ON 이고 테이블별 재정의가 없다 |
| 일시(transient) 통계를 쓰고 있었다 | 기각 | 전역 persistent ON 이고 `innodb_table_stats` 행이 존재한다 |
| 변경분이 10% 임계에 못 미쳤다 | 기각 | 공고 테이블 드리프트 139.8% 는 임계를 한참 초과한다 |
| 히스토그램이 바뀌었다 | 기각 | `COLUMN_STATISTICS` 0행이다 (`docs/analysis/ax2_plan_instability_20260911.md` 2.1절) |
| 백그라운드 재계산이 발화하지 않았거나 반영이 누락됐다 | 미확정 | 설정은 정상이므로 남은 자리는 런타임 층이다. 후보는 dict_stats 백그라운드 처리 지연, 컨테이너 재시작 시 메모리 변경 카운터 소실, 대량 적재 트랜잭션과 임계 판정 시점의 어긋남이다. 설정 조회만으로는 확정할 수 없어 미확정으로 남긴다 |

### 2.3 판정

설정 오구성이 원인이 아니다. 자동 재계산은 best-effort 성격의 백그라운드 동작이라 발화를 보장하지 않는데, 그 동작에 의존하면서 신선도를 점검하는 장치가 없었던 것이 방치의 구조적 원인이다. 그래서 이 Task 의 핵심 산출물은 정책 문장이 아니라 점검 실행기이며, 본 문서는 그 실행기를 언제 어떻게 쓰는지 설명한다.

## 3. 신선도 점검 실행기

정본: `scripts/check_mysql_stats_freshness.py`, 검증: `tests/test_mysql_stats_freshness.py`.

### 3.1 사용 절차

```sh
# 경과일만으로 점검 (기준 행 수 없이)
uv run python scripts/check_mysql_stats_freshness.py

# 기준 행 수까지 대조 (편차율 계산 포함)
uv run python scripts/check_mysql_stats_freshness.py --expected-rows "bid_results=3431580,bid_announcements=5504119"

# 기계 판독
uv run python scripts/check_mysql_stats_freshness.py --expected-rows "..." --json

# 임계 조정
uv run python scripts/check_mysql_stats_freshness.py --max-drift-pct 25 --max-stale-days 3
```

종료 코드는 정상 0, 임계 초과 1, 도구 오류 2 이다. 통계 행이 아예 없는 테이블은 정상으로 보지 않고 `MISSING` 으로 판정해 종료 코드 1 을 낸다. 기준 행 수를 주지 않으면 편차율은 계산하지 않고(`-` 표시) 경과일로만 판정한다. 기준 행 수는 데이터가 계속 늘므로 고정값이 아니라 코디네이터가 확정하는 값이며, 확정값이 없으면 경과일 판정만 쓴다.

### 3.2 임계 근거

- 편차율 기본 25%: 표본 추정 잡음을 상회한다. 갱신 직후에도 공고 테이블 통계는 실제 대비 15.9% 과대였고 자동 재계산 임계는 10% 이다. 25% 면 추정 잡음에 오탐 없이 실제 방치 규모(실행기 공식으로 58.3%, 문서 1절 표기로는 139.8%)를 확실히 검출한다.
- 경과일 기본 3일: 수집 크론이 매일 02:00 에 적재하므로 사흘 연속 미갱신이면 드리프트가 누적되는 구조이다. 열흘 방치를 사흘째에 검출한다.

### 3.3 읽기 전용 근거

실행기는 `SELECT NOW()` 와 `SELECT ... FROM mysql.innodb_table_stats ...` 두 문장만 내며 `scripts/db_readonly_query.py` 의 파서 검사(`assert_read_only`)와 `READ ONLY` 트랜잭션(`run_query`)을 그대로 재사용한다. 통계 갱신 명령을 포함한 어떤 쓰기도 실행하지 않고 파일도 쓰지 않으며 결과는 표준출력으로만 낸다. 재사용을 직접 임포트 대신 조회 경로의 지연 임포트로 한 이유는 그 모듈의 임포트가 DB 설정을 요구해 단위 테스트까지 DB 의존이 번지는 것을 막기 위함이다. 읽기 전용을 코드로 확인한 뒤 `scripts/orca_auto_approve.py` 의 `UV_RUN_ALLOWED_SCRIPTS` 에 등록했다.

## 4. 갱신 주기 선택지

통계 갱신은 실행계획을 바꾸는 되돌릴 수 없는 조작이다. 주기와 실행 주체를 정하는 것은 코디네이터의 판정 사항이며, 아래는 선택지와 각각의 대가이다. 자동 실행 코드는 만들지 않았다.

### 선택지 A. 수집 크론 직후 갱신 (매일 02:00 적재 뒤)

- 대가: 실행계획이 매일 바뀔 수 있어 야간 이후의 측정 기준선이 매일 무효화된다. 측정과 갱신이 같은 날이면 그날 측치는 전날과 비교할 수 없다.
- 기준선 무효화 시점: 갱신이 실행되는 즉시.
- 적합한 경우: 드리프트 누적을 원천 차단하고 싶을 때.

### 선택지 B. 신선도 임계 초과 시에만 갱신

- 절차: 점검 실행기를 주기적으로 조회한다(읽기 전용이라 안전하다). 종료 코드 1 이 나오면 사람이 승인한 뒤 수동으로 갱신한다. 조회 자체는 기준선을 건드리지 않는다.
- 대가: 갱신 시점에 기준선이 무효화되나 빈도는 가장 낮다. 대신 임계 안의 드리프트(25% 미만)는 계속 안고 간다.
- 기준선 무효화 시점: 임계 초과 후 실제 갱신을 실행한 때. 조회만으로는 무효화되지 않는다.
- 적합한 경우: 측정 안정성과 신선도를 절충하고 싶을 때.

### 선택지 C. 사람이 판단하는 수동 절차

- 절차: 측정 기간 중에는 갱신하지 않고 기준선을 고정한다. 측정 구간이 끝나면 점검 실행기로 상태를 확인하고 필요할 때만 갱신한다.
- 대가: 방치가 재발할 수 있다. 점검이 문서 조항으로만 남으면 지켜지지 않았다는 전례가 있으므로 점검 실행 결과를 측정 시작 조건에 묶는 것이 전제이다.
- 기준선 무효화 시점: 사람이 갱신을 실행한 때.
- 적합한 경우: 비교 측정의 엄밀성이 최우선일 때.

## 5. 경고

통계를 갱신하면 그 이전의 실행계획 관찰은 전부 무효가 된다. 2026-09-11 갱신으로 `docs/analysis/ax2_plan_instability_20260911.md` 와 그 이전의 `EXPLAIN` 관찰은 옛 통계 기준이 됐으며, 이후 측정은 갱신 후 상태를 기준선으로 삼는다. 갱신 전후를 같은 표에 놓고 비교하지 않는다.
