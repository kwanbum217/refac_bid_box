## 2. 구성 변경 요약

`docker-compose.yml`의 `app` 서비스에 `command`를 추가해 `WEB_CONCURRENCY`
환경변수로 Uvicorn 워커 프로세스 수를 조정할 수 있게 했습니다. 조정 기능
자체는 유지하되, [4절](#4-실제-docker-재검증-결과와-기각-판정)의 실제 Docker
재검증 결과에 따라 **기본값은 안전값 1로 롤백**했습니다.

```yaml
command:
  - python3
  - -m
  - uvicorn
  - src.app.main:app
  - --host
  - "0.0.0.0"
  - --port
  - "8000"
  - --workers
  - "${WEB_CONCURRENCY:-1}"
```

**적용 범위와 계약:**

| 항목 | 내용 |
| --- | --- |
| 적용 서비스 | `app`만. `worker`(Arq) 서비스는 그대로이며 `WEB_CONCURRENCY`를 읽지 않습니다 |
| 기본값 | `WEB_CONCURRENCY` 미설정 시 `1` (안전 기본값, 단일 워커) |
| 수동 실험 | `.env`에 `WEB_CONCURRENCY=3`(또는 다른 값) 설정 후 `docker compose up -d app` 재기동하면 다중 워커로 켤 수 있습니다. 4절 실측상 100ms 목표를 충족하지 못하므로 **운영 기본값으로는 사용하지 마십시오** |
| 되돌리기 | `.env`에서 `WEB_CONCURRENCY`를 지우거나 `1`로 설정 후 재기동. 코드 변경 불필요 |
| 개발/테스트 직접 실행 | `Dockerfile`의 `CMD`(단일 워커, `--workers` 없음)와 `make run`(`uvicorn --reload`)은 이번 변경과 무관하게 그대로 유지 |

### 2.1 안전한 exec와 셸 확장 검증

이 절의 내용은 워커 수 기본값과 무관하게 계속 유효합니다.

- `command`가 YAML 배열(exec 형태)이므로 컨테이너 진입점은 `/bin/sh -c`를 거치지
  않습니다. 즉 `WEB_CONCURRENCY` 값이 세미콜론·파이프·백틱 등을 포함해도 셸
  메타문자로 해석되지 않고, `--workers` 뒤의 인자 하나로만 `exec()`에 전달됩니다.
- `${WEB_CONCURRENCY:-1}` 치환은 Docker Compose 자체의 파서가 컴포즈 파일을
  렌더링하는 시점에 수행하며, 컨테이너 내부 셸이 관여하지 않습니다.
- Uvicorn은 `--workers`에 정수가 아닌 값이 오면 기동 자체를 거부하므로(예외 후
  프로세스 종료), 값 오타는 명령 주입이 아니라 즉시 실패로 이어집니다.
- `Dockerfile`의 기존 `CMD`도 이미 exec 배열 형태였고 이번 변경으로 건드리지
  않았습니다.

## 3. 메모리 비용

3워커 이상은 각 프로세스가 ML 모델(LightGBM/CatBoost 등, [`src/ml/predictor.py`](../../src/ml/predictor.py)의
싱글톤 프리로딩)을 **독립적으로** 메모리에 올립니다. 프로세스 간 공유 메모리가
아니므로 워커 수에 비례해 총 메모리가 늘어납니다. 아래 수치는 측정 환경이
서로 다르므로 섞어 쓰지 않습니다.

| 항목 | 값 | 측정 환경 | 성격 |
| --- | --- | --- | --- |
| 프로세스당 RSS | 약 305~308MB | 로컬(비 Docker) 3워커 실험, 자식 프로세스 개별 측정 | 로컬 사전 추산의 근거 수치(참고용) |
| 로컬 3워커 합산 | 약 0.92GB | 위 로컬 실험값의 단순 합산(305~308MB × 3) | 로컬 사전 추산. Docker 확정값 아님 |
| Docker 단일 앱 컨테이너 기준선 | 662.5MiB | `docker stats` (1워커) | **Docker 실측** |
| Docker 3워커 앱 컨테이너 총 메모리 | **1.259GiB** | `docker stats`, 실제 재기동 3워커 | **Docker 실측** ([4절](#4-실제-docker-재검증-결과와-기각-판정)) |
| Docker 4워커 앱 컨테이너 총 메모리 | **1.603GiB** | `docker stats`, 실제 재기동 4워커 | **Docker 실측** ([4절](#4-실제-docker-재검증-결과와-기각-판정)) |

로컬 사전 추산(약 0.92GB)은 컨테이너 밖에서 프로세스 수만 바꿔 본 실험의
RSS를 단순히 더한 값이라 Docker 실측(3워커 1.259GiB)보다 낮게 나왔습니다.
Docker의 cgroup 메모리 계정 방식·공유 라이브러리 매핑이 로컬 실험과 다르기
때문으로 추정하며, 이번 작업에서 원인을 추가로 규명하지는 않았습니다.
컨테이너 `mem_limit`은 현재 `docker-compose.yml`에 설정되어 있지 않습니다.

## 4. 실제 Docker 재검증 결과와 기각 판정

1·3절의 초기 신호(로컬 실험, 로컬 메모리 추산)를 근거로 3워커를 Compose
기본값 후보로 잠정 반영한 뒤, 코디네이터가 실제 `docker-compose.yml` 앱
컨테이너를 3워커·4워커로 재기동해 재검증했습니다. 오류는 두 구성 모두
0건이었습니다.

| 워커 수 | 기동 시간 | 앱 컨테이너 총 메모리 | c1 P95 | c2 P95 | c4 P95 | c10 P95 | c10 반복 측정 | 오류 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| 3 | 12초 | 1.259GiB | 15.75ms | 18.97ms | 40.96ms | **127.32ms** | 151.82ms / 135.33ms | 0 |
| 4 | 11초 | 1.603GiB | 15.61ms | 19.43ms | 41.23ms | **165.92ms** | - | 0 |

**판정: 기각.** 목표는 c10 P95 100ms입니다. 실제 Docker 환경에서 3워커
127.32ms(반복 측정도 151.82ms/135.33ms로 100ms 문턱 아래로 안정되지 않음),
4워커 165.92ms(3워커보다 오히려 악화)로 **두 구성 모두 목표에 실패**했습니다.
1절의 로컬 신호(3워커 60.56ms)는 실제 Docker 배포 환경을 대표하지 못했다는
뜻이며, 워커 수를 늘리는 접근 자체가 이 환경(Docker Desktop의 제한된 CPU
할당 등)에서는 c10 레이턴시를 개선하지 못하고 오히려 컨텍스트 스위칭·자원
경합 비용만 늘렸을 가능성이 있습니다. 원인을 더 파고들지는 않았습니다.

이에 따라 3워커를 Compose 기본값으로 채택하려던 결정을 **철회**합니다.
`WEB_CONCURRENCY` 조정 기능 자체(2절)는 남겨 두되, 기본값은 안전한 1로
되돌리고, 3워커 이상은 필요할 때 `.env`에서 수동으로 켜서 실험하는
옵션으로만 존재합니다.

## 5. 결론과 안전 기본값

| 항목 | 현재 값 |
| --- | --- |
| Compose `WEB_CONCURRENCY` 기본값 | **1** (안전 기본값, 단일 워커) |
| 3워커 이상 | Compose 기본값 아님. `.env`의 `WEB_CONCURRENCY`로 수동 실험만 가능 |
| c10 P95 100ms 목표 | 현재 구성(1워커)에서는 여전히 미달(199.18ms, [1절](#1-배경-초기-신호--이후-실제-docker-재실측으로-기각됨)). 워커 수 증설로는 해결되지 않음이 4절에서 확인됨 |

`/predict` c10 P95 100ms 목표를 달성하려면 워커 프로세스 수 증설이 아닌
다른 접근(예: 요청 배칭, 모델 추론 경로 자체의 프로파일링, Docker 리소스
할당 조정)이 필요합니다. 이는 본 작업 범위 밖이며 별도 백로그로 남습니다.
