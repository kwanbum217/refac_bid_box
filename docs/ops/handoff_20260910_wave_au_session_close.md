## 2. compare-stats 병목 가설이 실측으로 뒤집혔습니다

**이번 세션의 가장 중요한 결과입니다.** 선행 조사의 전제가 재현되지 않았습니다.

| 항목 | 선행 조사(AT4)의 주장 | 이번 실측 |
| --- | --- | --- |
| 원형 `IN` 의 실행계획 | `type=ALL`, `bid_results` 약 311만 행 전체 스캔 | `ix_bid_results_dt_cat` **range 스캔** |
| 이 쿼리의 비중 | 캐시 미적중 6.5초의 **1순위 병목** | 약 **0.9초** |
| `EXISTS` 전환 효과 | 예상 행 311만 -> 72만 | 평균 914.0ms -> 902.0ms, **개선 없음** |

`EXPLAIN ANALYZE` 3회 교차 실행값입니다. 원형 903/943/896ms, EXISTS
960/892/854ms. COUNT 는 양쪽 327,686 으로 동일합니다.

### 2.1 그래서 무엇을 했는가

`EXISTS` 전환 자체는 병합했습니다. 근거는 성능이 아니라 **의미 보존과 회귀
안전**입니다. 리뷰어도 같은 기준으로 병합 가능 판정을 냈습니다. 중복 낙찰행에서
매칭 건수가 부풀지 않는다는 것을 테스트로 고정했으므로, 나중에 누군가 `JOIN`
으로 다시 쓰는 것을 막아 줍니다.

**이 변경을 성능 개선으로 인용하지 마십시오.**

### 2.2 남은 것

- 추정과 실측이 갈린 원인이 미확정입니다. 리뷰어가 bind 값 차이와 버퍼풀
  설명을 기각했고 나머지는 미확정으로 남겼습니다.
- 6.5초의 실제 구성비를 다시 규명해야 합니다. 매칭 쿼리가 0.9초라면 나머지
  5.6초는 월별 두 회와 기관별 상위 10 에 있습니다. 그 셋은 `Using temporary;
  Using filesort` 이며 예상 행이 74만에서 104만입니다.
- `EXISTS` 와 원형이 NULL, 빈 문자열, 중복 공고번호에서 갈리는지는 실행 대조로
  확인하지 않았습니다. 코드 수준 동등성 추론과 한 시점의 COUNT 일치까지입니다.

## 3. RAG 정형 경로 SQL 구간 계측 (완료, 측정 미실행)

`sql_ms` 90초의 구성비를 분리할 수 있는 계측을 넣었습니다. **측정은 아직입니다.**

기록되는 값입니다.

| 필드 | 의미 |
| --- | --- |
| `segments` | 캐시 조회, 각 집계 호출, `_top_rows`, `corrupted_probe`, 결과 조립의 구간별 ms |
| `cursor_ms`, `cursor_count` | SQLAlchemy 커서 실행 시간 합계와 횟수 |
| `total_ms` | `retrieve_structured_data` 전체 소요 |
| `residual_ms` | `total_ms - cursor_ms`. **connection checkout 대기와 파이썬 부수 비용** |

`residual_ms` 가 핵심입니다. 90초 중 커서 실행이 얼마이고 대기가 얼마인지를
이 값 하나로 가릅니다.

**기본 비활성입니다.** `LATENCY_SEGMENT_LOGGING` 이 거짓이면 수집기도 리스너도
동작하지 않습니다. 켜면 기존 `rag_engine_latency` 로그와 같은 `trace_id` 로
결합됩니다. 사용법은
`docs/analysis/au2_structured_sql_instrumentation_20260910.md` 입니다.

**다음 측정 대상은 q03/q08/q25/q31 네 문항뿐입니다.** 전량 fixture 를 돌릴
