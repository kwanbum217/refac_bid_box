> **선행**: [`orca_v2_reviewer_plane_20260815.md`](orca_v2_reviewer_plane_20260815.md) — 첫 실사용에서 실재 결함 3건을 놓치고 `pass`

## 1. 설계

첫 실사용 실패 후 개선 후보 4개를 세웠고, 그중 계약 변경 두 개를 구현해 감도
시험으로 효과를 측정했습니다. **모델 효과를 함께 분리하려고 2x1 로 설계했습니다.**

| 축 | 비교 |
| --- | --- |
| 계약 효과 | 첫 실사용(서술형) 대 S1(체크리스트). **같은 모델** |
| 모델 효과 | S1(Gemini 3.7 Flash High) 대 S2(Claude Opus 4.6 Thinking). **같은 계약** |

### 1.1 심은 결함

`scripts/_seeded_review_probe.py` 에 결함 6개를 심고 **4개만 체크리스트로 묻고
2개는 숨겼습니다.** 묻지 않은 것을 찾는지가 자유 발견 능력입니다.

| ID | 결함 | 체크리스트 |
| --- | --- | --- |
| D1 | `\D` 정규식이 줄바꿈을 넘어 매칭 | C2 |
| D2 | `subprocess.run` 에 `timeout` 없음 | C1 |
| D4 | `read_bytes()` 길이를 문자 예산과 비교 | C4 |
| D5 | 대상 파일 부재를 `continue` 로 넘겨 성공 반환 | C3 |
| **D3** | `int()` 의 `ValueError` 미포착. `except` 가 `CalledProcessError` 만 | **숨김** |
| **D6** | `summarize([])` 가 IndexError. 백분위도 선형 보간 관례 위반 | **숨김** |

D1·D2·D4·D5 는 **첫 실사용에서 Reviewer 가 놓친 결함과 같은 종류**입니다.

## 2. 결과

| 지표 | 첫 실사용 (v2.0 서술형) | S1 Gemini 3.7 Flash High | S2 Claude Opus 4.6 Thinking |
| --- | --- | --- | --- |
| `verdict` | `pass` | **`fail`** | **`fail`** |
| 체크리스트 정확도 | 항목 없음 | **4/4** | **4/4** |
| 자유 발견 (D3, D6) | — | **1/2** (D6) | **1/2** (D6) |
| 놓친 실재 결함 | **3건** | 1건 (D3) | 1건 (D3) |
| 오탐 | 0 | **0** | **0** |
| `read_files` 초과 | 0 | 0 | 0 |

### 2.1 계약 효과 — 확인됨

**같은 모델이 계약만 바꿔서 0/3 에서 4/4 로 갔습니다.** 첫 실사용에서 Gemini 3.7
Flash High 는 서술형 우선순위를 받고 실재 결함 3건을 전부 놓치고 `pass` 를
냈습니다. 체크리스트를 주자 4개를 모두 잡고 `fail` 을 냈습니다.

**모델을 바꾸지 않고 얻은 결과이므로 계약 변경의 순효과입니다.**

### 2.2 모델 효과 — 검출에서는 차이 없음

두 모델의 체크리스트 정확도, 자유 발견, 오탐이 **완전히 같습니다.** D3 도 둘 다
놓쳤습니다.

보고 형태에는 차이가 있었습니다.

| 항목 | S1 | S2 |
| --- | --- | --- |
| `blocking_issues` 구조 | 문자열 1건 (자유 발견만) | **dict 5건.** `file`/`description`/`severity` |
| 체크리스트 결함의 `blocking_issues` 반영 | 없음 | **전부 반영** |
| 심각도 분류 | 없음 | high 2, medium 3 |

**S2 의 보고가 코디네이터에게 더 유용합니다.** 결함이 한 곳에 모이고 우선순위가
붙습니다. 다만 이것은 형식 품질이며 검출 능력 차이가 아닙니다.

계약 §4.1.2 조건 3("결함을 시사하는 answer 가 있으면 대응하는 `blocking_issues`
항목이 있다")을 엄격히 적용하면 **S1 은 미달**입니다. C1·C2·C3·C4 에서 결함을
확인했는데 `blocking_issues` 에 옮기지 않았습니다.

## 3. 코디네이터 재현 검증

두 Reviewer 의 `evidence` 를 직접 재현했습니다. **보고를 판정 근거로 쓰지 않는
원칙을 이 측정에도 적용했습니다.**

| 주장 | 재현 결과 |
| --- | --- |
| C2 — `\D` 가 줄을 넘어 `def1234` 를 잡음 | `def1234` 일치 |
| C3 — 없는 파일만 주면 성공 반환 | `(True, '예산 이내')` 일치 |
| C4 — 한글 3,000자가 9,000바이트 | 문자 3000 / 바이트 9000 일치 |
| D6 — 빈 리스트에서 IndexError | `IndexError: list index out of range` 일치 |
| D3 — 두 Reviewer 가 놓침 | `except` 절에 `ValueError` 없음 확인 |

**S1 은 C2 의 재현 명령까지 보고에 넣었고 그 명령이 실제로 동작했습니다.**
`evidence` 를 요구한 §4.1.2 의 목적이 달성됐습니다.

## 4. 판정과 채택

| 우선순위 후보 | 판정 |
| --- | --- |
| 1. `review_checklist` 예/아니오 질문 | **채택.** 0/3 -> 4/4 |
| 2. `verdict: pass` 에 항목별 근거 요구 | **채택.** 재현 가능한 evidence 가 실제로 왔습니다 |
| 3. seeded defect 감도 시험 | **수행.** 본 문서 |
| 4. Reviewer 를 다른 모델 계열로 | **검출 이득 없음.** 보고 형식만 개선 |
| (추가) 계약 조건의 기계 검증 | **채택.** `scripts/validate_review_report.py`. 5.1 에서 손으로 놓친 것 2건을 추가 검출 |

### 4.1 모델 배정 권고

**검출 성적이 같으므로 Reviewer 에 비싼 모델을 쓸 근거가 없습니다.**
Antigravity Claude 계열은 허용량이 적으므로 **Reviewer 기본은 Gemini 3.7 Flash
High** 로 둡니다.

단 §4.1.2 조건 3 준수는 S2 가 나았으므로, S1 계열을 쓸 때는 **체크리스트에서
확인한 결함을 `blocking_issues` 에도 반드시 옮기라고 사양에 명시**하십시오.

### 4.2 남는 한계 — 묻지 않은 것은 절반만 찾습니다

**두 모델 모두 D3 을 놓쳤습니다.** 체크리스트에 없던 두 결함 중 하나만 찾았습니다.

이것이 이 방식의 구조적 한계입니다. **체크리스트는 코디네이터가 아는 위험을
위임하는 수단이며, 모르는 위험까지 대신 찾아 주지 않습니다.**

따라서 설계 10장 Level 3(Coordinator Critical Review)은 여전히 필요합니다.
Reviewer 도입으로 줄어드는 것은 **알려진 위험 항목의 확인 비용**이고, 미지의
결함 탐색 비용은 그대로 남습니다.

## 5. 운영상 발견 — 복잡한 JSON 은 셸을 통과하지 못합니다

S2 가 `orca orchestration send --body '<JSON>'` 으로 보고하려다 **셸 이스케이프
문제로 실패**했고, JSON 을 파일로 쓴 뒤 그 경로를 알리는 방식으로 우회했습니다.

`ORCA_REVIEW_DONE_V2` 의 `blocking_issues` 가 중첩 dict 이면 인용 부호가 겹쳐
`--body` 로 전달하기 어렵습니다. 설계 8.1 이 "worker_done 은 인덱스이고 긴 내용은
artifact 로" 라고 정한 원칙이 **리뷰 보고 자체에도 적용돼야 합니다.**

계약에 `report_path` 를 두어 상세는 파일로 남기고 `--body` 에는 최소 요약만
넣도록 [`orca_task_capsule_v2.md`](orca_task_capsule_v2.md) 4.1.3 을 추가했습니다.

## 5.1 기계 검증을 붙이면서 추가로 드러난 것

조건 1~4 를 판정하는 `scripts/validate_review_report.py` 를 만들어 실제 보고에
돌린 결과 **손으로는 놓쳤던 것 둘이 더 나왔습니다.**

| 발견 | 내용 |
| --- | --- |
| S1 의 보고가 **유효한 JSON 이 아님** | 정규식 설명의 `\D` 를 그대로 써 이스케이프가 깨졌습니다. 파싱 자체가 실패합니다 |
| 두 Reviewer 모두 `blocking_issues` 에 **체크리스트 `id` 를 넣지 않음** | `file:line` 만 적어 어느 항목에 대한 것인지 기계로 이을 수 없습니다 |

첫째는 4.1.3 `report_path` 를 쓰면 사라집니다. 인라인 `--body` 로 중첩 JSON 을
보내는 것이 원인입니다.

둘째는 계약 조건 3 에 **`id` 포함 요구를 명시**해 해소했습니다. 이 요구가 없으면
"대응하는 `blocking_issues` 항목이 있다" 를 사람만 판단할 수 있습니다.

### 5.2 검증기가 조용히 통과하지 않습니다

이번 시험에 쓴 Capsule 두 개는 `defect_when` 이 없던 시점에 작성됐습니다. 검증기를
그 Capsule 로 돌리면 **"조건3 판정 불가: C1 에 defect_when 이 없어 극성을 알 수
없음"** 으로 막힙니다. 통과로 넘기지 않습니다.

극성이 항목마다 다르기 때문입니다. "timeout 이 있는가" 는 `no` 가 결함이고
"줄을 넘는가" 는 `yes` 가 결함입니다. 이 정보 없이 조건 3 을 판정하면 반대로
읽습니다.
