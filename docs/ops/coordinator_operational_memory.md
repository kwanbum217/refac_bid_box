## 1. 도구 계약 (가장 자주 걸리는 것)

| 사실 | 내용 |
| --- | --- |
| 정본 스킬 재독 | `orca skills get orchestration` 을 조율 시작 전에 읽는다. 저장소 스킬은 "이 저장소에서 그 도구를 어떻게 쓸지에 대한 합의"일 뿐이고 도구 계약은 정본에만 있다. 2026-09-01, 09-02 두 세션 연속 실패 |
| `dispatch --inject` | **의도적으로 비감독.** `worker_dispatches` 행을 만들지 않고 `worker-release` 가 `no_owned_resource` 로 돌아온다. 골랐으면 인수인계에 적는다 |
| `check --ack` | 개별 `msg_...` 가 아니라 **`deliveryId`** 를 넘긴다. 오류 문구 `does not belong to this Run` 이 Run 문제처럼 읽히지만 식별자 종류가 틀린 것이다. FIFO 이므로 비어질 때까지 소진한다 |
| `dispatch` exit 3 | `terminal_not_settled` 는 **오탐**이다. 판정이 Dispatch 전에 이뤄지고 재확인이 없다. `orca terminal read` 로 도달을 직접 확인하고 진행한다 |
| `terminal close --tab` | **금지.** 워커 창이 코디네이터와 같은 탭의 분할 창일 수 있다. 창 단위로만 닫는다 |
| `worker-start --agent` | `claude`, `codex`, `cursor` 만 받는다. Antigravity·OpenCode·Qwen·Grok·Kimi 는 `terminal create` 후 `--terminal` 로 붙인다 |
| 두 점 diff | `git diff main..HEAD` 는 브랜치가 갈라진 뒤 main 에 들어온 커밋까지 섞어 보여 준다. 브랜치 변경만 보려면 `main...HEAD` 세 점 |

## 2. Capsule 작성 (여기서 틀리면 워커가 통째로 헛돈다)

| 규칙 | 이유 |
| --- | --- |
| 전량 테스트에 `-m 'not data_assets'` 를 반드시 붙인다 | 빠뜨리면 격리 워크트리에서 `test_model_bin_files_exist` 와 `test_chroma_db_exists` 가 실패하고, 워커가 `model.bin` 을 심볼릭 링크로 끌어오거나 `rm` 승인을 요청한다 |
| `review_checklist` 의 `defect_when` 은 `yes`/`no` 극성 문자열 | 산문을 적으면 게이트 5가 못 읽는다. 항목 키는 `id`·`question`·`defect_when` |
| 리뷰 Capsule 의 id 는 빌더 Capsule 과 **정확히 일치** | 게이트 5는 id 집합, `defect_when` 극성, `answer` 의 yes/no 세 가지를 모두 본다. 하나라도 다르면 정상 판정이 결함으로 읽힌다 |
| `escalate_when` 에 사실 불일치 조항 | `ground_truth` 가 틀릴 수 있다. "호출부는 3곳" 이 실제로 4곳이었고 이 조항 덕에 드러났다 |
| `ground_truth` 에는 **코드를 열어 확인한 사실만** | 증상에서 역추론한 가설을 "재조사 불필요" 로 못박으면 워커가 검증 없이 전제로 삼는다. 2026-09-05 에 실제로 틀린 전제를 심었다 |
| 워커 경로는 전부 **워크트리 상대 경로** | 절대 경로를 주면 워커가 주 저장소로 이동한다. 2026-08-23 에 CLI 4종 워커가 전부 이동했고 하나는 거기서 브랜치를 만들어 병합 2건이 엉뚱한 곳에 쌓였다 |
| DB 조회는 `scripts/db_readonly_query.py` 만 | `docker exec ... mysql` 형태는 자동 승인 화이트리스트 밖이라 질의마다 사람 승인을 기다린다. 허용 형태만 적지 말고 **금지 형태와 이유를 함께** 적는다 |

### 표준 조항 두 개 (복사해 쓸 것)

```
- "코디네이터 확정 계약이다. 요구하지 않은 API 표면을 늘리지 말라. 별칭 상수,
   호환용 kwargs 우회, 서브커맨드 별칭, 위치 인자를 임의로 추가하지 말라."
- "코디네이터 확정 계약이다. 보고할 때 검증 명령의 건수를 마지막 커밋 기준 실제
   실행 결과 그대로 적어라. 부분 실행 결과를 전량으로 적으면 계약 위반이다.
   worker_done 은 정확히 한 번만 보내라."
```

2026-09-08 에 이 조항을 넣기 전에는 워커가 호출부 없는 별칭과 `**kwargs` 우회를

코디네이터의 게이트 실행을 무효로 만들었습니다. 넣은 뒤로 재발이 없었습니다.

## 3. 워커 감시 (사용자가 먼저 발견하면 코디네이터 실패)

| 사실 | 내용 |
| --- | --- |
| 배경 감시기 수명 | `nohup ... &` 로 띄우면 Bash 도구 호출이 끝나는 순간 함께 죽는다. 프로세스 수를 확인한다 |
| 경보 도달 경로 | 로그 파일에만 적으면 아무에게도 도달하지 않는다. 정체 시 **종료**하는 형태로 만들어 알림이 오게 한다 |
| Antigravity 신뢰 대화창 | 절대경로 단위라 새 워크트리마다 다시 묻는다. `terminal create` 전에 `scripts/orca_trust_worktree.py` 로 등록 |
| `AI: Out of credits` | **차단이 아니다.** Google AI Pro 구독이라 크레딧 0이어도 동작한다. 언급하지 말 것 |
| agy 스플래시 정체 | `agy` 를 직접 띄우면 `Checking for updates...` 에서 멈춘다. 인증 문제가 아니다. 런처(`orca_agy_launch.py`) + preamble 주입이 정본 |
| kimi·qwen·claude·opencode·grok | 전부 런처를 `--command` 로 지정해 띄운다. `terminal send` 로 CLI 를 직접 실행하면 워커 행이 안 생겨 사용자가 진행을 못 본다 |
| 정체 판정 | 커밋 수와 미커밋 변경 수로 본다. 터미널 폴링은 정보량 대비 가장 비싸다 |
| 워커의 `succeeded` | 믿지 않는다. 커밋 수 0이면 병합 대상이 없다는 뜻이다 |

**자동 승인 화이트리스트 밖 명령**(사람 개입 필요): `pgrep`, `pkill`, 환경변수 접두
명령(`FOO=bar cmd`), `git add`, `git commit`, `orca ...`, CLI `--help`.
Capsule 에 명령 형태를 지정하기 전에 승인 대상인지 확인하십시오.

## 4. 병합과 검증

| 규칙 | 이유 |
| --- | --- |
| `premerge --record` 는 **워커 워크트리에서** | 증거의 `commit` 이 `MERGE_HEAD` 와 정확히 일치해야 한다. 주 저장소에서 돌리면 거부된다. 워크트리를 지우기 전에 만든다 |
| `source_commit` 갱신 | HEAD 보다 5커밋 초과로 뒤처지면 **모든 브랜치의 테스트가 실패**한다. 병합 커밋에서 함께 갱신한다 |
| 인수인계의 테스트 수치 | 근거로 삼지 말고 착수 시 직접 기준선을 잡는다. 2026-09-01 에 "2,928건 통과" 가 실제로는 실패 27건이었다 |
| 감사 보고서 | 기준 커밋을 먼저 확인한다. 2026-08-31 Grok 보고서가 838커밋 뒤처져 10건 중 8건이 이미 수정 완료였다 |
| 측정 중 저장소 동결 | 측정이 도는 동안 커밋·병합·브랜치 조작 금지. 2026-08-26 에 병합 한 번이 20분치 측정 72회차를 폐기시켰다 |
| 코디네이터가 검증 대상 브랜치에 커밋 금지 | 리뷰가 끝난 브랜치에 코드를 올리면 게이트 6이 보고 건수 불일치로 실패하고, 그 커밋은 아무도 리뷰하지 않은 채 병합된다. 작아 보여도 별도 Task 로 낸다 |
| `docs/` 에서 `.orca/` 링크 금지 | gitignore 대상이라 격리 워크트리에 없어 링크 검증이 실패한다. 인라인 코드로 참조한다 |
| `git branch -D` 금지 | `-d` 가 거부하면 아직 병합되지 않은 것이다. 삭제 전 `git log --oneline main..<branch>` 를 읽는다 |
| `rework` 유사 이름 Capsule | `.orca/capsules/<원본id>_rework/` 를 만들고 `allowed_read_files` 첫 줄에 넣는다. 워커가 그쪽으로 이탈하므로 투입 전에 양쪽에서 삭제한다 |

## 5. 병렬 세션 안전

이 저장소는 여러 에이전트 세션이 **동시에** 작업하는 경우가 있습니다.

- `git add -A` 금지. 변경한 경로를 명시적으로 나열한다
- `git stash` 금지. 상대 세션의 미커밋 변경까지 치운다
- `git add` 직전에 `git status --short --branch` 로 HEAD 브랜치를 확인한다. 2026-08-06 에 30분 뒤 HEAD 가 상대 브랜치로 바뀌어 있었다
- 컨테이너와 브랜치를 임의로 정리하지 않는다
- 테스트 실패는 단독 재실행으로 격리해 원인을 가른다

## 7. 워커 모델 배정

- 기본은 빌더 Antigravity Gemini, 리뷰어는 다른 계열(Qwen `qwen3.7-plus` 또는 Grok)
- 한쪽 풀이 마르면 등급을 낮추기 전에 **다른 풀의 같은 등급**을 먼저 확인한다
- **CLI 마다 가용성이 따로 논다.** 같은 모델이 두 CLI 에 있어도 한쪽에서만 사라진다. 모델 이름으로 판정하지 말고 쓸 CLI 로 직접 probe 한다
- 목록 이탈과 1회 실패를 소멸로 단정하지 않는다. 조치 없이 복구된 사례가 있다
- 무료 풀은 쓰기 과제에 쓰지 않는다. 리뷰어에도 열지 않는다
- 배정 정본은 `scripts/orca_model_router.py` 의 `TIER_POLICY` 이며 문서는 사본을 두지 않는다

## 8. 규칙은 문서가 아니라 게이트로 강제한다

**이 저장소에서 실제로 지켜진 규칙은 전부 종료 코드로 거부되는 것들입니다.**
문서 조항으로만 둔 규칙(정본 재독, 병합 전 전량 테스트)은 둘 다 깨졌습니다.

새 규칙을 만들 때는 설명으로 끝내지 말고 **`scripts/orca_taskctl.py dispatch` 나
pre-commit 이 거부하는 형태**로 제출하십시오. 사용자가 2026-09-02 에 같은 것을
세 번 물었습니다.

기계로 강제되고 있는 것: 동시 쓰기 3대 상한, 완료 세션 잔류 회수, 승인 감시기 부착,
전량 테스트 증거와 `MERGE_HEAD` 일치, 커밋 메시지 한국어, `source_commit` 신선도,
리뷰 체크리스트 id 일치, 워커 보고 진실성(재실행 대조).
