# 호스트 DB 이중화 제거

> **작성일**: 2026-08-09
> **버전**: v1.0.0
> **상태**: 완료. 잔여 결정 1건(호스트 MariaDB LaunchAgent 처리)
> **대상**: 개발 호스트의 `DATABASE_URL`
> **측정 스크립트**: [`scripts/compare_host_container_db.py`](../../scripts/compare_host_container_db.py)

---

## 1. 문제

`AGENTS.md` 는 MySQL 8 Docker 통일과 이중화 제거를 규정합니다. 그런데 실제
환경은 둘로 갈려 있었습니다.

| 경로 | 대상 DB |
| --- | --- |
| 호스트 `.env` (스크립트·측정) | 로컬 MariaDB `127.0.0.1:3307` |
| 컨테이너 `app` / `worker` (운영) | MySQL 8 Docker `db:3306` |

**호스트에서 잰 값이 운영 경로와 다른 DB 를 봅니다.** 오류가 나지 않고 숫자만
달라지므로 조용히 틀립니다. KB 커버리지 작업에서 `source_bid_count` 가
499,195 대 500 으로 갈린 것이 그 사례입니다.

---

## 2. 전환 전 대조

전환하면 호스트 스크립트가 보던 DB 가 바뀝니다. **한쪽에만 있는 행이 있으면
데이터 무손실(G1)이 깨지므로** 먼저 대조했습니다. 읽기만 했습니다.

### 2.1 행 수

31개 테이블 중 8개가 달랐습니다.

| 테이블 | 호스트 3307 | 컨테이너 3306 | 차이 |
| --- | ---: | ---: | ---: |
| `bid_announcements` | 5,461,079 | 5,461,126 | **+47** |
| `bid_results` | 3,405,928 | 3,405,950 | **+22** |
| `institution_win_rate_stats` | 38,765 | 35,408 | -3,357 |
| `bid_ranking_snapshots` | 152 | 142 | -10 |
| `chat_session_states` | 7 | 22 | +15 |
| `pipeline_executions` | 7 | 10 | +3 |
| `accounts_customuser` | 2 | 4 | +2 |
| `servc_inst_verify` | (없음) | 1,077,789 | 검증용 임시 테이블 |

최신 시각도 컨테이너가 앞섭니다. `bid_announcements` 는 호스트 2026-08-03,
컨테이너 2026-08-08 입니다. **운영 수집이 컨테이너에만 반영되고 있었습니다.**

### 2.2 원본 테이블은 연도별로도 컨테이너가 우위입니다

행 수 합계만으로는 "호스트에만 있는 행"을 배제하지 못합니다. 연도별로
갈랐습니다.

| 테이블 | 컨테이너가 적은 연도 | 차이가 나는 연도 |
| --- | ---: | --- |
| `bid_announcements` | **0개** | 2026년 +47 |
| `bid_results` | **0개** | 2026년 +22 |

**모든 연도에서 컨테이너 ≥ 호스트이고, 차이는 최근 수집분뿐입니다.** 호스트
에만 있는 원본 행이 없으므로 전환해도 손실이 없습니다.

### 2.3 호스트가 많았던 두 테이블은 파생입니다

`institution_win_rate_stats` 와 `bid_ranking_snapshots` 는 원본이 아니라
`bid_results` / `bid_announcements` 에서 만든 **사전 집계**입니다. 재생성으로
복구됩니다.

### 2.4 스키마 차이는 표기뿐입니다

`bigint(20)`(MariaDB) 대 `bigint`(MySQL 8) 표시 차이 5건이 전부입니다. MySQL
8.0.19 부터 정수 표시 폭이 폐지된 결과이고 실제 타입은 같습니다.

## 3. 조치

### 3.1 호스트 `DATABASE_URL` 을 컨테이너 DB 로

`.env` 의 `DATABASE_URL` 을 `127.0.0.1:3306` 으로 옮겼습니다. Docker `db`
서비스가 3306 을 호스트로 공개하므로 호스트 스크립트도 같은 DB 를 봅니다.

**계정이 다릅니다.** 포트만 바꾸면 인증에서 막힙니다. 컨테이너 MySQL 은
`docker-compose.yml` 의 `db` 서비스 설정을 씁니다.

전환 후 확인: MySQL 8.0.46, 공고 5,461,126행, 결과 3,405,950행.

### 3.2 뒤처진 파생 집계 재생성

전환 과정에서 **컨테이너의 기관 집계가 2026-08-02 이후 갱신되지 않은 것**을
발견했습니다.

| 항목 | 값 |
| --- | ---: |
| 재생성 전 | 35,408행 / 갱신 시각 2026-08-02 10:42 |
| 재생성 후 | **38,765행** / 2026-08-09 05:15 |
| 증감 | +3,357행 (115초) |

**이것은 서빙에 영향이 있었습니다.** 추론 경로는 이 표를 유니크 키로 조회하고,
없는 기관은 이력 없음으로 처리돼 예측이 기본값 쪽으로 끌려갑니다. 오류가 나지
않으므로 화면만 보면 알 수 없습니다. 재생성 후 값이 호스트 MariaDB 와 정확히
일치했습니다.

순위 스냅샷도 함께 재집계했습니다(142행).

### 3.3 수동 재생성 경로 추가

순위 스냅샷에는 `make rebuild-rankings` 가 있는데 기관 집계에는 없었습니다.
같은 상황이 반복되므로 추가했습니다.

```bash
make rebuild-institution-stats
```

**이 작업은 컨테이너 안에서 돌리십시오.** 기관 집계는 지수감쇠 계산에
`bid_results` 340만 행을 읽는데, 호스트에서 3306 으로 붙으면 전송 중
`Lost connection to MySQL server` 로 끊깁니다.

```bash
docker exec refac_bid_box-worker-1 python scripts/rebuild_institution_stats.py
```

## 4. 남은 결정

**호스트 MariaDB(3307)를 어떻게 할 것인가는 담당자 결정입니다.**

이 인스턴스는 `~/Library/LaunchAgents/local.bidbox.mariadb.plist` 로 등록된
상시 서비스이고 `KeepAlive` 가 걸려 있어 프로세스를 죽여도 즉시 재기동합니다.
멈추려면 `launchctl bootout` 으로 등록을 해제해야 하는데, 이는 되돌리기가
번거로운 변경이라 손대지 않았습니다.

| 선택지 | 내용 | 유의 |
| --- | --- | --- |
| 그대로 둔다 | 포트만 겹치지 않으면 무해 | 실수로 3307 을 보는 설정이 다시 생길 수 있음 |
| LaunchAgent 해제 | `launchctl bootout gui/$UID/local.bidbox.mariadb` | 데이터는 남습니다. 되돌리려면 재등록 필요 |
| 데이터까지 정리 | datadir 삭제 | **권하지 않습니다.** 마지막 대조 지점이 사라집니다 |

**당분간 그대로 두기를 권합니다.** 이번 대조에서 호스트 MariaDB 가 기관 집계의
정답(38,765행)을 들고 있었습니다. 컨테이너가 뒤처졌을 때 비교할 기준이
있는 편이 낫습니다.

## 5. 확인 방법

```bash
.venv/bin/python scripts/compare_host_container_db.py
```

이중화가 해소된 상태면 첫 줄에서 그렇게 알리고 종료합니다. 다시 갈라졌다면
테이블별 차이를 출력합니다.
