### 3.5 버퍼풀을 실제로 비우자 가장 빨랐습니다

## 4. 선행 수정이 실제 경로에서 동작하지 않았습니다

**Wave AJ2 의 런처 고지문 역할 분기는 병합됐지만 동작하지 않았습니다.** 이번 세션의
리뷰어 두 대가 모두 커밋 강제 고지문을 받았고, 코디네이터가 코드로 재현했습니다.

```
빌더  TASK -> builder
리뷰어 TASK -> builder     # 리뷰어인데 builder 로 판정
```

원인은 `detect_role` 이 찾는 표지(`ORCA_REVIEW_DONE_V2`, `review_done.json`)가
**런처가 실제로 받는 preamble 에 없다**는 것입니다. preamble 은 Orca 지시문과 TASK
블록뿐이고 TASK 블록에는 objective 문장과 Capsule **경로**만 들어갑니다. Capsule
본문은 워커가 나중에 파일로 읽습니다.

**AJ2 의 리뷰가 이를 놓친 이유가 핵심입니다.** 판정 함수를 Capsule 본문 형태의
표본으로 검증했기 때문입니다. 코디네이터가 Capsule 에 "리뷰어 지시문 표본으로
판정 함수를 실행한다" 라고만 적고 **그 표본이 무엇이어야 하는지를 못박지 않은 것**이
원인입니다.

AK3 가 preamble 기록 지점에 `[ORCA_ROLE: builder|reviewer]` 표지를 넣고 `detect_role`
이 그것을 최우선 근거로 삼게 해 해결했습니다. 표지가 없으면 종전 판정으로 물러서고
확정 불가 시 `builder` 로 떨어지는 fail-closed 를 유지합니다. 병합 후 `main` 에서
직접 확인했습니다.

**교훈: 판정 함수의 검증 표본은 실제 입력이어야 합니다.** AK3 Capsule 에는 "손으로
만든 표본이 아니라 taskctl 이 실제로 기록한 preamble 을 근거로 삼으라" 를 계약으로
못박았고, 리뷰 체크리스트에도 같은 항목을 넣었습니다.

| 게이트가 아니다 | `evaluate_canonical` 목록·판정 불변. 기존 산출물 3건이 소급 무효화되지 않음 |
| 조용히 넘어가지 않는다 | 조회 실패 시 값은 `null`, 실패 사유를 함께 기록 |
| 측정을 막지 않는다 | 조회 실패해도 측정 계속 |
| 주입 가능해야 한다 | 모든 조회를 `cmd_fn` 경로로 수행 |
| 비밀이 새지 않는다 | 비밀번호는 컨테이너 내부 환경변수 참조, 산출물에는 숫자와 사유만 |

### 8.5.1 잡아낸 것 둘

**리뷰어가 죽은 단언을 발견했습니다.** 비밀 누설 검증에
`assert "password" not in text or "password" in "some_standard_field"` 형태가 있었고
뒤쪽 항이 상수 거짓이라 아무 일도 하지 않았습니다. 보호가 약해진 것은 아니나 조건이
완화된 것으로 오독됩니다. 비차단 관찰이었으나 재작업에 포함해 정리했습니다.

**게이트 6이 보고 수치의 뒤처짐을 잡았습니다.** 빌더가 전량 테스트를 3,964건으로
보고했는데 최종 커밋에서 재실행하니 3,968건이었습니다. 테스트 추가 전 시점의 수치를
적은 것이며, 코드 결함은 아니지만 **보고가 최종 상태와 어긋나면 기계 검증이 성립하지
않습니다.** 재작업에서 최종 커밋 기준으로 재실측해 해소했습니다.

### 8.5.2 AK3 가 운영에서 검증됐습니다

AL1 리뷰어 지시문에 **커밋 강제 고지문이 붙지 않았습니다.** AK3 의
`[ORCA_ROLE: reviewer]` 표지가 실제 Dispatch 경로에서 동작한 첫 운영 증거이며, 직전
두 세션에서 리뷰어가 이 고지문 때문에 질문으로 멈추던 문제가 재현되지 않았습니다.

## 8.6 세션 종료 정리에서 발견한 잔여 프로세스 결함 두 건

Docker 를 내리고 종료 점검을 하다가 발견했습니다. **저장소·데이터에 피해는 없었고
둘 다 프로세스 수명주기 문제입니다.**

### 8.6.1 자동 승인 감시기가 스스로 빠져나오지 못했습니다

닫힌 워커 터미널을 대상으로 하는 `scripts/orca_auto_approve.py` 프로세스가 **17개**
살아 있었습니다. 이 세션에서 회수한 워커 전부의 감시기이며, 터미널을 `terminal close`
로 닫은 뒤에도 종료되지 않았습니다.

사양상 대상 터미널 읽기가 연속 5회 실패하면 감시 대상에서 제외되고 전부 소진되면
자동 반환합니다. **관측된 것은 그 자기 종료가 일어나지 않았다는 사실이며, 왜인지는
조사하지 않았습니다.** 닫힌 터미널 읽기가 실패로 분류되지 않는 것인지, 실패 계수가
누적되지 않는 것인지 확인이 필요합니다.

`taskctl finalize` 가 `stop_auto_approve` 로 명시 종료하는 경로가 있으나, 이 세션은
게이트를 직접 실행하고 병합했기 때문에 그 경로를 타지 않았습니다. **런처 경로로 띄운
워커는 회수해도 감시기가 남습니다.**

정리는 살아 있는 터미널의 것만 남기고 나머지를 종료하는 방식으로 했습니다.

### 8.6.2 권한 설정 자식이 코디네이터 터미널 핸들을 들고 떴습니다

`scripts/orca_agy_launch.py --setup-permissions <terminal> <model>` 형태의 자식
프로세스가 **18개** 남아 있었고, 전부 인자로 **코디네이터 터미널 핸들**을 들고
있었습니다. 워커 터미널 핸들이어야 하는 자리입니다. 스크립트 경로는 워커 워크트리
(`wave-al1`) 아래였으므로 런처 자체는 올바른 워커 터미널에서 실행됐습니다.

`schedule_permission_setup` 은 인자로 받은 핸들이 없으면 `ORCA_TERMINAL_HANDLE`
환경변수를 씁니다. **추정 원인은 `orca terminal create` 로 워커 창을 만들 때
코디네이터의 `ORCA_TERMINAL_HANDLE` 이 그대로 상속된 것입니다. 확인하지 않았으므로
단정하지 않습니다.**

**실제 피해는 없었습니다.** 실행 중이던 `orca_auto_approve.py` 는 전부 올바른 워커
핸들을 들고 있었고, 코디네이터 터미널을 감시하던 승인기는 없었습니다. 다만 조건이
맞으면 **코디네이터 세션의 승인 대화창을 자동 승인하는 경로**가 되므로 그냥 둘
문제가 아닙니다.

### 8.6.3 후속 과제

| 내용 |
| --- |
| `orca_auto_approve.py` 가 대상 터미널이 닫힌 뒤 실제로 자기 종료하는지 확인하고, 안 되면 종료 조건을 고칩니다 |
| 런처 경로로 띄운 워커의 감시기를 `worker-release` 시점에 함께 종료하게 합니다. 지금은 `finalize` 를 타야만 정리됩니다 |
| `schedule_permission_setup` 이 상속된 `ORCA_TERMINAL_HANDLE` 을 쓰지 않도록 대상 터미널을 명시 인자로 강제합니다. 코디네이터 핸들이 들어오면 거부하는 것이 안전합니다 |

## 9. 정리 상태

**모든 자원을 회수했습니다.** 빌더 2대와 리뷰어 2대 전부 `worker_done` ack 직후
회수했습니다. 런처 경로 워커는 `worker-release` 가 `retained` 로 돌아와
`orca terminal close --terminal` 로 창 단위 종료했습니다 (`--tab` 미사용).

워크트리 `wave-ak2`, `wave-ak3`, `wave-al1` 은 `main` 병합 확인 후 제거했고 브랜치도
`git branch -d` 로 삭제했습니다. `orca_settled_session_audit.py` 는 잔류 없음입니다.

**프로세스 수준 잔여는 종료 점검에서 따로 정리했습니다(8.6 절).** Orca 기록상
회수가 끝나도 감시기 프로세스는 남을 수 있으므로, 세션 종료 시
`pgrep -f orca_auto_approve` 로 살아 있는 터미널의 것만 남았는지 확인하십시오.

**Docker 스택은 내렸습니다.** Redis 는 `SHUTDOWN NOSAVE` 로 먼저 종료한 뒤
`docker compose down` 을 실행했고, 잔여 컨테이너는 없으며 `dump.rdb` 도 생기지
않았습니다. 데이터 볼륨 3종(`mysql_data`, `redis_data`, `meilisearch_data`)은
그대로 보존했습니다.

측정 중 변경한 것은 전부 원복했습니다. `.env` 는 백업본과 완전 일치로 되돌리고
백업본을 제거했으며, `innodb_buffer_pool_dump_at_shutdown` 은 `ON` 으로 복구했습니다.
DB 데이터는 건드리지 않았고 제거한 `ib_buffer_pool` 은 페이지 ID 목록일 뿐입니다.
