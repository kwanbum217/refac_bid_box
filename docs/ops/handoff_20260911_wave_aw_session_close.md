## 2. R-25 완료: 탐침이 사라졌습니다

### 2.1 원인과 수정

스냅샷 재구축이 `if dropped:` 일 때만 마커를 써서, `get_skipped_count` 의 0 이
**마커 부재**와 **마커 값 0** 을 구분하지 못했습니다. 그래서 깨끗한 차원은
영원히 40초짜리 탐침을 돌았습니다. **데이터가 깨끗할수록 느린 구조**였습니다.

수정은 둘입니다.

- 마커를 손상 유무와 무관하게 항상 기록 (`metric_count = int(bool(dropped))`)
- `get_skipped_marker` 추가. 부재는 `None`, 존재는 `int`. 기존
  `get_skipped_count` 의 시그니처와 반환 의미는 그대로

### 2.2 확정된 효과

| 항목 | 적용 전 | 적용 후 |
| --- | ---: | ---: |
| `corrupted_probe_ms` 합계 (콜드 4건) | 144,541ms | **0ms** |
| `cursor_count` (콜드) | 11~12 | **9** |

**이 둘은 구조적 사실입니다.** 탐침 질의가 그대로 사라졌고 그것이 커서 실행
횟수 감소로 확인됩니다. 타이밍 잡음과 무관합니다.

### 2.3 확정되지 않은 것

### 2.4 효과는 마커가 있어야 납니다

측정 전에 `rebuild_ranking_snapshots(force_weekly=True)` 를 실행했습니다

탐침이 돌았습니다. **운영에서는 야간 스케줄이 이 역할을 합니다.** 마이그레이션
소급 생성은 하지 않았습니다. 점진 적용입니다.

### 2.5 리뷰어가 확인한 트레이드오프

마커는 재구축 시점의 사실이므로, 그 뒤 유입된 손상은 다음 재구축까지 안내가
지연됩니다. **허용 가능으로 판정했습니다.** 근거 셋입니다.

- 순위 값 자체는 `exclude_corrupted` 가 계속 거릅니다. 지연되는 것은 안내 문구뿐입니다.
- 옛 동작도 마커가 1 이면 탐침을 건너뛰었습니다. 스냅샷 시점 사실을 이미 신뢰하고 있었습니다.
- 야간 재구축의 `_compute_rows` 가 이미 같은 `LIMIT 1` 탐침을 돌립니다. **마커 값이 곧 실시간 탐침의 답**이므로 잃는 정보가 없습니다.

## 4. 코디네이터가 겪은 것

### 4.1 리뷰어에게 또 커밋을 시켰습니다

Wave AV 인수인계에 "리뷰어에게 커밋을 시키지 마십시오" 라고 적어 놓고, 같은
세션에서 grok 을 교정하며 "커밋하십시오" 라고 지시해 그대로 재발시켰습니다.
Level 1 게이트 2 와 6 이 또 실패했습니다.

**워커 교정 지시를 쓸 때 그 지시가 직전에 적은 금지 사항과 충돌하지 않는지
보십시오.** 이번에도 `git diff --name-only main...HEAD` 로 각 파일이 자기
Capsule 범위 안임을 직접 확인한 뒤 병합했습니다.

### 4.2 grok 이 또 이탈했습니다

`files_modified` 에 자기 산출물이 아니라 빌더 파일을, 그것도 존재하지 않는
경로(`src/ranking_snapshots.py`)로 적고 있었습니다. **화면을 미리 읽어 선제
교정해 왕복을 한 번 줄였습니다.** 판정 품질 자체는 이번에도 좋았습니다.

`worker_done.json` 과 `review_done.json` 을 둘 다 썼는데, 계약에 맞는 것은
후자입니다. Capsule 의 `report_path` 를 게이트에 넘기십시오.

### 4.3 워커가 정확한 지점에서 두 번 물었습니다

Muse Spark 가 기존 테스트 충돌과 Capsule 쓰기 범위 두 지점에서 `question` 을
올렸습니다. 둘 다 정당했고 코디네이터 판정이 필요한 사안이었습니다.

**첫 번째가 특히 좋았습니다.** "마커 0 의 해석이 기존 테스트 2건과 정면
충돌한다" 였는데, 실제로는 설계 충돌이 아니라 **테스트 대역이 마커 부재를
표현하지 못하는 문제**였습니다. `_TopRowsSession.scalar()` 가 항상 정수를
돌려주어 `marker=0` 이 두 상태를 겸했습니다. 대역 기본값을 `None` 으로 바꾸는
4줄 수정으로 해결했고 테스트 이름과 단언은 그대로입니다.

**정책을 바꾸는 Task 에는 그 정책을 고정하던 기존 기대도 함께 바뀐다는 것을
미리 적으십시오.** AT1 에서도 같은 일이 있었는데 또 놓쳤습니다.

### 4.4 Capsule 쓰기 범위는 승인과 함께 열어야 합니다

기존 테스트 수정을 승인했더니 워커의 `worker_done` 가드가 기계 검사로 거부했습니다.
승인만 하고 `allowed_write_files` 를 안 열어서입니다. 주 저장소와 워크트리
양쪽의 정본·자리표시자 Capsule 네 곳을 모두 갱신해야 합니다.
