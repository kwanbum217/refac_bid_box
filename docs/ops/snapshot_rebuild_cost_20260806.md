## 1. 배경

챗봇의 콜드 첫 질의가 약 2초입니다(`docs/design/sse_first_token_20260805.md` 4.2절). 원인은 `_snapshot_scope` 가 **날짜 필터가 붙는 순간 사전 집계 스냅샷을 포기**하고 실시간 집계로 넘어가는 데 있습니다.

"2026년", "최근" 같은 흔한 표현이 곧 날짜 필터이므로, 날짜 축을 가진 스냅샷을 미리 만들어 두면 콜드 경로가 사라집니다. 그 타당성을 재기 위해 현재 재집계 비용을 측정했습니다.

## 3. 기각 1: 날짜 축 확장

플래너가 만드는 날짜 창은 대체로 유한한 정형 집합입니다(오늘 / 어제 / 이번 주 / 지난달 / 최근 N일 / 연·월 창). 명시 날짜 쌍만 임의입니다. 따라서 정형 창 7개 정도를 축으로 두는 설계가 가능해 보였습니다.

**비용이 허용하지 않습니다.** 7개 창을 더하면 조합이 15에서 105로 늘고, 현재 조합당 33.7초 기준 재집계가 **약 59분**이 됩니다. 매일 02:00 에 한 시간을 쓰는 것은 받아들일 수 없습니다.

조합당 비용을 먼저 크게 낮추지 않는 한 이 방향은 성립하지 않습니다.

## 4. 기각 2: SQL 손상값 필터 제거

`exclude_corrupted` 는 `NOT LIKE '%<U+FFFD>%'` 를 GROUP BY 전에 전 행에 겁니다. 선행 와일드카드라 인덱스를 쓰지 못합니다. 게다가 파이썬 쪽 `is_corrupted_display_text` 가 어차피 다시 걸러내므로 중복으로 보였습니다.

**첫 측정은 3.6배 개선으로 나왔으나 오측이었습니다.** LIKE 질의를 먼저 돌려 버퍼 풀이 데워진 뒤 비교 대상을 잰 탓입니다. 순서를 뒤집고 각 2회 실행 후 2회차를 채택해 다시 쟀습니다.

| 차원 | LIKE 제거 | 현재(LIKE) | 차이 |
| --- | ---: | ---: | ---: |
| `bidwinnr_nm` | 771ms | 806ms | 4% |
| `dminstt_nm` | 1,361ms | 1,740ms | 22% |
| `bid_ntce_nm` | 163,369ms | 166,954ms | 2% |

이 정도 이득으로는 폴백 분기를 추가할 근거가 되지 않아 구현을 되돌렸습니다.

> **교훈**: 같은 테이블을 훑는 두 질의를 연달아 비교하면 앞선 질의가 버퍼 풀을 데워 뒤 질의가 유리해집니다. 순서를 뒤집어 재확인해야 합니다.

### 6.1 적용: `bid_ntce_nm` 주간 재집계 (2026-08-06)

공고명 상위 N 은 전 기간 누적 순위라 하루 만에 뒤집히지 않습니다. 위험이 가장 낮은 방안이라 이것을 적용했습니다.

**요일로 판정하지 않습니다.** 크론이 도는 시각의 시간대에 따라 건너뛰거나 두 번 도는 날이 생깁니다. 대신 **해당 차원 스냅샷의 나이**를 보고 `WEEKLY_REBUILD_INTERVAL_DAYS`(7일)를 넘었을 때만 다시 집계합니다. 시간대와 무관하게 자기교정되고, 호출부(야간 스케줄)를 손댈 필요도 없습니다.

건너뛴 차원의 기존 스냅샷은 지우지 않습니다. 지우면 조회가 실시간 경로로 떨어져 오히려 느려집니다. 한 번도 집계된 적이 없으면 주기와 무관하게 만듭니다.

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| 야간 재집계 | 506.2초 | **135.8초** |
| 감소폭 | | **73%** |

예상(3분의 1)보다 큰 폭입니다. `bid_ntce_nm` 전체 조합이 167초였고 카테고리 4개까지 더하면 370초여서, 이 차원 하나가 야간 비용의 대부분을 쓰고 있었습니다.

대가는 공고명 순위가 최대 7일 낡을 수 있다는 것입니다. 누적 순위의 성격상 답변이 달라지지 않습니다.

인덱스 추가는 되돌리기 어려운 변경이며 저장 공간에 영향을 주므로, 위 방안으로 부족할 때 검토합니다. 남은 비용의 대부분은 카테고리별 그룹핑(19~47초)이며 `(category, 이름컬럼)` 복합 인덱스가 그 지렛대입니다.

## 8. 증분 집계 타당성 판정 (2026-08-10)

6장이 "설계·구현 규모가 큼" 으로만 적고 넘긴 **증분 집계**를 판정했습니다.
3장이 남긴 과제("조합당 비용을 먼저 크게 낮추지 않는 한 날짜 축 확장은
성립하지 않는다")에 대한 답이기도 합니다.

계기는 Canva 엔지니어링 블로그의 세션 폐지 최적화 사례입니다. 12시간 윈도우를
30분 청크로 파티셔닝하고 **변경된 청크만** 다시 읽는 구조인데, 매번 전량을
다시 세는 우리 재집계와 대비됩니다. 코드 읽기와 parquet 카디널리티 측정만으로
판정했고 DB 접속이나 학습은 하지 않았습니다.

### 8.1 집계 자체는 합산 가능합니다

`_compute_rows` 의 집계는 `func.count(model.id)` 하나입니다.

```python
select(column, func.count(model.id))
  .where(exclude_corrupted(column), *scope)
  .group_by(column)
  .order_by(func.count(model.id).desc())
  .limit(SNAPSHOT_DEPTH * OVERFETCH_FACTOR)
```

**COUNT 는 합산 가능(additive)합니다.** 중앙값·백분위처럼 부분집계를 합칠 수
없는 통계는 하나도 쓰지 않습니다. 손상값 필터(`exclude_corrupted` 와
`is_corrupted_display_text`)는 행 단위 술어라 부분집계에 그대로 걸면 결과가
같고, `SKIPPED_MARKER_RANK` 플래그는 OR 로 합치면 됩니다.

### 8.2 막는 것은 `ORDER BY ... LIMIT` 입니다

저장되는 것은 전체 그룹 count 가 아니라 **상위 30개**입니다. 부분집계의 상위 N
을 합쳐도 전체의 상위 N 이 되지 않습니다.

> 어제까지 31위였던 기관이 오늘 하루 급증해 전체 1위가 될 수 있습니다. 어제
> 스냅샷에 그 기관이 없으므로 어제 상위 30 + 오늘치를 합치면 놓칩니다.

분산 top-K 의 고전적 함정입니다. 증분화하려면 **전체 그룹의 count 를 보존**
해야 하고, 그 비용은 차원의 카디널리티가 정합니다.

### 8.3 차원별 카디널리티

`data/feature_store/dataset_*.parquet` 3,060,777행 실측입니다.

| 카테고리 | 행 | 공고명 고유 | 고유율 | 수요기관 고유 |
| --- | ---: | ---: | ---: | ---: |
| Servc | 917,629 | 890,460 | 97.0% | 22,459 |
| Thng | 784,266 | 743,472 | 94.8% | 25,003 |
| Cnstwk | 1,358,882 | 1,320,178 | 97.2% | 25,079 |

| 차원 | 카디널리티 | 전체 보존 비용 | 판정 |
| --- | ---: | ---: | --- |
| `dminstt_nm` | 22,459~25,079 | 약 15만 행 | **가능** |
| `bidwinnr_nm` | 미측정 (DB 필요) | 추정 수십만 | 조건부 가능 |
| `bid_ntce_nm` | **행의 94.8~97.2%** | 약 300만 행 | **부적합** |

공고명은 고유율이 97% 입니다. 전체 그룹 count 를 보존하면 원본과 크기가 거의
같은 표가 생겨 집계의 의미가 사라집니다.

### 8.4 6.1 적용 덕분에 남은 비용은 증분화 가능한 쪽입니다

**착수 전 예상은 "증분화가 되는 차원은 싸고, 비싼 차원은 안 된다" 였으나
틀렸습니다.** 6.1 절의 주간 재집계가 이미 `bid_ntce_nm` 을 야간 경로에서
빼냈기 때문입니다.

| 시점 | 야간 재집계 | 구성 |
| --- | ---: | --- |
| 6.1 적용 전 | 506.2초 | `bid_ntce_nm` 이 370초로 대부분 |
| **6.1 적용 후 (현재)** | **135.8초** | 전부 `dminstt_nm`·`bidwinnr_nm` 카테고리별 그룹핑 |

5장 실측에서 `dminstt_nm`(Servc) 46.7초, `dminstt_nm`(Cnstwk) 42.6초,
`bidwinnr_nm`(Cnstwk) 29.0초입니다. **남은 135.8초는 전부 카디널리티가 작아
증분화가 성립하는 차원입니다.** 대상과 기법의 위치가 어긋나지 않습니다.

### 8.5 미해결 선행 조건: 데이터가 append-only 가 아닙니다

증분 집계는 과거 구간이 불변이어야 성립합니다. 그런데 공고에는 **변경공고와
재공고**가 있고(`ntce_kind_nm`), 검색 색인도 "공고 최신 차수" 를 대상으로
잡습니다.

같은 공고번호의 이전 차수가 나중에 대체되면 이미 집계에 반영된 행이 사후에
바뀝니다. 그러면 부분집계 합산이 전량 재집계와 어긋나고, **오류 없이 조용히
틀린 값**이 됩니다. 이 저장소에서 파생 집계가 뒤처져 조용히 틀렸던 사고와 같은
종류입니다.

**착수한다면 이것을 먼저 재야 합니다.** 변경 차수가 과거 집계를 실제로 뒤집는
빈도와 규모를 확인하기 전에는 구현에 들어가지 않습니다. DB 접속이 필요합니다.

### 8.6 결론

| 항목 | 판정 |
| --- | --- |
| 기술적 성립 | **부분 성립.** `dminstt_nm`·`bidwinnr_nm` 은 가능, `bid_ntce_nm` 은 부적합 |
| 대상 적합성 | 6.1 적용 후 남은 135.8초가 전부 가능 차원이라 적합 |
| 선행 조건 | 변경 차수의 과거 집계 무효화 규모 측정 (미수행) |
| **우선순위** | **낮음** |

우선순위가 낮은 이유는 7장 그대로입니다. 콜드 첫 질의는 이미 목표 안이고
야간 135.8초는 사용자가 겪는 시간이 아닙니다. 여유를 넓히는 작업입니다.

### 8.7 더 나은 대안이 있을 수 있습니다

`bid_ntce_nm` 은 증분화가 안 되지만, 애초에 이 차원을 **관계형 GROUP BY 로
푸는 것이 맞는지**가 남은 질문입니다. 실행 계획이 664만 행 전표 스캔 뒤 임시
테이블과 파일소트인데, 이는 검색 엔진의 패싯 집계가 훨씬 잘하는 작업입니다.

2026-08-09 부터 진행 중인 Meilisearch 전환이 공고명을 이미 색인 대상에 포함
합니다. 그 인덱스가 완성되고 P95 측정이 끝나면, `bid_ntce_nm` 차원을 패싯
집계로 대체할 수 있는지 검토할 가치가 있습니다. 새 인프라를 더하지 않고
주간 재집계 370초를 통째로 없앨 수 있는 경로입니다.

`varchar(500)` 인덱스 추가는 **하지 않습니다.** 546만 행 대상 인덱스 생성이
Docker MySQL 을 `fsync() returned EIO` 로 죽인 전례가 있습니다
(`docs/handoff/2026-08-09_bid_search_meilisearch_handoff.md` 2장).

### 8.8 이 판정에서 얻은 것

**"증분화하면 빨라진다" 는 직관은 집계 함수가 합산 가능한지만으로 결정되지
않습니다.** 저장 형태(top-K 냐 전량이냐), 차원의 카디널리티, 원본의 불변성이
모두 걸립니다. 이번에는 세 번째(변경공고)가 가장 큰 장애물이었는데 착수 전에는
보이지 않던 것입니다.

**남의 사례를 옮길 때는 우리 병목의 위치를 먼저 확인해야 합니다.** Canva 의
문제는 stateless 암호화 쿠키 때문에 폐지 목록을 수백 pod 에 전파해야 하는
것이었고, 우리 세션은 Redis 에 상태를 두어 `destroy_session` 이 O(1) 삭제
하나입니다(`src/app/core/security.py`). 같은 글에서 가져올 것은 세션 설계가
아니라 "읽기가 잦고 변경이 드문 데이터의 파티셔닝" 이라는 원칙뿐이었습니다.
