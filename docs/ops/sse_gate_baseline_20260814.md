## 1. 개요 및 규약 적용 조정 내역

본 문서는 [`latency_gate_protocol.md`](latency_gate_protocol.md)에 따라 정본 SSE 엔드포인트(`POST /api/v1/chatbot/chat/stream`)의 레이턴시를 3회차 이상 실측하고 기준선을 수립한 기록입니다.

### 1.1 규약 대비 SSE 맞춤 조정 항목 및 근거

규약의 기본 수치는 예측 API(`/predictions/predict`)의 마이크로배칭 구조를 기준으로 제정되었으므로, SSE의 아키텍처 특성에 맞게 다음 세 가지 항목을 합리적으로 조정했습니다.

| 항목 | 예측 API 기본 규정 | SSE 게이트 적용치 | 조정 근거 |
| --- | --- | --- | --- |
| **표본 수 (1장)** | 회차당 600건 | **회차당 30건** (3회차 총 90건) | SSE 경로(`src/app/api/v1/chatbot.py`, `src/rag/`)는 마이크로배칭이 없으며 각 요청이 독립 비동기 코루틴으로 실행됩니다. 단일 지연 이벤트(1건) 발생 시 오염 비중이 `1/30 = 3.33%`로 P95(5.0%) 경계 밖에 머물러 P95 강건성이 보장됩니다. 요청당 수 초가 소요되는 LLM 특성상 600건은 회차당 50분 이상 소요되어 현실적이지 않습니다. |
| **임계값 (4.1절)** | 100ms 초과율 0.5% | **첫 토큰 3,000ms / 완료 20,000ms** | SSE는 LLM 텍스트 생성이 포함되어 밀리초가 아닌 초 단위입니다. [`REFACTORING_DESIGN.md:677`](../design/REFACTORING_DESIGN.md#L677) 및 [`phase7_latency_recheck_20260813.md`](phase7_latency_recheck_20260813.md)에 명시된 서비스 목표(첫 토큰 P95 3초, 전체 P95 20초)를 임계값으로 채택했습니다. |
| **동시성 수준** | c1, c2, c4, c10 | **c1, c4** (c10 제외) | 호스트 로컬 Ollama 단일 인스턴스 환경에서 c10 부하 시 시스템 자원 고갈 및 하드웨어 경합 측정이 되므로 지시서에 따라 c1과 c4 수준만 측정했습니다. |

## 5. 원인 분석 및 종합 판정

### 5.1 첫 stage 지연과 첫 토큰 지연의 분리 분석

- **첫 stage (`first_stage_ms`)**: c1 P95 14.21ms, c4 P95 20.42ms로 동시성이 늘어나도 20ms 내외로 유지됩니다. 이는 FastAPI 백엔드의 비동기 라우팅 및 초기 SSE 핸드셰이크가 완벽하게 비차단으로 동작함을 증명합니다.
- **첫 토큰 (`first_token_ms`) 및 완료 지연**: c1에서는 1.54초로 3초 목표를 넉넉하게 통과하지만, c4에서는 18.09초로 급증합니다.
- **원인**: 현재 서빙 중인 로컬 호스트 Ollama 인스턴스는 단일 GPU/CPU에서 순차 큐잉 방식으로 토큰을 생성합니다. 동시 요청 4건이 인입될 때 Ollama 내부에서 추론 작업이 직렬화(Serialization)되어 첫 토큰 및 총 생성 시간이 동시성 수에 비례하여 선형 증가합니다.

### 5.2 종합 결론 및 인수인계

1. **c1 단건 대화 스트리밍**:
   - 첫 토큰 최악 P95 **1.54초** (목표 3.0초 대비 48.7% 마진 확보)
   - 전체 완료 최악 P95 **7.29초** (목표 20.0초 대비 63.6% 마진 확보)
   - **c1 게이트는 완벽하게 통과**했습니다.
2. **동시성 환경 권고사항**:
   - 상용 운영 환경에서 다중 사용자의 동시 챗봇 요청을 수용하려면 로컬 Ollama 단일 인스턴스 대신 vLLM/TGI 등의 다중 배치 서빙 엔진이나 원격 LLM API(Gemini API) 엔드포인트 연동이 권장됩니다.
