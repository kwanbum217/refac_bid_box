# 공고 기초금액 이상치와 집계 오버플로우

> **작성일**: 2026-09-04
> **버전**: v1.0.0
> **상태**: 코드 수정 완료. 원본 데이터는 G1 원칙에 따라 보존
> **대상**: `src/app/services/dashboard.py` 금액 집계 경로, `src/app/models/bids.py` 금액 변환
> **관련 화면**: `/bids/dashboard/`, `/bids/compare/`

## 1. 증상

`GET /api/v1/bids/compare-stats` 응답의 공고 총액이 음수였습니다.

| 항목 | 값 |
| --- | --- |
| `announce_count` | 5,497,840 |
| `announce_total_base_amount` | -6,063,896,128,872,295,352 |
| `agency_announce_top10` 1위 | 강원특별자치도 양양군 137,150,113,242,120,737원 (324건) |

324건짜리 기관이 137경 원으로 1위에 오르면서 기관 순위 전체가 무의미해진
상태였습니다.

## 2. 원인

두 가지가 겹쳤습니다. 하나는 원본 데이터, 하나는 집계 코드입니다.

### 2.1 조달청 원본 금액 이상치 33건

전체 5,497,840건 중 기초금액이 100조원을 넘는 행이 33건입니다. 세 부류이며
모두 조달청이 준 원본 값이 그렇습니다. 수집 파서가 만들어낸 값이 아닙니다.

| 부류 | 건수 | 예시 | 정상 참고값(`presmpt_prce`) |
| --- | --- | --- | --- |
| 자릿수 중복 입력 | 4 | `137150000137150000` (`137150000` 반복) | 124,681,818 |
| 더미값 | 27 | `111111111111111` (`presmpt_prce` 는 전부 `101010101010101`) | - |
| BIGINT 포화 | 2 | `base_amount` 가 `9223372036854775807` | 111,272,728 |

BIGINT 포화 2건은 성격이 다릅니다. 원본 `bdgtAmt` 가
`12240000012240000011`, `26849000084793201743` 로 20자리라 BIGINT 범위를 넘고,
적재 시점에 조용히 클램프되어 `base_amount` 컬럼에 최대값이 들어갔습니다.
이 두 건만으로 합계에 약 1.8e19 가 더해집니다.

### 2.2 BIGINT 로 누적한 집계

`bid_dataset_summaries.total_amount` 컬럼은 `decimal(30,0)` 이라 자릿수가
충분합니다. 그런데도 음수가 저장돼 있었습니다. 집계 표현식이 행마다
`CAST(... AS BigInteger)` 한 뒤 `SUM` 했기 때문에, 컬럼에 담기기 전에 이미
범위를 넘겨 wrap 된 값이 만들어졌습니다.

이상치를 걷어내도 남는 구조적 위험입니다. 데이터가 계속 쌓이면 정상값만으로도
같은 일이 납니다.

### 2.3 파싱 규칙 불일치

같은 금액을 읽는 경로가 둘인데 규칙이 달랐습니다.

| 경로 | 콤마 처리 | 큰 정수 |
| --- | --- | --- |
| `models.bids._coerce_amount` (상세 화면) | 제거함 | `int(float(...))` 로 정밀도 손실 |
| `dashboard._announcement_amount_expr` (집계) | 하지 않음 | - |

`int(float("12240000012240000011"))` 은 `12240000012240001024` 가 됩니다.
2^53 을 넘는 자릿수에서 값이 어긋나며, 해당 자릿수의 원본이 실재합니다.

## 3. 조치

원본 데이터는 건드리지 않았습니다. G1 원칙상 `raw_data` 는 조달청이 준 그대로
두고, 집계에서만 배제합니다. 재수집해도 조달청 원본이 같은 값이므로 교정으로
해결되지 않습니다.

| 항목 | 조치 |
| --- | --- |
| 누적 타입 | `Numeric(30, 0)` 으로 캐스팅해 DECIMAL 로 누적 |
| 이상치 | `MAX_REASONABLE_ANNOUNCEMENT_AMOUNT`(100조) 초과 시 집계에서 `NULL` |
| 파싱 규칙 | 집계 SQL 에도 콤마 제거 추가, `_coerce_amount` 는 정수 문자열을 `int()` 로 직접 변환 |

상한을 100조로 잡은 근거는 실측입니다. 100조 초과가 33건, 10조 초과가 49건이며,
그 사이 16건에는 실재하는 최대 규모 사업(가덕도신공항 약 10.7조)이 들어 있습니다.
상한을 10조로 낮추면 이상치 제거가 아니라 데이터 절단이 됩니다.

## 4. 남은 과제

### 4.1 BIGINT 포화 2건의 `base_amount`

`R25BK01131785`, `R25BK01210563` 의 `base_amount` 컬럼에 든
`9223372036854775807` 은 조달청 원본이 아니라 **적재 과정이 만들어낸 값**입니다.
원본 보존 대상이 아니라 오히려 고쳐야 할 값(`NULL`)으로 보이나, 기존 DB 값
변경이라 판단을 보류했습니다. 현재는 집계에서 배제되므로 화면에는 영향이
없습니다.

### 4.2 수집 단계의 범위 검증 부재

BIGINT 범위를 넘는 값이 경고 없이 클램프되어 적재됩니다. 수집 시점에 걸러
적재를 막거나, 최소한 기록을 남기는 편이 낫습니다.

### 4.3 `agency_top10` 성능

본 문서의 조사는 `compare-stats` 무응답에서 출발했습니다. 병목은
`agency_announce_top10` 이며, 웜 상태 31.97초입니다. 금액을 `raw_data` longtext
에서 JSON 파싱해 1년치 약 23만 행에 `SUM` + `GROUP BY` + `ORDER BY` 를 걸기
때문에 인덱스가 닿지 않습니다. 캐시가 살아 있는 동안만 빠르고, 수집으로 캐시
키가 바뀌면 다시 느려집니다. 별도 과제입니다.

| 쿼리 | 웜 상태 |
| --- | --- |
| `matched_count` | 2.20s |
| `announce_by_month` | 0.39s |
| `result_by_month` | 0.22s |
| `agency_top10` | 31.97s |
