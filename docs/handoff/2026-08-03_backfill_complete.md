## 3. 함께 고친 두 가지 결함

### 3.1 수집기 계약체결방법 필드명 오류 (커밋 `15d2dd2`)

G2B 응답의 계약체결방법 필드명은 `cntrctCnclsMthdNm` 인데 수집기가 응답에
존재하지 않는 `cntrctMthdNm` 을 읽고 있었습니다. `_get_text` 가 `None` 을
돌려주어 수집은 성공으로 끝나고 컬럼만 통째로 비었습니다.

`raw_data` 에 원본 응답이 남아 있어 API 재수집 없이 복구했습니다.

| 항목 | 값 |
| --- | ---: |
| 갱신 | 3,366,849건 |
| 채워진 행 | 2,062,760 -> 3,999,393 |
| 소요 | 4분 13초 |
| 처리량 (실측) | 28,947 행/초 |

복구 스크립트는 [`scripts/repair_contract_method.py`](../../scripts/repair_contract_method.py)
입니다. 이미 값이 있는 행은 건드리지 않으므로 다시 실행해도 안전합니다.

### 3.2 공고-낙찰 조인 차수 자리수 불일치 (커밋 `beccd3b`)

G2B 는 같은 차수를 공고 API 에서 3자리(`000`), 낙찰 API 에서 2자리(`00`)
로 내려줍니다. 정규화 없이 문자열로 이으면 조인이 거의 전부 실패합니다.

물품 실측입니다. 공고는 이미 완전한데도 조인율이 3.40% 였습니다.

| 조인 방식 | 조인율 |
| --- | ---: |
| 공고번호 + 차수 (정규화 없음) | 3.40% |
| 차수 자리수 정규화 후 | **99.91%** |

**학습 파이프라인은 영향이 없습니다.** `src/ml/dataset.py` 의
`_normalized_ord` 가 이미 정규화하고 있었습니다. 실제 피해자는
`kb_builder.py` 로, 공고 문서에 낙찰 정보가 붙지 않아 RAG 답변에서
낙찰 결과가 빠져 있었습니다.

`normalize_bid_ntce_ord` 를 `src/app/models/bids.py` 에 추가하고
`kb_builder` 조인 키를 교체했습니다.

> 이 발견으로 "조인율 5.2% 는 공고 결손 탓" 이라는 2026-08-02 문서의 진단이
> 부분적으로 틀렸음이 확인됐습니다. 실제 결손은 용역뿐이었고, 물품·건설의
> 낮은 조인율은 차수 버그였습니다.

## 4. 성능 실측 (2026-08-03)

덩어리는 240일 = 15일 구간 16개입니다. API 가 한 번에 15일·999건까지만
주므로 동시 요청 16개를 채우기 위한 크기입니다.

| 항목 | 값 |
| --- | ---: |
| 덩어리당 적재 건수 (평균) | 107,212 |
| 덩어리당 API 호출 | 약 112회 |
| 덩어리당 소요 | 약 72초 |
| 그중 API 수신 | 약 61초 (85%) |
| 그중 DB 적재 | 약 11초 (15%) |

적재 경로를 쪼갠 실측입니다.

| 구간 | 처리량 |
| --- | ---: |
| MariaDB 순수 쓰기 (서버 내부) | 51,000 행/초 |
| 실제 경로 (Python -> 전송 -> 쓰기) | 9,500 행/초 |

5배 차이는 Python 측 비용입니다. `raw_data` 가 행당 평균 5.3KB 라
dict 생성·JSON 직렬화·전송이 디스크 쓰기보다 4배 비쌉니다.

**병목은 DB 가 아니라 API 수신입니다.** DB 적재를 0초로 만들어도 덩어리당
72초가 61초가 될 뿐입니다. 더 빠르게 하려면 동시 요청 수를 올려야 하는데,
2026-08-02 실측에서 32 는 차단이 발생했으므로 16 이 현재 안전 상한입니다.
API 호출 건수 상향이 반영되면 동시성을 다시 실측할 여지가 있습니다.

### 5.2 Redis 기동과 대시보드 집계 예열

백필 중 Redis 가 내려가 있어 캐시 예열이 메모리 캐시로 대체됐습니다.
적재 자체에는 영향이 없으나 대시보드 첫 조회가 느립니다.

```bash
make up   # 또는 docker compose -f docker/docker-compose.yml up -d redis
.venv/bin/python -c "

from src.app.services.dashboard import warm_dashboard_stats_cache
```

Redis 는 내릴 때 `SHUTDOWN NOSAVE` 를 씁니다.

### 5.3 재학습 R2 재측정

```bash
.venv/bin/python -m src.tasks.retrain_task
```

**소요 시간에 근거가 없습니다.** 기존 `retrain_logs` 3건은 E2E 테스트
산출물이라 시간 정보가 없습니다. 조인 가능한 학습 표본이 약 3만 건에서
350만 건 규모로 늘어 데이터셋 생성과 교차검증 비용이 함께 뜁니다.
`limit` 을 걸어 짧게 재보고 전량 학습 시간을 역산하는 편이 확실합니다.

이번 백필로 예정가격·기초금액이 살아났으므로, 기관 이력만으로 낸
R2 0.376 이 개선될 여지가 있습니다.
