### 3.2 보완 영역 브라우저 확인

### 3.3 재색인과 필터 확인

`9db188a5` 병합 뒤 로컬 Meilisearch 를 오늘 런북 4.3.1 절 절차(`docker compose exec -e MEILI_TIMEOUT_SECONDS=30 app python3 scripts/sync_search_index.py`)로 전체 재색인했다.

| 항목 | 값 |
| --- | --- |
| 적재 | 공고 4,879,588건, 낙찰 3,439,172건 |
| 클라이언트 시간 | 1,011초. 2026-09-22 실측 581.9초보다 길다. 공고 문서마다 판정 함수를 돌리는 비용이 더해졌다 |
| 서버 큐 소진 | 클라이언트 종료 후 30초 |
| 문서 적재 실패 | 0건. 오늘 실패 작업은 이미 있는 인덱스 생성 시도(`index_already_exists`) 1건뿐이며 코드가 의도적으로 허용한다 |
| `qualification_analyzable = true` | 4,567건 (용역 공고 문서 1,860,016건 중). 규칙 레지스트리가 2026-05-26 개정 이후 별표만 담아 그 전 공고는 판별되지 않는다 |

재색인 뒤 앱을 재시작하고 확인했다. `/bids/?qual=1` 1·2쪽과 `cat=Servc&qual=1` 은 각 20행이 모두 뱃지가 붙은 공고였고, `cat=Thng&qual=1` 은 0행이었다. 필터는 인덱스에 저장된 값으로 거르고 뱃지는 렌더 때 DB 원문으로 다시 판별하므로, 두 경로의 판정이 일치함을 뜻한다. 체크박스 선택 상태와 페이지 링크의 `qual=1` 유지도 확인했다.

재색인 시간이 늘어난 만큼 RTO 단계표의 재색인 예산(42분)과 실측(839.3초)은 다음 restore drill 에서 다시 잰다.
