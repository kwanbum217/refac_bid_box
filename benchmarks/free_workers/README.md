## 1. 무엇을 재는가

**모델이 아니라 워커 스택을 잽니다.** 하나의 측정 단위는
`모델 + 제공자 + CLI 하네스` 셋의 조합입니다. 같은 모델이라도 OpenCode 로
띄운 것과 Kimi 로 띄운 것은 다른 스택이며, 승인 정책과 대화 경로가 달라
결과가 갈립니다.

`or-free/nemotron-ultra`(Kimi)와 `opencode/nemotron-3-ultra-free`(OpenCode)를
따로 잰 이유가 이것입니다.

## 3. 채점 방법

각 스택은 격리 워크트리에서 같은 Capsule 을 받아 실제로 파일을 고치고
테스트를 씁니다. **각자 자기 테스트를 통과하므로 그것으로는 우열이
갈리지 않습니다.**

그래서 `scoring.py` 를 따로 둡니다. 구현 내부(함수명, 상태 파일 스키마)를
보지 않고 `main()` 의 종료 코드와 stdout 만 검사하므로, 어떤 구현이든 같은
계약을 지켰다면 통과합니다.

```bash
uv run python benchmarks/free_workers/scoring.py <임시디렉터리>
```

## 4. 이 벤치마크로 말할 수 있는 것과 없는 것

**말할 수 있는 것**

- 이 스택이 저위험 Python builder 과제를 완주하는가 (pass/fail)
- 완주하지 못한다면 어떤 방식으로 실패하는가

**말할 수 없는 것**

- 스택 사이의 속도 우열. `results/2026-08-20.json` 은 스택당 1회 실행이며,
  무료 엔드포인트의 큐·콜드스타트·429 편차를 분리하지 못했습니다.
- `benchmarker`, `documenter` 적합성. 잰 적이 없습니다.
- `reviewer` 적합성. 병합 판정에 쓰이는 임계 경로라 무료 풀에 열지 않습니다.
